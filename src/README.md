# เรียนรู้ Rust ด้วยลิงก์ลิสต์ที่เยอะเกินเหตุ

> ติดปัญหาตรงไหน หรืออยากเข้าไปดูโค้ดเวอร์ชันสุดท้ายทั้งหมดทีเดียวเลยใช่ไหม?
> [ทุกอย่างอยู่บน GitHub!][github]

> **หมายเหตุ**: หนังสือฉบับปัจจุบันเขียนขึ้นสำหรับ Rust 2018
> ซึ่งเปิดตัวครั้งแรกพร้อมกับ rustc 1.31 (8 ธ.ค. 2018) หากทูลเชน Rust ของคุณ
> ใหม่พอ ไฟล์ `Cargo.toml` ที่คำสั่ง `cargo new` สร้างขึ้นมาจะมีบรรทัด
> `edition = "2018"` ระบุไว้ (หรือถ้าคุณกำลังอ่านเล่มนี้อยู่ในอนาคตอันไกลโพ้น
> ก็อาจจะเป็นตัวเลขที่ใหม่กว่านั้นไปแล้วก็ได้!) การใช้ทูลเชนเวอร์ชันเก่ากว่านั้นก็ยังพอทำได้อยู่
> แต่มันจะแอบปลดล็อก **โหมดฮาร์ดคอร์ (hardmode)** ลับ ๆ ซึ่งคุณจะเจอดงข้อผิดพลาด
> จากคอมไพเลอร์โผล่มาเพียบโดยที่หนังสือเล่มนี้ไม่ได้พูดถึงเลยสักแอะ โห ฟังดูน่าสนุกพิลึก!

ผมมักจะโดนถามอยู่บ่อย ๆ ว่าจะเขียนลิงก์ลิสต์ใน Rust ยังไงดี ซึ่งเอาจริง ๆ คำตอบมันขึ้นอยู่กับ
โจทย์และความต้องการของคุณล้วน ๆ แถมยังไม่ใช่คำถามที่จะตอบส่ง ๆ ให้จบได้ในสองสามนาที
ผมก็เลยตัดสินใจเขียนหนังสือเล่มนี้ขึ้นมา เพื่อตอบคำถามนี้แบบเจาะลึกให้กระจ่างม้วนเดียวจบไปเลย

ในซีรีส์ชุดนี้ ผมจะสอนคุณทั้งการเขียนโปรแกรม Rust ระดับพื้นฐานไปจนถึงระดับสูง
ผ่านการลงมือเขียนลิงก์ลิสต์ทั้งหมด 6 แบบด้วยกัน ซึ่งเมื่อทำจนครบ คุณจะได้เรียนรู้:

* ชนิดของตัวชี้และเรเฟอเรนซ์ต่าง ๆ เหล่านี้: `&`, `&mut`, `Box`, `Rc`, `Arc`, `*const`, `*mut`, `NonNull`(?)
* ความเป็นเจ้าของ (ownership), การยืม (borrowing), ความสามารถในการแก้ไขข้อมูลตามตัวแปรแม่ (inherited mutability), ความสามารถในการแก้ไขข้อมูลภายใน (interior mutability), เทรต Copy
* สารพัดคีย์เวิร์ด: struct, enum, fn, pub, impl, use, ...
* การจับคู่แพตเทิร์น (pattern matching), เจเนอริก (generics), ดีสตรัคเตอร์ (destructors)
* การเขียนเทสต์, การติดตั้งทูลเชนรุ่นใหม่ ๆ, การใช้งาน `miri`
* โลกแห่ง Unsafe Rust: ตัวชี้ดิบ (raw pointers), การมีตัวชี้ชี้ซ้ำซ้อน (aliasing), โมเดลการยืมแบบซ้อน (stacked borrows), UnsafeCell, แวเรียนซ์ (variance)

ใช่แล้ว ลิงก์ลิสต์มันเลวร้ายขนาดนั้นแหละ! แค่จะเขียนมันขึ้นมาให้ใช้งานได้จริง คุณก็ต้องงัดสารพัดแนวคิดพวกนี้ออกมาใช้จนครบ

เพื่อให้เห็นภาพตรงกัน ผมจะเขียนคำสั่งทุกอย่างที่ผมพิมพ์ลงในเทอร์มินัลให้ดูด้วย
และผมจะใช้ Cargo ซึ่งเป็นตัวจัดการแพ็กเกจมาตรฐานของ Rust ในการพัฒนาโปรเจกต์นี้
แม้จริง ๆ แล้ว Cargo จะไม่ใช่สิ่งจำเป็นไฟลต์บังคับในการเขียนโค้ด Rust แต่มัน*ดีกว่าการสั่ง rustc เพียว ๆ แบบคนละเรื่อง*
ถ้าคุณแค่อยากลองเล่นขำ ๆ ก็สามารถรันโปรแกรมง่าย ๆ ผ่านเบราว์เซอร์บน [play.rust-lang.org][play] ได้เลย

ในบทหลัง ๆ เราจะใช้ `rustup` เพื่อติดตั้งเครื่องมือเพิ่มเติมของ Rust
ผมขอแนะนำเป็นอย่างยิ่งให้[ติดตั้งทูลเชน Rust ทั้งหมดของคุณด้วย rustup](https://www.rust-lang.org/tools/install)

เอาล่ะ มาเริ่มสร้างโปรเจกต์ของเรากันเลย:

```text
> cargo new --lib lists
> cd lists
```

เราจะแยกโค้ดของลิสต์แต่ละตัวไว้ในไฟล์ของตัวเอง เพื่อจะได้ไม่ทำลายงานเดิมที่ทำไปแล้ว

และคงต้องบอกไว้ตรงนี้เลยว่า ประสบการณ์การเรียนรู้ Rust ของแท้นั้น
คือการเขียนโค้ดลงไป แล้วปล่อยให้คอมไพเลอร์แหกปากด่าคุณ จากนั้นคุณก็ต้องมานั่งกุมขมับคิดว่ามันหมายความว่าอะไรกันแน่!
ซึ่งผมจะพยายามทำให้คุณได้สัมผัสโมเมนต์แบบนี้บ่อยที่สุดเท่าที่จะทำได้
เพราะการหัดอ่านและทำความเข้าใจข้อความแจ้งเตือนความผิดพลาด (error messages) รวมถึงเอกสารประกอบชั้นยอดของ Rust
นั้น*สำคัญอย่างยิ่งยวด*ต่อการเป็นโปรแกรมเมอร์ Rust ที่เก่งกาจและทำงานได้อย่างมีประสิทธิภาพ

เอาจริง ๆ ที่พูดไปตะกี้ก็แอบโม้นิดหน่อย เพราะตอนที่ผมเขียนหนังสือเล่มนี้จริง ๆ ผมเจอคอมไพเลอร์ด่า*เยอะกว่าที่เอามาโชว์มาก*
โดยเฉพาะในบทหลัง ๆ ผมจะไม่ยกพวก error ไร้สาระประเภทพิมพ์ตกหรือก็อปแปะผิดแบบที่คุณน่าจะเคยเจอกันในทุกภาษามาให้ดูหรอกนะ
นี่คือ *'ทัวร์แบบมีไกด์พาชม'* จังหวะที่คอมไพเลอร์แหกปากใส่เราแบบเน้น ๆ ต่างหาก

เราจะค่อย ๆ ไปกันทีละสเต็ป และบอกไว้ก่อนเลยนะว่าตลอดทั้งเล่มนี้ผมจะไม่ทำตัวซีเรียสเคร่งเครียดอะไรทั้งนั้น
ให้ตายสิ ผมคิดว่าการเขียนโปรแกรมมันควรจะสนุกไม่ใช่เหรอ!
ถ้าคุณเป็นพวกที่ชอบเนื้อหาวิชาการอัดแน่น ขึงขัง จริงจัง และเป็นทางการระดับเป๊ะทุกกระเบียดนิ้วแล้วละก็
หนังสือเล่มนี้ไม่ใช่สำหรับคุณอย่างแน่นอน และผมก็คงช่วยอะไรคุณไม่ได้ด้วย...
คุณมาผิดที่แล้วล่ะ

# ประกาศเตือนภัยเพื่อสาธารณชน (ที่จำเป็นต้องบอก)

ขอพูดให้เคลียร์ 100% ตรงนี้เลยนะ: ผมเกลียดลิงก์ลิสต์เข้าไส้ เกลียดแบบสุดขั้วหัวใจ
ลิงก์ลิสต์เป็นโครงสร้างข้อมูลที่ห่วยแตกสิ้นดี แน่นอนว่ามันอาจจะมีบางกรณีที่มันทำงานได้ยอดเยี่ยมจริง ๆ อยู่บ้าง เช่น:

* คุณต้องการ*แยกหรือรวม*ลิสต์ขนาดใหญ่*เป็นจำนวนมาก*
* คุณกำลังทำระบบ concurrent แบบ lock-free เจ๋ง ๆ
* คุณกำลังเขียนงานสาย kernel หรือ embedded และจำเป็นต้องใช้ intrusive list
* คุณใช้ภาษาตระกูล pure functional ซึ่งความหมายเชิงภาษาที่จำกัดและการห้ามแก้ไขข้อมูล (immutability)
  ทำให้ลิงก์ลิสต์กลายเป็นของที่ใช้งานง่ายกว่าโครงสร้างอื่น
* ...และอีกสารพัด!

แต่เคสพวกนี้มัน*หายากระดับงมเข็มในมหาสมุทร*สำหรับคนเขียน Rust ทั่วไป!
99% ของเวลาทั้งหมด คุณควรใช้ `Vec` (สแต็กบนอาร์เรย์) และอีก 99% ของ 1% ที่เหลือ
คุณควรใช้ `VecDeque` (เดกบนอาร์เรย์) โครงสร้างข้อมูลพวกนี้เหนือชั้นกว่าเห็น ๆ สำหรับงานแทบทุกประเภท
เพราะมันจัดสรรหน่วยความจำน้อยกว่า เปลืองเมโมรีน้อยกว่า แถมยังเข้าถึงข้อมูลแบบสุ่ม (random access) ได้จริง
และมีความเป็นมิตรกับแคช (cache locality) ดีกว่าเยอะมาก

ลิงก์ลิสต์เป็นโครงสร้างข้อมูลที่ทั้ง*เฉพาะทาง (niche)* และ*อยู่นอกกระแสหลัก*พอ ๆ กับ trie เลยด้วยซ้ำ
คงไม่มีใครแปลกใจถ้าผมจะบอกว่า trie เป็นโครงสร้างข้อมูลเฉพาะกลุ่มที่โปรแกรมเมอร์ทั่ว ๆ ไปสามารถทำงานตลอดชีวิตโดยไม่ต้องเรียนรู้มันเลยก็ยังมีความสุขดีได้
-- แต่ลิงก์ลิสต์กลับมีสถานะโด่งดังเยี่ยงดาราฮอลลีวูดอย่างน่าประหลาด! เราสอนเด็กมหาลัยทุกคนให้เขียนลิงก์ลิสต์
มันเป็นคอลเลกชันเฉพาะทางเพียงตัวเดียว[ที่ผมพยายามจะฆ่าตัดตอนทิ้งจาก std::collections แต่ไม่สำเร็จ][rust-std-list]
และมันยังเป็น[*'เดอะลิสต์'* ใน C++][cpp-std-list] อีกต่างหาก!

พวกเราทุกคนในคอมมูนิตี้ควรจะร่วมใจกันบอกว่า *ไม่* ให้กับลิงก์ลิสต์ในฐานะโครงสร้างข้อมูล "มาตรฐาน" ได้แล้ว
มันเป็นโครงสร้างข้อมูลที่ใช้ได้ดีกับกรณีเฉพาะทางที่ยอดเยี่ยมหลายกรณีก็จริง
แต่กรณีเหล่านั้น*เป็นข้อยกเว้น* ไม่ใช่เรื่องปกติธรรมดา

มีคนจำนวนไม่น้อยที่ดูเหมือนจะอ่านแค่ย่อหน้าแรกของประกาศนี้แล้วก็หยุดอ่าน
คือแบบว่า จู่ ๆ เขาก็พยายามจะเถียงผมด้วยการยกหนึ่งในตัวอย่างที่ผมเขียนไว้ใน
รายการ*กรณีการใช้งานที่ยอดเยี่ยม* ซึ่งเป็นสิ่งที่ผมเพิ่งจะเขียนบอกไปต่อจากย่อหน้าแรกแท้ ๆ นั่นแหละ!

เพื่อที่ผมจะได้แปะลิงก์ส่งมายังข้อโต้แย้งโดยละเอียดนี้ได้โดยตรง
ต่อไปนี้คือสารพัดข้อโต้แย้งที่ผมมักจะเจออยู่เป็นประจำ พร้อมกับคำตอบของผม
ถ้าคุณแค่อยากเรียนรู้ Rust เฉย ๆ จะกดข้ามไปที่[บทแรก](first.md)เลยก็ได้นะ!

## ประสิทธิภาพไม่ได้สำคัญเสมอไป

ใช่เลย! แอปพลิเคชันของคุณอาจจะติดคอขวดที่ I/O หรือโค้ดส่วนนั้นอาจจะอยู่ใน cold path
ที่ไม่ค่อยได้ถูกเรียกใช้ ซึ่งมันก็ไม่ได้สำคัญอะไรจริง ๆ นั่นแหละ แต่นี่ไม่ใช่เหตุผลที่จะเอามาอ้างเพื่อใช้ลิงก์ลิสต์เลยสักนิด
นี่มันเป็นข้ออ้างสำหรับการจะหยิบ*อะไรก็ได้ทั้งนั้น*มาใช้ต่างหากเล่า! แล้วจะทนใช้ลิงก์ลิสต์ไปทำไมล่ะ?
ไปใช้ linked hash map โน่นเลยสิ!

ถ้าประสิทธิภาพมันไม่สำคัญขนาดนั้น การเลือกใช้ค่าตั้งต้นตามธรรมชาติที่เรียบง่ายอย่างอาร์เรย์
มันก็ย่อม*ไม่มีปัญหาอะไรอยู่แล้วจริงไหม*

## พวกมันมี O(1) สำหรับ split-append-insert-remove ถ้าคุณมีตัวชี้อยู่ตรงนั้น

ก็จริง! แต่เหมือนอย่างที่ [Bjarne Stroustrup เคยชี้ให้เห็นไว้][bjarne] นั่นแหละว่า *เอาเข้าจริงเรื่องนี้มันแทบไม่มีความหมายเลย*
ถ้าเวลาที่คุณต้องใช้เพื่อวิ่งหาตัวชี้นั้น นานกว่าเวลาที่ใช้ก็อปปี้ข้อมูลทั้งหมดในอาร์เรย์แบบเทียบกันไม่ติด
(ซึ่งจริง ๆ แล้วอาร์เรย์มันก็อปปี้ได้เร็วสุด ๆ)

เว้นเสียแต่ว่าภาระงานของคุณจะหมดไปกับต้นทุนการแยกและเชื่อมต่อลิสต์เป็นหลักจริง ๆ ไม่อย่างนั้นบทลงโทษที่*การทำงานอื่น ๆ แทบทุกอย่าง*
ต้องแบกรับจากผลกระทบของแคชและความซับซ้อนของโค้ด จะกวาดผลกำไรในทางทฤษฎีทิ้งจนหมดเกลี้ยง

*แต่ก็นั่นแหละ ถ้าคุณทำ profiling แอปพลิเคชันของคุณแล้วพบว่ามันเสียเวลากับการแยกและรวมลิสต์มหาศาลจริง ๆ ลิงก์ลิสต์ก็อาจจะช่วยให้คุณได้ประโยชน์ขึ้นมาบ้าง*

## ผมจ่ายค่าเฉลี่ย (amortization) ไม่ไหว

โอ้โห คุณกำลังก้าวเข้าสู่พื้นที่เฉพาะทางสุด ๆ แล้วล่ะ เพราะคนส่วนใหญ่เขารับต้นทุนแบบเฉลี่ยกันได้สบาย ๆ
แต่ถึงอย่างนั้น อาร์เรย์จะมีต้นทุนเฉลี่ยก็แค่*ในกรณีที่แย่ที่สุด*เท่านั้น การใช้อาร์เรย์ไม่ได้แปลว่าคุณจะต้องจ่ายต้นทุนแบบเฉลี่ยเสมอไป
ถ้าคุณรู้ล่วงหน้าหรือพอกะขอบเขตบนได้ว่าจะเก็บข้อมูลกี่ตัว คุณก็สามารถจองพื้นที่หน่วยความจำล่วงหน้า (pre-reserve) เท่าที่ต้องการได้เลย
จากประสบการณ์ของผม การกะจำนวนข้อมูลล่วงหน้าเป็นเรื่องที่*เจอบ่อยมาก* ยิ่งใน Rust ด้วยแล้ว
iterator ทุกตัวจะมี `size_hint` มาให้สำหรับกรณีนี้โดยเฉพาะ

เมื่อทำแบบนั้น `push` และ `pop` ก็จะกลายเป็นการทำงานแบบ O(1) อย่างแท้จริง
แถมยังจะ*เร็วกว่าอย่างเห็นได้ชัด*เมื่อเทียบกับ `push` และ `pop` บนลิงก์ลิสต์
เพราะคุณแค่ขยับ pointer offset เขียนไบต์ลงไป แล้วบวกตัวเลขอินทิเจอร์ขึ้นไป 1 โดยไม่ต้องวิ่งไปขอความช่วยเหลือจาก allocator หน้าไหนเลย

เป็นไงล่ะ สำหรับความเร็วระดับ low latency?

*แต่ก็นั่นแหละ ถ้าคุณคาดเดาปริมาณงานไม่ได้จริง ๆ ลิงก์ลิสต์ก็อาจช่วยประหยัดเวลา latency ในกรณีเลวร้ายที่สุดได้บ้าง!*

## ลิงก์ลิสต์ใช้พื้นที่น้อยกว่า

อืม เรื่องนี้มันซับซ้อนหน่อยนะ กลยุทธ์การปรับขนาดอาร์เรย์แบบ "มาตรฐาน" คือการขยายหรือหดขนาด
โดยยอมให้มีพื้นที่ว่างในอาร์เรย์ได้สูงสุดถึงครึ่งหนึ่ง ซึ่งมันก็เปลืองพื้นที่เยอะจริง ๆ นั่นแหละ
ยิ่งใน Rust เราไม่ได้หดขนาดคอลเลกชันคืนให้อัตโนมัติ (เพราะมันจะเสียเที่ยวเปล่า ๆ ถ้าคุณแค่จะใส่มันกลับเข้ามาใหม่อีก)
ความสูญเปล่าตรงนี้ก็เลยอาจพุ่งสูงเข้าใกล้ไม่มีที่สิ้นสุดได้เลย!

แต่นั่นคือกรณีที่แย่ที่สุดนะ ในกรณีที่ดีที่สุด สแต็กบนอาร์เรย์มีโอเวอร์เฮดแค่ตัวชี้ 3 ตัวสำหรับอาร์เรย์ทั้งก้อน
ซึ่งโดยพื้นฐานคือแทบไม่มีโอเวอร์เฮดเลยด้วยซ้ำ

ในทางกลับกัน ลิงก์ลิสต์จะกินพื้นที่สูญเปล่าไปกับทุก ๆ องค์ประกอบแบบไม่มีข้อยกเว้น
โดยซิงกลีลิงก์ลิสต์จะเสียพื้นที่ไปกับตัวชี้ 1 ตัวต่อโหนด ส่วนดับเบิลลิงก์ลิสต์จะเสียถึง 2 ตัว
และไม่เหมือนกับอาร์เรย์ สัดส่วนความสูญเปล่านี้จะแปรผันตามขนาดขององค์ประกอบข้อมูลด้วย
ถ้าข้อมูลของคุณมีขนาด*มหึมา* ความสูญเปล่านี้ก็จะเข้าใกล้ 0 แต่ถ้าข้อมูลของคุณตัวกระจิริด (เช่น ข้อมูลระดับไบต์)
มันอาจสร้างโอเวอร์เฮดด้านหน่วยความจำสูงถึง 16 เท่า (8 เท่าบนระบบ 32 บิต)!

อันที่จริง มันจะพุ่งไปถึงราว 23 เท่า (11 เท่าบนระบบ 32 บิต) เสียด้วยซ้ำ เพราะจะมีการเพิ่ม padding
เข้าไปในข้อมูลระดับไบต์เพื่อให้ขนาดของโหนดทั้งก้อนเรียงตัวตรงกับขนาดของตัวชี้ (alignment)

นี่ยังคิดบนสมมติฐานกรณีที่ดีที่สุดของ allocator ด้วยนะ ว่าการจัดสรรและคืนหน่วยความจำ (allocate/deallocate)
ของโหนดเกิดขึ้นอย่างหนาแน่นติดกัน และคุณไม่ได้สูญเสียหน่วยความจำให้กับปัญหาการแตกกระจายของพื้นที่ (memory fragmentation)

*แต่ก็นั่นแหละ ถ้าข้อมูลของคุณตัวใหญ่เบิ้ม คาดเดาปริมาณงานไม่ได้เลย และมี allocator ชั้นดี ลิงก์ลิสต์ก็อาจจะช่วยประหยัดเมโมรีให้คุณได้อยู่บ้าง!*

## ฉันใช้ลิงก์ลิสต์ตลอดเวลาในภาษาเชิงฟังก์ชัน

ยอดเยี่ยมเลย! ลิงก์ลิสต์เป็นอะไรที่งดงามมากในภาษาเชิงฟังก์ชัน เพราะคุณสามารถจัดการพวกมันได้
โดยไม่ต้องแก้ไขข้อมูลในหน่วยความจำ (without mutation) สามารถอธิบายโครงสร้างแบบรีเคอร์ซีฟได้
และยังรองรับลิสต์แบบอนันต์ได้ด้วยเวทมนตร์ของการประมวลผลแบบ lazy

โดยเฉพาะอย่างยิ่ง ลิงก์ลิสต์เป็นสิ่งที่ดีเพราะมันเป็นตัวแทนของการวนรอบ (iteration) โดยไม่จำเป็นต้องเก็บสถานะที่เปลี่ยนแปลงค่าได้เลย
ขั้นตอนถัดไปก็แค่ขยับไปดูซับลิสต์ตัวถัดไปเท่านั้น

ซึ่งจริง ๆ แล้ว Rust ก็ทำเรื่องแบบนี้ได้เป็นส่วนใหญ่ผ่าน [อิเทอเรเตอร์][iterators]
พวกมันสามารถทำงานกับลำดับข้อมูลแบบอนันต์ได้ และคุณยัง map, filter, reverse หรือเชื่อมต่อพวกมันเข้าด้วยกันได้เหมือนกับลิสต์ในภาษาเชิงฟังก์ชัน
แถมยังประมวลผลแบบ lazy เหมือนกันเด๊ะ!

นอกจากนี้ Rust ยังช่วยให้คุณจัดการกับช่วงข้อมูลย่อยของอาร์เรย์ได้อย่างง่ายดายด้วย *[สไลซ์][slices]*
การแยก head/tail แบบปกติที่คุณคุ้นเคยในภาษาเชิงฟังก์ชันก็ทำได้[เพียงแค่สั่ง `slice.split_at_mut(1)`][split] เท่านั้น
ในอดีต Rust เคยมีระบบทดลองสำหรับการจับคู่แพตเทิร์นบน slice ที่เจ๋งมาก แม้ว่าฟีเจอร์นั้นจะถูกปรับให้เรียบง่ายลงตอนที่เข้าสู่สถานะเสถียรแล้ว
แต่ [แพตเทิร์นสไลซ์พื้นฐาน][slice-pats] ก็ยังเจ๋งอยู่ดี! และแน่นอนว่าเราแปลงสไลซ์ให้กลายเป็นอิเทอเรเตอร์ได้สบาย ๆ!

*แต่ก็นั่นแหละ ถ้าคุณถูกจำกัดอยู่แค่ในโลกของ immutability ลิงก์ลิสต์ก็เป็นตัวเลือกที่ดีมากจริง ๆ*

โปรดสังเกตนะว่าผมไม่ได้บอกว่าการเขียนโปรแกรมเชิงฟังก์ชันมันด้อยหรือแย่ แต่ในเชิงความหมายแล้วมัน*มีขีดจำกัดโดยพื้นฐาน*:
คุณมักจะถูกจำกัดให้พูดได้แค่ว่าสิ่งต่าง ๆ *เป็น*อย่างไร แต่บอกไม่ได้ว่าควรจะ*ลงมือทำ*มันอย่างไร
ซึ่งจริง ๆ นี่คือ*ฟีเจอร์เด่น*เลยนะ เพราะมันเปิดทางให้คอมไพเลอร์สามารถทำ[การแปลงโค้ดสุดพิสดาร][ghc]ได้สารพัด
และอาจค้นพบวิธี*ที่ดีที่สุด*ในการทำสิ่งต่าง ๆ โดยที่คุณไม่ต้องมานั่งปวดหัวกังวลเอง
ทว่าข้อดีนี้ก็ต้องแลกมาด้วยการที่คุณ*หมดสิทธิ์*เข้าไปควบคุมจัดการมันอย่างละเอียด แม้จะมีช่องทางหลบเลี่ยงอยู่บ้าง
แต่พอถึงจุดหนึ่ง คุณก็ต้องกลับไปเขียนโค้ดแบบโพรซีเดอรัลอยู่ดี

แม้แต่ในภาษาเชิงฟังก์ชันเอง เมื่อถึงเวลาที่จำเป็นต้องใช้โครงสร้างข้อมูลจริง ๆ คุณก็ควรพยายามเลือกใช้โครงสร้างข้อมูลที่เหมาะกับงาน
ใช่ ซิงกลีลิงก์ลิสต์คือเครื่องมือหลักของคุณสำหรับการควบคุมโฟลว์การทำงาน
แต่มันเป็นวิธีที่แย่มากสำหรับการเก็บข้อมูลก้อนใหญ่และการสืบค้นข้อมูลในนั้น

## ลิงก์ลิสต์ดีมากสำหรับการสร้างโครงสร้างข้อมูลแบบคอนเคอร์เรนต์!

ใช่เลย! ถึงแม้ว่าการเขียนโครงสร้างข้อมูลแบบคอนเคอร์เรนต์จะเป็นอะไรที่คนละเรื่องเลย
และไม่ใช่เรื่องที่ควรทำเล่น ๆ แน่นอนว่าไม่ใช่สิ่งที่หลายคนจะ*คิด*อยากทำด้วยซ้ำ
แต่เมื่อมีคนเขียนมันขึ้นมาตัวหนึ่ง คุณก็ไม่ได้เลือกใช้มันเพราะมันเป็นลิงก์ลิสต์หรอก
คุณเลือกใช้เพราะมันเป็นคิว MPSC หรืออะไรทำนองนั้นต่างหาก กลยุทธ์การอิมพลีเมนต์ข้างในกลายเป็นเรื่องไกลตัวไปแล้วในกรณีนี้!

*แต่ก็ใช่ ลิงก์ลิสต์คือฮีโร่ตัวจริงในเงามืดของโลก lock-free concurrency*

## พึมพำ ๆ เคอร์เนล เอ็มเบดเด็ด อะไรสักอย่าง อินทรูซีฟ.

มันเฉพาะทางสุดโต่งไปแล้วคุณ คุณกำลังพูดถึงสถานการณ์ที่คุณไม่ได้ใช้แม้กระทั่ง*รันไทม์*ของภาษาด้วยซ้ำ
นั่นไม่ใช่สัญญาณเตือนภัย (red flag) ตัวเบ้อเริ่มหรอกเหรอว่าคุณกำลังทำอะไรที่พิสดารอยู่?

แถมมันยังอันตรายแบบสุดกู่ (wildly unsafe) อีกด้วย

*แต่เอาเถอะ ตามสบาย ไปสร้างลิสต์แบบ zero-allocation บนสแต็กสุดเท่ของคุณได้เลย*

## อิเทอเรเตอร์ไม่ถูกทำให้ใช้งานไม่ได้จากการเพิ่ม/ลบที่ไม่เกี่ยวข้อง

นั่นคือการเต้นระบำบนเส้นด้ายที่คุณกำลังเล่นอยู่ โดยเฉพาะถ้าคุณไม่มี garbage collector คอยเก็บกวาดให้
ผมอาจจะมองว่าโฟลว์การควบคุมและแพตเทิร์นความเป็นเจ้าของของคุณมันอาจจะอีรุงตุงนังเกินไปหน่อย ขึ้นอยู่กับรายละเอียดของงาน

*แต่ก็ใช่ คุณสามารถทำลูกเล่นพิลึกพิลั่นสุดเจ๋งได้มากมายด้วยเคอร์เซอร์*

## พวกมันง่ายและดีมากสำหรับการสอน!

ก็ใช่สิ คุณกำลังอ่านหนังสือที่เขียนขึ้นมาเพื่อข้ออ้างนั้นอยู่เลยนี่นา
เอาเถอะ ซิงกลีลิงก์ลิสต์มันก็ค่อนข้างเรียบง่ายจริง ๆ นั่นแหละ แต่พอเป็นดับเบิลลิงก์ลิสต์เมื่อไหร่
มันจะเริ่มชวนปวดเศียรเวียนเกล้าขึ้นมาทันที เหมือนอย่างที่เรากำลังจะได้เห็นกันนี่ไงล่ะ
