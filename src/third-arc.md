# Arc (การแชร์แบบอะตอมิก)

เหตุผลหนึ่งในการเลือกใช้ลิงก์ลิสต์แบบเปลี่ยนแปลงค่าไม่ได้ (immutable linked list) ก็คือเพื่อแชร์ข้อมูลข้ามเธรดต่าง ๆ เพราะจริง ๆ แล้ว shared mutable state (สถานะที่แชร์กันและแก้ไขค่าได้) คือต้นตอของหายนะทั้งปวง และหนึ่งในวิธีตัดไฟแต่ต้นลมก็คือการกำจัดส่วนที่ *แก้ไขค่าได้ (mutable)* ทิ้งไปให้หมดตลอดกาล

ติดอยู่อย่างเดียวคือ ลิสต์ของเราตอนนี้ไม่ได้ thread-safe (ปลอดภัยต่อมัลติเธรด) เลยแม้แต่น้อย! เพราะการจะทำให้มัน thread-safe ได้นั้น เราจำเป็นต้องเข้าไปยุ่งกับตัวนับจำนวนอ้างอิง *ในแบบอะตอมิก (atomically)* หาไม่แล้ว หากมีสองเธรดพยายามเพิ่มตัวนับอ้างอิงพร้อม ๆ กัน *ผลลัพธ์อาจจะบันทึกสำเร็จแค่เธรดเดียว* และนั่นอาจทำให้ลิสต์ถูกสั่ง deallocate คืนหน่วยความจำเร็วเกินไปจนโปรแกรมพัง!

และเพื่อให้ได้ความ thread-safe เราจึงต้องเปลี่ยนมาใช้ *`Arc`*! เจ้า `Arc` นั้นเหมือนกับ `Rc` ทุกประการ เว้นเสียแต่ว่าตัวนับจำนวนอ้างอิงของมันจะถูกปรับค่าผ่าน atomic operations ซึ่งแน่นอนว่ามันย่อมมี overhead (ภาระการทำงาน) เพิ่มขึ้นมานิดหน่อยหากคุณไม่ได้จำเป็นต้องใช้มัลติเธรด Rust จึงแยกเตรียมมาให้ทั้งสองแบบ สิ่งที่เราต้องทำทั้งหมดก็แค่แทนที่ทุกจุดที่เรียกใช้ `Rc` ด้วย `std::sync::Arc` แค่นั้นเอง ลิสต์ของเราก็จะกลายเป็น thread-safe ทันที เรียบร้อย!

แต่นี่ก็จุดประกายคำถามที่น่าสนใจขึ้นมา: แล้วเราจะ *รู้* ได้ยังไงว่าไทป์ไหน thread-safe หรือไม่ thread-safe? เราจะเผลอทำพลาดจนระบบพังโดยไม่รู้ตัวได้ไหม?

คำตอบคือ: ไม่มีทาง! คุณไม่มีทางทำเรื่อง thread-safety พังในภาษา Rust ได้หรอก!

เหตุผลที่เป็นเช่นนั้นก็เพราะ Rust ออกแบบระบบความปลอดภัยของเธรดมาเป็นพลเมืองชั้นหนึ่ง (first-class citizen) ของภาษา โดยขับเคลื่อนผ่านสอง trait หลัก: `Send` และ `Sync`

ชนิดข้อมูลหนึ่งจะถือว่า implement *`Send`* หากมันปลอดภัยที่จะ *ย้ายความเป็นเจ้าของ (move)* ข้ามไปยังเธรดอื่น และชนิดข้อมูลหนึ่งจะถือว่า implement *`Sync`* หากมันปลอดภัยที่จะ *แชร์ (share)* ใช้งานร่วมกันระหว่างหลายเธรด นั่นหมายความว่า ถ้า `T` มีคุณสมบัติ `Sync` ตัวเรเฟอเรนซ์ `&T` ก็จะมีคุณสมบัติ `Send` นั่นเอง โดยคำว่าปลอดภัยในบริบทนี้ หมายถึง มันเป็นไปไม่ได้เลยที่จะเกิดภาวะแย่งชิงข้อมูล (*data races*) ขึ้น (อย่าสับสนกับคำที่กว้างกว่าอย่าง *race conditions* นะครับ)

พวกนี้จัดเป็น *marker traits* ซึ่งเป็นคำหรู ๆ ที่ใช้เรียก trait ที่ไม่มีเมธอดหรืออินเทอร์เฟซอะไรข้างในเลยแม้แต่อย่างเดียว ไทป์ของคุณเพียงแค่ *มี* คุณสมบัติ Send หรือ *ไม่มี* เท่านั้น มันเป็นแค่ตราประทับคุณสมบัติที่ API *อื่น ๆ* สามารถนำไปตั้งเป็นเงื่อนไข (trait bound) ได้ และถ้าไทป์ของคุณไม่ได้เป็น `Send` อย่างถูกต้อง ก็เป็นไปไม่ได้ในทางสแตติกคอมไพล์ไทม์เลยที่คุณจะส่งมันข้ามไปยังเธรดอื่นได้! สุดยอดไปเลยใช่ไหมล่ะ!

นอกจากนี้ `Send` และ `Sync` ยังเป็น auto traits ที่คอมไพเลอร์ derive ให้เองโดยอัตโนมัติตราบใดที่ฟิลด์ประกอบทั้งหมดข้างในตัวมันเป็นชนิดที่เป็น `Send` และ `Sync` คล้ายกับวิธีที่ไทป์จะ implement `Copy` ได้ก็ต่อเมื่อฟิลด์ข้างในทั้งหมดเป็น `Copy` เท่านั้น แต่ต่างกันตรงที่สำหรับ `Send` และ `Sync` คอมไพเลอร์จะใจดี implement ให้เราเองทันทีโดยไม่ต้องสั่ง `#[derive(...)]` ใด ๆ ทั้งสิ้น

ชนิดข้อมูลแทบทั้งหมดใน Rust จึงมีคุณสมบัติเป็นทั้ง `Send` และ `Sync` โดยธรรมชาติ ไทป์ส่วนใหญ่เป็น `Send` เพราะมันถือสิทธิ์ความเป็นเจ้าของข้อมูลทั้งหมดไว้คนเดียว และไทป์ส่วนใหญ่เป็น `Sync` เพราะหนทางเดียวที่จะแชร์ข้อมูลข้ามเธรดได้ก็คือการส่งผ่านทาง shared reference (`&T`) ซึ่งบังคับให้ข้อมูลข้างในกลายเป็นแบบเปลี่ยนแปลงค่าไม่ได้ (immutable) ไปโดยปริยาย!

อย่างไรก็ดี ยังมีชนิดข้อมูลพิเศษบางจำพวกที่แหกกฎเหล่านี้: นั่นคือพวกที่มีคุณสมบัติ *Interior Mutability (การแก้ไขค่าจากภายใน)* ที่ผ่านมาเราเพิ่งจะได้สัมผัสแค่ *Inherited Mutability (การแก้ไขค่าแบบสืบทอดตามคอนเทนเนอร์)* (หรือ External Mutability) กล่าวคือ ความสามารถในการแก้ไขค่าของตัวแปรจะสืบทอดมาจากตัวคอนเทนเนอร์ที่ห่อหุ้มมันอยู่ นั่นแปลว่าคุณไม่สามารถแอบไปแก้ไขค่าฟิลด์ใดฟิลด์หนึ่งในตัวแปรที่เป็น immutable เพียงเพราะแค่นึกอยากจะทำได้

แต่ไทป์พวก Interior Mutability กลับฉีกกฎนี้ทิ้ง: มันยินยอมให้คุณแก้ไขค่าของข้อมูลได้แม้จะอยู่หลัง shared reference (`&T`) ก็ตาม! โดย Interior Mutability จะถูกแบ่งออกเป็น 2 ตระกูลหลัก: กลุ่ม Cells (`Cell`, `RefCell`) ซึ่งทำงานได้เฉพาะในบริบทของเธรดเดี่ยว (single-threaded) เท่านั้น และกลุ่ม Locks (`Mutex`, `RwLock`) ซึ่งรองรับการทำงานในบริบทแบบมัลติเธรด ซึ่งแน่นอนว่ากลุ่ม Cells ย่อมมีต้นทุนที่ถูกกว่าและเร็วกว่ามากเมื่อคุณสามารถใช้งานมันได้ นอกจากนี้ยังมีกลุ่ม Atomics ซึ่งเป็นข้อมูลระดับพรีมิทีฟที่ทำงานเสมือนมีล็อกในตัว

แล้วทั้งหมดที่เล่ามานี้มันเกี่ยวอะไรกับ `Rc` และ `Arc` กันล่ะ? คำตอบก็คือ ทั้งคู่จำเป็นต้องใช้ Interior Mutability ในการปรับค่า *ตัวนับจำนวนอ้างอิง (reference count)* ของมันยังไงล่ะครับ! และที่ซับซ้อนไปกว่านั้นก็คือ ตัวนับอ้างอิงนี้ถูกแชร์ใช้งานร่วมกันในทุก ๆ อินสแตนซ์! ตัว `Rc` เลือกใช้ Cell แบบธรรมดา นั่นจึงเป็นเหตุผลว่าทำไมมันถึงไม่ thread-safe ส่วน `Arc` เลือกใช้ Atomic นั่นจึงทำให้มัน *กลายเป็น thread-safe* นั่นเอง ทว่า คุณไม่สามารถเสกให้ไทป์อะไรก็ได้กลายเป็น thread-safe ได้ด้วยเวทมนตร์เพียงเพราะจับมันยัดใส่ใน `Arc` หรอกนะ เพราะ `Arc` เองก็ทำได้เพียงแค่ derive คุณสมบัติความ thread-safe ตามชนิดข้อมูลข้างในของมันเหมือนกับไทป์อื่น ๆ เท่านั้น

จริง ๆ ผมไม่อยากลงลึกไปถึงรายละเอียดเชิงลึกของ atomic memory model หรือการ implement `Send` แบบ manual สักเท่าไหร่ เพราะยิ่งคุณดำดิ่งลงไปในเรื่อง Thread-Safety ของ Rust ลึกเท่าไหร่ สิ่งต่าง ๆ ก็จะยิ่งทวีความซับซ้อนขึ้นไปอีกมาก แต่ในฐานะผู้ใช้งานระดับสูงทั่วไป ทุกอย่างมัน *ทำงานได้อย่างราบรื่นและถูกต้องในตัวมันเอง (just works)* โดยที่คุณแทบไม่ต้องมานั่งปวดหัวกับมันเลยด้วยซ้ำ
