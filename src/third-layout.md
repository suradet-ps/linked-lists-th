# โครงสร้างในหน่วยความจำ

เอาล่ะ กลับมาเริ่มต้นวางแผนเรื่องโครงสร้างเมโมรีกันใหม่อีกครั้ง

สิ่งสำคัญที่สุดเกี่ยวกับลิสต์แบบเพอร์ซิสเทนต์ (persistent list) คือคุณสามารถหยิบเอาส่วนหาง (tail) ของลิสต์ออกมาจัดการหรือใช้งานร่วมกันได้แทบจะฟรี ๆ (ไม่มีต้นทุนเพิ่ม):

ตัวอย่างเช่น นี่คือรูปแบบการใช้งาน (workload) ทั่วไปที่เรามักจะพบเห็นได้เสมอในลิสต์แบบเพอร์ซิสเทนต์:

```text
list1 = A -> B -> C -> D
list2 = tail(list1) = B -> C -> D
list3 = push(list2, X) = X -> B -> C -> D
```

แต่ปลายทางเราต้องการให้แผนผังในหน่วยความจำมีหน้าตาเป็นแบบนี้:

```text
list1 -> A ---+
              |
              v
list2 ------> B -> C -> D
              ^
              |
list3 -> X ---+
```

โครงสร้างแบบนี้ไม่มีทางทำได้ด้วย `Box` เด็ดขาด เพราะความเป็นเจ้าของใน `B` มีลักษณะเป็น*การเป็นเจ้าของร่วมกัน* (shared ownership) แล้วตกลงใครควรเป็นคนคืนหน่วยความจำของมันกันล่ะ? ถ้าผมสั่ง drop `list2` มันควรจะตามไป deallocate คืนเมโมรีของ `B` ด้วยไหม? ถ้าใช้ Box ปกติเราย่อมคาดหวังให้มันทำแบบนั้นแน่นอน!

ภาษาเชิงฟังก์ชัน (Functional languages) &mdash; หรือจริง ๆ ก็แทบจะทุกภาษาบนโลกนี้ &mdash; รอดพ้นปัญหานี้ไปได้อย่างสบายใจเฉิบด้วยการพึ่งพา *Garbage Collection (ระบบเก็บขยะ)* ด้วยมนตร์วิเศษของระบบ GC ตัว `B` จะถูกคืนหน่วยความจำก็ต่อเมื่อไม่มีใครในโปรแกรมกำลังชี้ไปหามันอีกแล้วเท่านั้น ไชโย!

Rust ไม่มีระบบ Garbage Collector เหมือนอย่างที่ภาษาเหล่านั้นมี ภาษาเหล่านั้นใช้ GC แบบ *Tracing* ซึ่งจะคอยไล่คุ้ยขุดตรวจเมโมรีทั้งหมดที่ค้างอยู่ในระบบระหว่างรันไทม์ แล้วชี้เป้าอัตโนมัติว่าอะไรคือขยะที่ทิ้งได้ แต่สำหรับ Rust ในตอนนี้ สิ่งที่เรามีให้ใช้มีเพียงแค่ *ระบบนับจำนวนอ้างอิง (Reference Counting)* เท่านั้น เราสามารถมองว่า Reference Counting เป็นระบบ GC แบบเรียบง่ายที่สุด สำหรับเวิร์กโหลดหลาย ๆ แบบ มันอาจจะมี throughput (ประสิทธิภาพการประมวลผล) ต่ำกว่าตัวเก็บขยะแบบ tracing อย่างเห็นได้ชัด และมันจะพังไม่เป็นท่าทันทีถ้าคุณเผลอสร้างการอ้างอิงวนรอบเป็นวงกลม (cycles) ขึ้นมา... แต่ก็นะ! นี่คือทั้งหมดที่เรามีให้ใช้แล้วนี่นา! ยังดีที่สำหรับเคสการใช้งานของเรา เราจะไม่มีวันเจอการวนรอบเป็นไซเคิลแน่นอน (ถ้าว่างพอก็ลองพิสูจน์ดูด้วยตัวเองได้เลยครับ &mdash; แต่ผมคนหนึ่งล่ะที่ไม่คิดจะทำแน่ ๆ)

แล้วเราจะใช้ Garbage Collection แบบ Reference Counting ได้ยังไงล่ะ? คำตอบคือ `Rc`! เจ้า `Rc` นั้นมีพฤติกรรมคล้ายกับ `Box` มาก แต่เราสามารถโคลนทำซ้ำ (duplicate) ตัวมันได้ และพื้นที่หน่วยความจำของมันจะ*ถูกคืนค่าก็ต่อเมื่อ* `Rc` *ทุกตัว* ที่แตกแขนงออกมาจากมันถูก drop ทิ้งไปจนหมดเกลี้ยงแล้วเท่านั้น ทว่า ความยืดหยุ่นตรงนี้ต้องแลกมาด้วยต้นทุนที่แสนสาหัส: เราสามารถทำได้เพียงแค่ขอยืมเรเฟอเรนซ์แบบแชร์ (shared reference) ไปยังข้อมูลข้างในของมันเท่านั้น นั่นหมายความว่าเราไม่สามารถดึงข้อมูลจริง ๆ ออกมาจากลิสต์ของเราได้เลย และเราก็ไม่สามารถแก้ไขค่า (mutate) อะไรในนั้นได้อีกด้วย

แล้วหน้าตาโครงสร้างของเราควรจะเป็นอย่างไรดี? ก่อนหน้านี้เราเคยเขียนไว้ว่า:

```rust ,ignore
pub struct List<T> {
    head: Link<T>,
}

type Link<T> = Option<Box<Node<T>>>;

struct Node<T> {
    elem: T,
    next: Link<T>,
}
```

เราแค่เปลี่ยนจาก `Box` เป็น `Rc` ตรง ๆ เลยได้ไหม?

```rust ,ignore
// in third.rs

pub struct List<T> {
    head: Link<T>,
}

type Link<T> = Option<Rc<Node<T>>>;

struct Node<T> {
    elem: T,
    next: Link<T>,
}
```

```text
cargo build

 --> src/third.rs:5:23
  |

  |                       ^^ not found in this scope

  |

```

โอ้โห แสบทรวงจริง ๆ (sick burn) ต่างจากสิ่งที่เราเคยใช้ในลิสต์ก่อนหน้านี้ เจ้า `Rc` ดันง่อยเปลี้ยเสียขาเสียจนขนาดไม่ได้ถูกนำเข้า (implicitly imported) มาไว้ใน prelude ของ Rust ทุกโปรแกรมให้โดยอัตโนมัติด้วยซ้ำ *อะไรจะน่าสมเพชขนาดนั้น*

```rust ,ignore
use std::rc::Rc;
```

ดูเข้าท่าแฮะ! Rust นี่มันยังคงเขียนง่าย*เสียจริง ๆ* ให้ตายสิ ผมพนันได้เลยว่าเราแค่สั่ง Find and Replace เปลี่ยนคำว่า `Box` เป็น `Rc` ให้หมด แล้วก็นอนเอกเขนกปิดจ็อบงานวันนี้ได้เลย!
