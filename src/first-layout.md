# โครงสร้างข้อมูลพื้นฐานในหน่วยความจำ

เอาล่ะ แล้วลิงก์ลิสต์คืออะไร? ง่าย ๆ คือมันคือชิ้นส่วนข้อมูลหลายชิ้นบนฮีป
(เงียบก่อน คนเคอร์เนลทั้งหลาย!) ที่ชี้หากันเป็นลำดับ ลิงก์ลิสต์เป็นสิ่งที่
โปรแกรมเมอร์เชิงโพรซีเดอรัลไม่ควรยุ่งด้วยแม้แต่ไม้ยาว 10 ฟุต และเป็นสิ่งที่
โปรแกรมเมอร์เชิงฟังก์ชันใช้กับทุกอย่าง ดูจะยุติธรรมดี ถ้าเราจะขอคำนิยามของ
ลิงก์ลิสต์จากโปรแกรมเมอร์เชิงฟังก์ชัน พวกเขาอาจให้คำนิยามประมาณนี้:

```haskell
List a = Empty | Elem a (List a)
```

ซึ่งอ่านได้ประมาณว่า "ลิสต์คือ Empty หรือ Element ที่ตามด้วยลิสต์อีกตัว"
นี่คือคำนิยามแบบรีเคอร์ซีฟที่แสดงเป็น*ซัมไทป์ (sum type)* ซึ่งเป็นชื่อหรู ๆ ของ
"ชนิดที่สามารถมีค่าแตกต่างกันซึ่งอาจเป็นคนละชนิดกัน" Rust เรียกซัมไทป์ว่า `enum`!
ถ้าคุณมาจากภาษาตระกูล C นี่คือ enum ที่คุณรู้จักและรัก แต่เวอร์ชันโอเวอร์ไดรฟ์
งั้นมาแปลงคำนิยามเชิงฟังก์ชันนี้เป็น Rust กันเถอะ!

ตอนนี้เราจะเลี่ยงเจเนอริกไปก่อนเพื่อให้ง่าย เราจะรองรับแค่การเก็บ
จำนวนเต็ม 32 บิตแบบมีเครื่องหมาย:

```rust ,ignore
// in first.rs

// pub says we want people outside this module to be able to use List
pub enum List {
    Empty,
    Elem(i32, List),
}
```

*ฟี๊วว* ผมล้าไปหมดแล้ว มาคอมไพล์กันเลยดีกว่า:

```text
> cargo build

error[E0072]: recursive type `first::List` has infinite size
 --> src/first.rs:4:1
  |
4 | pub enum List {
  | ^^^^^^^^^^^^^ recursive type has infinite size
5 |     Empty,
6 |     Elem(i32, List),
  |               ---- recursive without indirection
  |
  = help: insert indirection (e.g., a `Box`, `Rc`, or `&`) at some point to make `first::List` representable
```

เอาเถอะ ผมไม่รู้ว่าคุณเป็นยังไง แต่ผมรู้สึกว่าถูกคอมมูนิตี้การเขียนโปรแกรม
เชิงฟังก์ชันหักหลังแน่ ๆ

ถ้าเราลองดูข้อความข้อผิดพลาดจริง ๆ (หลังจากที่เราผ่านความรู้สึกเรื่องการหักหลังไป)
เราจะเห็นว่า rustc บอกเราอย่างชัดเจนว่าต้องแก้ยังไง:

> insert indirection (e.g., a `Box`, `Rc`, or `&`) at some point to make `first::List` representable

โอเค `box` มันคืออะไร? ไปค้น `rust box` กัน...

> [std::boxed::Box - Rust](https://doc.rust-lang.org/std/boxed/struct.Box.html)

ดูนี่...

> `pub struct Box<T>(_);`
>
> A pointer type for heap allocation.
> See the [module-level documentation](https://doc.rust-lang.org/std/boxed/) for more.

*คลิกลิงก์*

> `Box<T>`, ที่เรียกกันติดปากว่า 'box' ให้รูปแบบการจัดสรรบนฮีปที่ง่ายที่สุดใน Rust
> Box ให้ความเป็นเจ้าของการจัดสรรนี้ และจะ drop เนื้อหาของมันเมื่อหลุดจากสโคป
>
> ตัวอย่าง
>
> การสร้าง box:
>
> `let x = Box::new(5);`
>
> การสร้างโครงสร้างข้อมูลแบบรีเคอร์ซีฟ:
>
```rust
#[derive(Debug)]
enum List<T> {
    Cons(T, Box<List<T>>),
    Nil,
}
```
>
```rust ,ignore
fn main() {
    let list: List<i32> = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
    println!("{:?}", list);
}
```
>
> โค้ดนี้จะพิมพ์ `Cons(1, Box(Cons(2, Box(Nil))))`
>
> โครงสร้างแบบรีเคอร์ซีฟต้องถูกครอบด้วย Box เพราะถ้าคำนิยามของ Cons เป็นแบบนี้:
>
> `Cons(T, List<T>),`
>
> มันจะใช้ไม่ได้ นั่นเป็นเพราะขนาดของ List ขึ้นอยู่กับจำนวนองค์ประกอบในลิสต์
> ดังนั้นเราจึงไม่รู้ว่าต้องจัดสรรหน่วยความจำเท่าไหร่สำหรับ Cons การนำ Box เข้ามา
> ซึ่งมีขนาดที่แน่นอน ทำให้เรารู้ว่า Cons ต้องมีขนาดเท่าไหร่

ว้าว เอ่อ นั่นอาจเป็นเอกสารที่เกี่ยวข้องและมีประโยชน์ที่สุดเท่าที่ผมเคยเห็นมา
แบบว่าสิ่งแรกในเอกสารคือ*สิ่งที่เรากำลังพยายามเขียน, ทำไมมันถึงใช้ไม่ได้,
และวิธีแก้ไข*เลย

ให้ตาย เอกสารนี่สุดยอด

โอเค มาทำแบบนั้นกัน:

```rust ,ignore
pub enum List {
    Empty,
    Elem(i32, Box<List>),
}
```

```text
> cargo build

   Finished dev [unoptimized + debuginfo] target(s) in 0.22s
```

เฮ้ มันบิลด์ผ่าน!

...แต่นี่จริง ๆ แล้วเป็นคำนิยามของ List ที่โง่สุด ๆ ด้วยเหตุผลหลายประการ

ลองพิจารณาลิสต์ที่มีสององค์ประกอบ:

```text
[] = Stack
() = Heap

[Elem A, ptr] -> (Elem B, ptr) -> (Empty, *junk*)
```

มีปัญหาหลักสองข้อ:

* เรากำลังจัดสรรโหนดที่แค่บอกว่า "ฉันไม่ได้เป็นโหนดจริง ๆ"
* โหนดหนึ่งของเราไม่ได้ถูกจัดสรรบนฮีปเลย

เมื่อมองผิวเผิน สองข้อนี้ดูเหมือนจะหักล้างกัน เราจัดสรรโหนดเพิ่มขึ้นหนึ่งตัวบนฮีป
แต่โหนดหนึ่งของเราไม่จำเป็นต้องถูกจัดสรรบนฮีปเลย อย่างไรก็ตาม ลองพิจารณา
โครงสร้างที่เป็นไปได้ของลิสต์เราดังนี้:

```text
[ptr] -> (Elem A, ptr) -> (Elem B, *null*)
```

ในโครงสร้างนี้ เราจัดสรรโหนดของเราบนฮีปอย่างไม่มีเงื่อนไข
ความแตกต่างสำคัญคือการไม่มี *junk* จากโครงสร้างแรกของเรา แล้ว junk นี้คืออะไร?
เพื่อเข้าใจมัน เราต้องดูว่า enum ถูกวางในหน่วยความจำอย่างไร

โดยทั่วไป ถ้าเรามี enum แบบ:

```rust ,ignore
enum Foo {
    D1(T1),
    D2(T2),
    ...
    Dn(Tn),
}
```

Foo จะต้องเก็บจำนวนเต็มบางตัวเพื่อระบุว่า enum แทน*วาเรียนต์*ใดอยู่ (`D1`, `D2`, .. `Dn`)
นี่คือ*แท็ก*ของ enum มันยังต้องมีพื้นที่เพียงพอสำหรับเก็บ*ใหญ่ที่สุด*ของ `T1`, `T2`, .. `Tn`
(บวกพื้นที่พิเศษบางส่วนเพื่อให้ตรงตามข้อกำหนดการจัดแนว)

ข้อสรุปใหญ่ตรงนี้คือ แม้ว่า `Empty` จะเป็นข้อมูลแค่หนึ่งบิต แต่มันจำเป็นต้องใช้พื้นที่
พอ ๆ กับตัวชี้และองค์ประกอบ เพราะมันต้องพร้อมที่จะกลายเป็น `Elem` ได้ตลอดเวลา
ดังนั้นโครงสร้างแรกจึงจัดสรรองค์ประกอบพิเศษหนึ่งตัวที่เต็มไปด้วย junk
กินพื้นที่มากกว่าโครงสร้างที่สองเล็กน้อย

ที่ว่าโหนดหนึ่งของเราไม่ถูกจัดสรรเลย ก็*แย่กว่า*การจัดสรรตลอดเวลาถึงแม้จะดูน่าแปลกใจ
นั่นเป็นเพราะมันทำให้เรามีโครงสร้างโหนดที่*ไม่สม่ำเสมอ* สิ่งนี้ไม่ได้ส่งผลที่เห็นได้ชัด
ต่อการ push และ pop โหนด แต่มันส่งผลต่อการแยกและรวมลิสต์

ลองพิจารณาการแยกลิสต์ในทั้งสองโครงสร้าง:

```text
layout 1:

[Elem A, ptr] -> (Elem B, ptr) -> (Elem C, ptr) -> (Empty *junk*)

split off C:

[Elem A, ptr] -> (Elem B, ptr) -> (Empty *junk*)
[Elem C, ptr] -> (Empty *junk*)
```

```text
layout 2:

[ptr] -> (Elem A, ptr) -> (Elem B, ptr) -> (Elem C, *null*)

split off C:

[ptr] -> (Elem A, ptr) -> (Elem B, *null*)
[ptr] -> (Elem C, *null*)
```

การแยกของโครงสร้างที่ 2 เกี่ยวข้องกับการคัดลอกตัวชี้ของ B ลงบนสแต็ก
และทำให้ค่าเก่าเป็น null เท่านั้น โครงสร้างที่ 1 ท้ายที่สุดทำแบบเดียวกัน
แต่ยังต้องคัดลอก C จากฮีปลงบนสแต็กด้วย การรวมคือกระบวนการเดียวกันแบบย้อนกลับ

หนึ่งในสิ่งดี ๆ ไม่กี่อย่างของลิงก์ลิสต์คือคุณสามารถสร้างองค์ประกอบในโหนดเอง
แล้วสับมันไปมาระหว่างลิสต์ได้อย่างอิสระโดยไม่ต้องขยับมันเลย
คุณแค่เลื่อนตัวชี้ แล้วของก็ถูก "ย้าย" โครงสร้างที่ 1 ทำลายคุณสมบัตินี้

เอาล่ะ ผมค่อนข้างมั่นใจว่าโครงสร้างที่ 1 แย่ แล้วเราจะเขียน List ใหม่ยังไงล่ะ?
เราอาจทำประมาณ:

```rust ,ignore
pub enum List {
    Empty,
    ElemThenEmpty(i32),
    ElemThenNotEmpty(i32, Box<List>),
}
```

หวังว่าคุณจะมองว่านี่เป็นไอเดียที่แย่กว่าด้วยซ้ำ โดยเฉพาะอย่างยิ่ง มันทำให้ตรรกะของเรา
ซับซ้อนขึ้นมาก เพราะตอนนี้มีสถานะที่ใช้ไม่ได้โดยสิ้นเชิง:
`ElemThenNotEmpty(0, Box(Empty))` มันยัง*คง*ประสบปัญหาเรื่องการจัดสรรองค์ประกอบ
ที่ไม่สม่ำเสมอ

อย่างไรก็ตาม มันมี*หนึ่ง*คุณสมบัติที่น่าสนใจ: มันหลีกเลี่ยงการจัดสรรกรณี Empty ได้อย่างสิ้นเชิง
ลดจำนวนการจัดสรรบนฮีปรวมลงได้หนึ่งครั้ง แต่โชคร้าย ในการทำแบบนั้นมันกลับสิ้นเปลือง
*พื้นที่มากกว่าเดิมอีก*! เพราะโครงสร้างก่อนหน้าใช้ประโยชน์จาก
*การเพิ่มประสิทธิภาพด้วยพอยน์เตอร์ null (null pointer optimization)*

เราเห็นก่อนหน้านี้ว่า enum ทุกตัวต้องเก็บ*แท็ก*เพื่อระบุว่าบิตของมันแทนวาเรียนต์ใด
อย่างไรก็ตาม ถ้าเรามี enum ชนิดพิเศษ:

```rust,ignore
enum Foo {
    A,
    B(ContainsANonNullPtr),
}
```

การเพิ่มประสิทธิภาพด้วยพอยน์เตอร์ null จะทำงาน ซึ่งจะ*กำจัดพื้นที่ที่ต้องใช้สำหรับแท็ก*
ถ้าวาเรียนต์เป็น A ทั้ง enum จะถูกตั้งให้เป็น `0` ทั้งหมด มิฉะนั้น วาเรียนต์คือ B
สิ่งนี้ใช้ได้เพราะ B ไม่สามารถเป็น `0` ทั้งหมดได้ เนื่องจากมันมีตัวชี้ที่ไม่เป็นศูนย์
เจ๋ง!

ลองคิดดูสิว่ามี enum และชนิดอื่น ๆ อีกมั้ยที่สามารถทำการเพิ่มประสิทธิภาพแบบนี้ได้?
จริง ๆ แล้วมันมีเยอะมาก! นี่คือเหตุผลที่ Rust ปล่อยให้การจัดวาง enum ไม่ระบุเลย
ยังมีการเพิ่มประสิทธิภาพการจัดวาง enum ที่ซับซ้อนกว่านี้อีกหลายแบบที่ Rust จะทำให้เรา
แต่แบบพอยน์เตอร์ null คือแบบที่สำคัญที่สุดแน่นอน!
มันหมายความว่า `&`, `&mut`, `Box`, `Rc`, `Arc`, `Vec`, และ
ชนิดสำคัญอื่น ๆ อีกหลายชนิดใน Rust ไม่มีโอเวอร์เฮดเมื่ออยู่ใน `Option`!
(เราจะได้เจอพวกนี้ส่วนใหญ่ตามเวลาอันควร)

แล้วเราจะหลีกเลี่ยง junk พิเศษ จัดสรรอย่างสม่ำเสมอ *และ*ได้การเพิ่มประสิทธิภาพด้วย
พอยน์เตอร์ null สุดหวานนั้นยังไง? เราต้องแยกแนวคิดของการมีองค์ประกอบ
ออกจากการจัดสรรลิสต์อีกตัวให้ชัดเจนขึ้น ในการทำแบบนี้ เราต้องคิดแบบ C มากขึ้น:
struct!

ในขณะที่ enum ให้เราประกาศชนิดที่สามารถมีค่าได้*หนึ่งใน*หลายค่า struct ให้เราประกาศ
ชนิดที่มี*หลายค่า*พร้อมกันได้ ลองแยก List ของเราออกเป็นสองชนิด: List และ Node

เหมือนเดิม List คือ Empty หรือมีองค์ประกอบที่ตามด้วย List อีกตัว
โดยการแทนกรณี "มีองค์ประกอบที่ตามด้วย List อีกตัว" ด้วยชนิดที่แยกออกไปโดยสิ้นเชิง
เราสามารถย้าย Box ไปอยู่ในตำแหน่งที่เหมาะสมกว่าได้:

```rust ,ignore
struct Node {
    elem: i32,
    next: List,
}

pub enum List {
    Empty,
    More(Box<Node>),
}
```

ลองตรวจสอบลำดับความสำคัญของเราดู:

* หางของลิสต์ไม่จัดสรร junk พิเศษ: ผ่าน!
* `enum` อยู่ในรูปแบบที่ได้รับการเพิ่มประสิทธิภาพด้วยพอยน์เตอร์ null แบบเต็มรูปแบบ: ผ่าน!
* องค์ประกอบทั้งหมดถูกจัดสรรอย่างสม่ำเสมอ: ผ่าน!

เอาล่ะ! จริง ๆ แล้วเราเพิ่งสร้างโครงสร้างที่ตรงกับที่เราใช้แสดงว่าโครงสร้างแรกของเรา
(ตามคำแนะนำของเอกสาร Rust อย่างเป็นทางการ) มีปัญหา

```text
> cargo build

warning: private type `first::Node` in public interface (error E0446)
 --> src/first.rs:8:10
  |
8 |     More(Box<Node>),
  |          ^^^^^^^^^
  |
  = note: #[warn(private_in_public)] on by default
  = warning: this was previously accepted by the compiler but
    is being phased out; it will become a hard error in a future release!
```

:(

Rust โมโหเราแล้ว เราเขียนว่า `List` เป็น public (เพราะเราอยากให้คนอื่นใช้งานมันได้)
แต่ไม่ได้เขียน `Node` เป็น public ปัญหาคือ อินเทอร์นัลของ `enum` นั้นเป็น public หมด
และเราไม่ได้รับอนุญาตให้พูดถึงชนิด private ต่อสาธารณะ เราสามารถทำให้ `Node` ทั้งหมด
เป็น public ได้ แต่โดยทั่วไปใน Rust เราชอบให้รายละเอียดการนำไปปฏิบัติเป็น private
มาทำให้ `List` เป็น struct เพื่อที่เราจะได้ซ่อนรายละเอียดการนำไปปฏิบัติ:

```rust ,ignore
pub struct List {
    head: Link,
}

enum Link {
    Empty,
    More(Box<Node>),
}

struct Node {
    elem: i32,
    next: Link,
}
```

เพราะ `List` เป็น struct ที่มีฟิลด์เดียว ขนาดของมันจึงเท่ากับฟิลด์นั้น

ไร้ประโยชน์โดยสิ้นเชิง: เราไม่เคยใช้ `head` และไม่มีใครที่ใช้ไลบรารีของเราจะใช้ได้เช่นกัน
