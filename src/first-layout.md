# โครงสร้างข้อมูลพื้นฐานในหน่วยความจำ

เอาล่ะ แล้วลิงก์ลิสต์คืออะไรกันแน่? สรุปสั้น ๆ คือมันก็แค่ก้อนข้อมูลหลาย ๆ ก้อนที่กระจัดกระจายอยู่บนฮีป (ใจเย็นก่อน ชาวเคอร์เนลทั้งหลาย!) แล้วชี้หากันเป็นลูกโซ่ตามลำดับ ลิงก์ลิสต์คือสิ่งที่โปรแกรมเมอร์สาย procedural อย่าได้คิดจะแตะต้องเด็ดขาด แต่กลับเป็นสิ่งที่โปรแกรมเมอร์สาย functional หยิบมาใช้กับทุกสิ่งทุกอย่างในชีวิต ถ้าอย่างนั้น ก็น่าจะแฟร์ดีหากเราลองไปถามนิยามของลิงก์ลิสต์จากชาว functional ดู ซึ่งพวกเขาก็น่าจะให้นิยามหน้าตาประมาณนี้กลับมา:

```haskell
List a = Empty | Elem a (List a)
```

ซึ่งอ่านคร่าว ๆ ได้ว่า "List อาจจะเป็น Empty (ลิสต์ว่าง) หรือไม่ก็เป็น Element (ข้อมูลหนึ่งตัว) ที่ตามด้วย List อีกก้อนหนึ่ง" นี่คือนิยามแบบเรียกซ้ำ (recursive definition) ที่เขียนอยู่ในรูปของ *ซัมไทป์ (sum type)* ซึ่งเป็นชื่อหรู ๆ ของ "ชนิดข้อมูลที่สามารถเก็บค่าได้หลายรูปแบบ และแต่ละรูปแบบอาจเป็นคนละชนิดกันได้" ในภาษา Rust เราเรียกซัมไทป์ว่า `enum`! ถ้าคุณมาจากภาษาตระกูล C นี่คือ enum ตัวเดิมที่คุณคุ้นเคยและชื่นชอบ แต่ถูกอัปเกรดพลังมาแบบโอเวอร์ไดรฟ์ งั้นเรามาลองแปลงนิยามเชิงฟังก์ชันนี้ให้อยู่ในรูปภาษา Rust กันเถอะ!

เพื่อไม่ให้เรื่องมันซับซ้อนเกินไป ตอนนี้เราจะยังไม่ใช้ generic โดยจะรองรับแค่การเก็บจำนวนเต็ม 32-bit แบบมีเครื่องหมาย (i32) ไปก่อน:

```rust ,ignore
// in first.rs

// pub says we want people outside this module to be able to use List
pub enum List {
    Empty,
    Elem(i32, List),
}
```

*เฮ้อ* แค่นี้ก็เล่นเอาเหนื่อยละ มาลองคอมไพล์โค้ดนี้กันเลยดีกว่า:

```text
> cargo build

error[E0072]: recursive type `first::List` has infinite size
 --> src/first.rs:4:1
  |
4 | pub enum List {
  | ^^^^^^^^^^^^^ recursive type has infinite size
5 |     Empty,
6 |     Elem(i32, List),
  |               ---- recursive without indirection
  |
  = help: insert indirection (e.g., a `Box`, `Rc`, or `&`) at some point to make `first::List` representable
```

ก็นั่นแหละ... ผมไม่รู้ว่าคุณรู้สึกยังไงนะ แต่ผมคนหนึ่งล่ะที่รู้สึกเหมือนโดนคอมมูนิตี้ชาว Functional Programming หักหลังเข้าเต็มเปา

แต่พอเราลองกวาดสายตาดูข้อความ error จริง ๆ (หลังจากที่ทำใจเรื่องโดนหักหลังได้แล้ว) เราจะพบว่าจริง ๆ แล้ว rustc บอกวิธีแก้ปัญหานี้ให้เราอย่างชัดเจนแจ่มแจ้งเลยทีเดียว:

> insert indirection (e.g., a `Box`, `Rc`, or `&`) at some point to make `first::List` representable

โอเค `box` เหรอ? มันคืออะไรกันล่ะเนี่ย? ลองเปิด Google ค้นหาคำว่า `rust box` ดูหน่อยซิ...

> [std::boxed::Box - Rust](https://doc.rust-lang.org/std/boxed/struct.Box.html)

มาดูซิว่ามันเขียนว่าอะไรบ้าง...

> `pub struct Box<T>(_);`
>
> A pointer type for heap allocation.
> See the [module-level documentation](https://doc.rust-lang.org/std/boxed/) for more.

*กดคลิกลิงก์เข้าไปดู*

> `Box<T>`, casually referred to as a 'box', provides the simplest form of heap allocation in Rust. Boxes provide ownership for this allocation, and drop their contents when they go out of scope.
>
> Examples
>
> Creating a box:
>
> `let x = Box::new(5);`
>
> Creating a recursive data structure:
>
```rust
#[derive(Debug)]
enum List<T> {
    Cons(T, Box<List<T>>),
    Nil,
}
```
>
```rust ,ignore
fn main() {
    let list: List<i32> = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
    println!("{:?}", list);
}
```
>
> This will print `Cons(1, Box(Cons(2, Box(Nil))))`.
>
> Recursive structures must be boxed, because if the definition of Cons looked like this:
>
> `Cons(T, List<T>),`
>
> It wouldn't work. This is because the size of a List depends on how many elements are in the list, and so we don't know how much memory to allocate for a Cons. By introducing a Box, which has a defined size, we know how big Cons needs to be.

โอ้โห... นี่อาจจะเป็นเอกสารคู่มือที่ตรงประเด็นและช่วยชีวิตได้มากที่สุดเท่าที่ผมเคยเห็นมาในชีวิตเลยมั้งเนี่ย! แบบว่าเปิดมาประโยคแรกก็คือ *สิ่งที่เรากำลังพยายามจะเขียนเป๊ะ ๆ บอกเสร็จสรรพว่าทำไมมันถึงพัง และต้องแก้ยังไง*

ให้ตายสิ เอกสาร Rust นี่มันเจ๋งจริง ๆ

เอาล่ะ งั้นเรามาแก้ตามนั้นกัน:

```rust ,ignore
pub enum List {
    Empty,
    Elem(i32, Box<List>),
}
```

```text
> cargo build

   Finished dev [unoptimized + debuginfo] target(s) in 0.22s
```

เฮ้ย มันคอมไพล์ผ่านเฉย!

...แต่นี่จริง ๆ แล้วเป็นนิยามของ List ที่งี่เง่าเอามาก ๆ ด้วยเหตุผลหลายประการ

ลองจินตนาการถึงลิสต์ที่มีข้อมูลอยู่สองตัวดู:

```text
[] = Stack
() = Heap

[Elem A, ptr] -> (Elem B, ptr) -> (Empty, *junk*)
```

ปัญหาใหญ่มีอยู่สองข้อ:

* เราต้องเสียเวลาจัดสรรหน่วยความจำบนฮีปให้กับโหนดที่เกิดมาแค่เพื่อจะบอกว่า "จริง ๆ แล้วฉันไม่ได้เป็นโหนดนะ"
* โหนดตัวแรกของเราไม่ได้อยู่บนฮีปเลยสักนิด แต่อยู่บนสแต็ก

เมื่อมองเผิน ๆ สองปัญหานี้ดูเหมือนจะเจ๊ากันไปเอง เพราะเราต้องขอฮีปเพิ่มมาหนึ่งโหนด แต่โหนดแรกของเรากลับไม่ต้องขอฮีปเลย ทว่า ลองพิจารณาเลย์เอาต์ที่เป็นไปได้อีกแบบหนึ่งของลิสต์เราดู:

```text
[ptr] -> (Elem A, ptr) -> (Elem B, *null*)
```

ในเลย์เอาต์แบบที่สองนี้ โหนดทุกตัวของเราจะถูกจัดสรรอยู่บนฮีปเหมือนกันทั้งหมดอย่างสม่ำเสมอ ข้อแตกต่างสำคัญคือการไม่มี *ขยะ (junk)* หลงเหลืออยู่เหมือนในเลย์เอาต์แรก แล้วไอ้ขยะที่ว่านี้มันคืออะไรกันแน่? เพื่อที่จะเข้าใจเรื่องนี้ เราจำเป็นต้องมาดูวิธีที่ enum จัดวางโครงสร้างในหน่วยความจำกันเสียก่อน

โดยทั่วไปแล้ว ถ้าเรามี enum หน้าตาแบบนี้:

```rust ,ignore
enum Foo {
    D1(T1),
    D2(T2),
    ...
    Dn(Tn),
}
```

ตัวแปร `Foo` จะต้องเก็บเลขจำนวนเต็มไว้ตัวหนึ่งเพื่อคอยบอกว่าตอนนี้มันกำลังแทน *วาเรียนต์ (variant)* ตัวไหนอยู่ (`D1`, `D2`, .. `Dn`) ซึ่งเลขตัวนี้เราเรียกว่า *แท็ก (tag)* ของ enum นอกจากนี้ มันยังต้องมีพื้นที่ว่างมากพอที่จะบรรจุวาเรียนต์ตัวที่ *ใหญ่ที่สุด* ในบรรดา `T1`, `T2`, .. `Tn` ได้ (บวกกับพื้นที่ว่างพิเศษอีกนิดหน่อยเพื่อให้ตรงตามข้อกำหนดเรื่อง memory alignment)

ประเด็นสำคัญที่สุดตรงนี้ก็คือ แม้ว่า `Empty` จะต้องการข้อมูลเพียงแค่บิตเดียว แต่มันกลับถูกบังคับให้ต้องกินเนื้อที่เท่ากับตัวชี้หนึ่งตัวบวกกับข้อมูลหนึ่งตัวเสมอ เพราะมันต้องพร้อมที่จะแปลงร่างกลายเป็น `Elem` ได้ตลอดเวลา ด้วยเหตุนี้ เลย์เอาต์แรกจึงต้องจัดสรรก้อนข้อมูลส่วนเกินบนฮีปที่เต็มไปด้วยขยะว่างเปล่า ซึ่งกินพื้นที่มากกว่าเลย์เอาต์แบบที่สองอยู่เล็กน้อย

และการที่โหนดตัวแรกของเราไม่ได้อยู่บนฮีปเลยนั้น พอมองลึกลงไปแล้วกลับส่งผล *แย่กว่า* การจับมันไปอยู่บนฮีปทั้งหมดเสียอีก ทั้งนี้เพราะมันทำให้โครงสร้างโหนดของเรา *ไม่สม่ำเสมอ (non-uniform)* แม้สิ่งนี้จะไม่ได้ส่งผลกระทบอะไรมากนักต่อการ push หรือ pop ข้อมูล แต่จะมีผลอย่างชัดเจนเวลาที่เราต้องการแยก (split) หรือรวม (merge) ลิสต์เข้าด้วยกัน

ลองมาดูการแยกลิสต์ของทั้งสองเลย์เอาต์เปรียบเทียบกัน:

```text
layout 1:

[Elem A, ptr] -> (Elem B, ptr) -> (Elem C, ptr) -> (Empty *junk*)

split off C:

[Elem A, ptr] -> (Elem B, ptr) -> (Empty *junk*)
[Elem C, ptr] -> (Empty *junk*)
```

```text
layout 2:

[ptr] -> (Elem A, ptr) -> (Elem B, ptr) -> (Elem C, *null*)

split off C:

[ptr] -> (Elem A, ptr) -> (Elem B, *null*)
[ptr] -> (Elem C, *null*)
```

การแยกลิสต์ในเลย์เอาต์แบบที่ 2 ทำเพียงแค่ก็อปปี้ตัวชี้ของ B ขึ้นมาไว้บนสแต็ก แล้วเซตค่าเดิมในโหนดให้กลายเป็น null เท่านั้น ส่วนเลย์เอาต์แบบที่ 1 ในท้ายที่สุดก็ต้องทำแบบเดียวกัน แต่ยังต้องเหนื่อยก็อปปี้ข้อมูลของ C จากฮีปขึ้นมาไว้บนสแต็กเพิ่มอีกด้วย และการรวมลิสต์กลับเข้ามาก็คือกระบวนการเดิมในทิศทางย้อนกลับ

หนึ่งในข้อดีเพียงไม่กี่อย่างของลิงก์ลิสต์ก็คือ คุณสามารถสร้างข้อมูลขึ้นมาในตัวโหนด แล้วสลับสับเปลี่ยนโยกย้ายมันไปมาระหว่างลิสต์ต่าง ๆ ได้อย่างอิสระโดยไม่ต้องขยับย้ายก้อนข้อมูลจริงเลยแม้แต่น้อย คุณแค่แก้ตำแหน่งตัวชี้ ของก็ถือว่า "ถูกย้าย" เรียบร้อยแล้ว แต่เลย์เอาต์แบบที่ 1 ดันมาพังคุณสมบัติข้อนี้ทิ้งไปอย่างน่าเสียดาย

เอาล่ะ ผมคิดว่าเราคงเห็นตรงกันแล้วว่าเลย์เอาต์แบบที่ 1 มันห่วย แล้วเราจะเขียน `List` ใหม่ยังไงดีล่ะ? เราอาจจะลองทำอะไรแบบนี้ดู:

```rust ,ignore
pub enum List {
    Empty,
    ElemThenEmpty(i32),
    ElemThenNotEmpty(i32, Box<List>),
}
```

ผมหวังว่าคุณจะรู้สึกว่าไอเดียนี้ฟังดูยิ่งแย่หนักกว่าเดิมอีกนะ เพราะอย่างแรกเลยคือมันทำให้ลอจิกของเราซับซ้อนขึ้นมหาศาล แถมยังมีสถานะที่เป็นไปไม่ได้โผล่ขึ้นมาด้วย เช่น `ElemThenNotEmpty(0, Box(Empty))` มิหนำซ้ำมันก็ *ยังคง* ประสบปัญหาเรื่องการจัดสรรโหนดที่ไม่สม่ำเสมออยู่ดี

อย่างไรก็ตาม โค้ดนี้มีคุณสมบัติที่น่าสนใจอยู่ *ข้อหนึ่ง*: คือมันไม่ต้องจัดสรรหน่วยความจำให้กับกรณี `Empty` เลยแม้แต่ครั้งเดียว ช่วยลดจำนวนครั้งในการขอหน่วยความจำบนฮีปลงไปได้ 1 ครั้ง แต่ทว่า ในการทำแบบนั้น มันกลับลงเอยด้วยการ *ผลาญพื้นที่หนักกว่าเดิมเสียอีก*! นั่นเป็นเพราะเลย์เอาต์ก่อนหน้านี้ได้อานิสงส์จากสิ่งที่เรียกว่า *การปรับประสิทธิภาพด้วยค่าพอยน์เตอร์ null (null pointer optimization)*

ก่อนหน้านี้เราเห็นแล้วว่า enum ทุกตัวจำเป็นต้องเก็บ *แท็ก (tag)* เพื่อระบุว่าบิตข้อมูลเหล่านั้นแทนวาเรียนต์ตัวไหนอยู่ แต่ถ้าเรามี enum ชนิดพิเศษที่มีหน้าตาทำนองนี้:

```rust,ignore
enum Foo {
    A,
    B(ContainsANonNullPtr),
}
```

กลไก null pointer optimization จะทำงานทันที ซึ่งมันจะช่วย *กำจัดพื้นที่ที่ต้องใช้เก็บแท็กทิ้งไปได้เลย* โดยหากวาเรียนต์นั้นเป็น A บิตของ enum ทั้งก้อนจะถูกเซตให้กลายเป็น `0` ทั้งหมด (null pointer) แต่ถ้าไม่ใช่ ก็แสดงว่าวาเรียนต์นั้นคือ B อย่างแน่นอน วิธีนี้ทำงานได้เพราะ B ไม่มีทางมีค่าเป็น `0` ล้วนได้อยู่แล้ว เนื่องจากมันเก็บตัวชี้ที่ไม่เป็นศูนย์ (non-null pointer) ฉลาดเป็นกรดเลยใช่ไหมล่ะ!

คุณพอนึกออกไหมว่ามี enum หรือชนิดข้อมูลแบบไหนอีกบ้างที่สามารถใช้ประโยชน์จากการปรับประสิทธิภาพแบบนี้ได้? มีเยอะมากเลยล่ะ! นี่คือเหตุผลที่ภาษา Rust ไม่ยอมกำหนดมาตรฐานการจัดวางเลย์เอาต์ของ enum ไว้อย่างตายตัว นอกจากนี้ Rust ยังมีการปรับแต่งเลย์เอาต์ของ enum ที่ซับซ้อนกว่านี้อีกหลายแบบ แต่การปรับแต่งด้วย null pointer ถือเป็นตัวที่สำคัญที่สุดอย่างแน่นอน! มันหมายความว่า `&`, `&mut`, `Box`, `Rc`, `Arc`, `Vec` และชนิดข้อมูลสำคัญอื่น ๆ อีกมากมายใน Rust จะไม่มีโอเวอร์เฮดเลยเวลาที่เรานำไปห่อหุ้มไว้ใน `Option`! (เราจะได้ไปทำความรู้จักกับของพวกนี้เกือบทั้งหมดเมื่อถึงเวลาอันควร)

แล้วเราจะทำยังไงดีล่ะ ถึงจะตัดขยะส่วนเกินทิ้งไปได้, จัดสรรหน่วยความจำได้อย่างสม่ำเสมอ, *แถม* ยังได้อานิสงส์จาก null pointer optimization สุดหวานเจี๊ยบนี้มาครอง? เราจำเป็นต้องแยกแนวคิดเรื่อง "การมีข้อมูลอยู่หนึ่งตัว" ออกจาก "การจัดสรรลิสต์ก้อนถัดไป" ให้ขาดจากกันอย่างชัดเจนยิ่งขึ้น และเพื่อที่จะทำแบบนั้นได้ เราจะต้องคิดในมุมมองที่ใกล้เคียงกับภาษา C มากขึ้นอีกนิด: นั่นคือการใช้ struct!

ในขณะที่ enum เปิดโอกาสให้เราประกาศชนิดข้อมูลที่สามารถเก็บค่าได้ *อย่างใดอย่างหนึ่ง* จากหลาย ๆ ค่า struct จะช่วยให้เราประกาศชนิดข้อมูลที่สามารถเก็บได้ *หลาย ๆ ค่าพร้อมกัน* ในคราวเดียว งั้นเรามาลองแยก `List` ของเราออกเป็นสองชนิดข้อมูลกัน: คือ `List` ตัวหนึ่ง และ `Node` อีกตัวหนึ่ง

และเช่นเคย `List` ยังคงเป็นได้ทั้ง Empty (ลิสต์ว่าง) หรือไม่ก็มีข้อมูลหนึ่งตัวที่ตามด้วย `List` อีกก้อนหนึ่ง แต่การแยกกรณี "มีข้อมูลตามด้วย List อีกก้อน" ออกมาเป็นชนิดข้อมูลต่างหากอย่างสมบูรณ์ จะช่วยให้เราสามารถยก `Box` ขึ้นไปไว้ในตำแหน่งที่เหมาะสมกว่าเดิมได้มาก:

```rust ,ignore
struct Node {
    elem: i32,
    next: List,
}

pub enum List {
    Empty,
    More(Box<Node>),
}
```

มาลองเช็กเช็กลิสต์ความต้องการของเรากันดูหน่อยซิ:

* ส่วนท้ายของลิสต์ไม่ต้องจัดสรรขยะส่วนเกิน: ผ่านฉลุย!
* `enum` อยู่ในรูปแบบที่ได้ประโยชน์จาก null pointer optimization อย่างเอร็ดอร่อย: ผ่านฉลุย!
* ข้อมูลทุกตัวได้รับการจัดสรรบนฮีปอย่างสม่ำเสมอเหมือนกันหมด: ผ่านฉลุย!

ยอดเยี่ยมไปเลย! จริง ๆ แล้ว โครงสร้างที่เราเพิ่งประกอบร่างขึ้นมานี้ ก็คือเลย์เอาต์แบบเดียวกับที่เราใช้เป็นตัวอย่างเพื่อพิสูจน์ให้เห็นว่าเลย์เอาต์แรกของเรา (ที่ลอกมาจากเอกสารคู่มือทางการของ Rust) มีปัญหานั่นแหละ

Rust เริ่มงอนเราอีกรอบแล้ว เราดันไปตั้งค่าให้ `List` เป็น public (เพราะเราอยากให้คนอื่นเรียกใช้งานได้) แต่เราไม่ได้ตั้ง `Node` ให้เป็น public ไปด้วย ปัญหาก็คือ ไส้ในของ `enum` จะเป็น public ทั้งหมดโดยอัตโนมัติ และ Rust ไม่อนุญาตให้เราเปิดเผยชนิดข้อมูลที่เป็น private สู่ภายนอกผ่านทาง public interface จริงอยู่ว่าเราจะแก้ด้วยการเปิด `Node` ให้เป็น public ทั้งหมดเลยก็ได้ แต่โดยธรรมเนียมปฏิบัติของ Rust แล้ว เรานิยมซ่อนรายละเอียดการทำงานภายใน (implementation details) ไว้เป็นความลับมากกว่า งั้นเรามาแปลง `List` ให้กลายเป็น struct กันดีกว่า เพื่อที่เราจะได้ซ่อนรายละเอียดการทำงานไว้ข้างในได้อย่างมิดชิด:

```rust ,ignore
pub struct List {
    head: Link,
}

enum Link {
    Empty,
    More(Box<Node>),
}

struct Node {
    elem: i32,
    next: Link,
}
```

และเนื่องจาก `List` เป็น struct ที่มีฟิลด์อยู่เพียงฟิลด์เดียว ขนาดของมันจึงเท่ากับขนาดของฟิลด์นั้นเป๊ะ ๆ ไชโยให้กับ zero-cost abstraction!

เอาล่ะ คราวนี้คอมไพล์ผ่านฉลุย! แม้ว่า Rust จะยังคงหงุดหงิดเราอยู่พอสมควร เพราะเท่าที่มันมองเห็น ทุกสิ่งทุกอย่างที่เราเพิ่งเขียนไปนั้นไร้ประโยชน์โดยสิ้นเชิง: เราไม่เคยเรียกใช้ `head` เลย และคนที่เอาไลบรารีของเราไปใช้ก็เรียกใช้ไม่ได้เหมือนกันเพราะมันเป็น private ซึ่งนั่นก็พลอยทำให้ `Link` กับ `Node` กลายเป็นของไร้ประโยชน์ตามไปด้วย งั้นเรามาแก้ปัญหานี้กันเถอะ! มาเริ่มลงมือเขียนโค้ดเมธอดให้กับ `List` ของเรากันเลย!
