# โครงสร้างในหน่วยความจำ (Layout)

เรามาเริ่มจากการศึกษาสรีระและโครงสร้างของศัตรูตัวฉกาจของเรากันก่อน ลิงก์ลิสต์แบบสองทาง (Doubly-Linked List) ในทางทฤษฎีแล้วดูเหมือนจะเรียบง่ายไม่มีอะไร แต่นั่นแหละคือเล่ห์เหลี่ยมกลลวงที่มันใช้หลอกล่อและปั่นหัวเรา มันก็คือ linked list แบบเดียวกับที่เราเคยเห็นซ้ำแล้วซ้ำเล่านั่นแหละ เพียงแต่คราวนี้เส้นเชื่อมโยงมันชี้ไปได้ทั้งสองทิศทาง ลิงก์เพิ่มขึ้นเป็นสองเท่า... ความชั่วร้ายก็ทวีคูณเป็นสองเท่าเช่นกัน!

ดังนั้น แทนที่จะเป็นแบบนี้ (ขอละเว้น `Some`/`None` ออกไปเพื่อให้ภาพดูสะอาดตาขึ้น):

```text
... -> (A, ptr) -> (B, ptr) -> ...
```

เราจะได้โครงสร้างหน้าตาแบบนี้แทน:

```text
... <-> (ptr, A, ptr) <-> (ptr, B, ptr) <-> ...
```

โครงสร้างแบบนี้ช่วยให้เราสามารถวิ่งท่องไปในลิสต์ได้จากทั้งสองทิศทาง หรือจะเลื่อนกระโดดไปข้างหน้าถอยหลังด้วย [เคอร์เซอร์ (cursor)](https://doc.rust-lang.org/std/collections/struct.LinkedList.html#method.cursor_back_mut) ก็ย่อมได้

และเพื่อแลกกับความยืดหยุ่นนี้ ทุกๆ โหนดจึงต้องเก็บพอยน์เตอร์เพิ่มขึ้นเป็นสองเท่า และทุกๆ operation ก็ต้องคอยตามแก้พอยน์เตอร์เยอะขึ้นกว่าเดิมมหาศาล มันเป็นความซับซ้อนที่ชวนให้เผลอทำโค้ดพังได้ง่ายเป็นบ้า ดังนั้นในบทนี้เราจึงต้องเขียนเทสต์กันแบบจัดหนักจัดเต็ม

คุณอาจจะสังเกตเห็นว่าผมจงใจละเว้นไม่วาดส่วน *ปลาย (ends)* ของลิสต์เอาไว้ นั่นเป็นเพราะจุดนี้คือหนึ่งในจุดที่มีทางเลือกในการ implement ที่เข้าท่าและมีเหตุผลรองรับด้วยกันทั้งคู่ แน่นอนว่าเรา*จำเป็นต้อง*มีพอยน์เตอร์สองตัวใน struct ของเราอย่างไม่ต้องสงสัย: ตัวหนึ่งชี้ไปที่หัวลิสต์ และอีกตัวชี้ไปที่ท้ายลิสต์

ในมุมมองของผม มี 2 แนวทางหลักที่น่าสนใจในการทำเรื่องนี้: นั่นคือแบบ "ดั้งเดิม (traditional)" กับแบบ "ดัมมี่โหนด (dummy node)"

แนวทางดั้งเดิมเป็นการต่อยอดแบบตรงไปตรงมาจากสิ่งที่เราเคยทำใน Stack &mdash; แค่เก็บพอยน์เตอร์ head กับ tail เอาไว้บน stack ของเรา:

```text
[ptr, ptr] <-> (ptr, A, ptr) <-> (ptr, B, ptr)
  ^                                        ^
  +----------------------------------------+
```

วิธีนี้ก็ใช้ได้ดี แต่มีข้อเสียอยู่เรื่องเดียว: เคสขอบ (corner cases) เพราะตอนนี้ลิสต์ของเรามีปลายเปิดสองด้าน นั่นแปลว่าเราต้องรับมือกับเคสขอบเพิ่มขึ้นเป็นสองเท่า และมันง่ายมากที่จะเผลอลืมไปสักเคสหนึ่งจนกลายเป็นบักร้ายแรง

ส่วนแนวทางแบบดัมมี่โหนด (dummy node) จะพยายามลบเหลี่ยมเคสขอบเหล่านี้ โดยการเพิ่มโหนดพิเศษขึ้นมาอีกหนึ่งตัว ซึ่งเป็นโหนดว่างเปล่าที่ไม่มีข้อมูลอะไรบรรจุอยู่เลย แต่ทำหน้าที่เชื่อมปลายทั้งสองข้างของลิสต์เข้าด้วยกันเป็นวงแหวน:

```text
[ptr] -> (ptr, ?DUMMY?, ptr) <-> (ptr, A, ptr) <-> (ptr, B, ptr)
           ^                                                 ^
           +-------------------------------------------------+ 
```

การทำแบบนี้จะทำให้ทุกๆ โหนดมีพอยน์เตอร์ที่ชี้ไปยังโหนดก่อนหน้าและโหนดถัดไปในลิสต์*อยู่เสมอ* แม้แต่ในจังหวะที่คุณลบเอลิเมนต์ตัวสุดท้ายออกจากลิสต์จนหมด สิ่งที่คุณต้องทำก็แค่เย็บพอยน์เตอร์ของ dummy node ให้วนกลับมาชี้ที่ตัวมันเองเท่านั้น:

```text
[ptr] -> (ptr, ?DUMMY?, ptr) 
           ^             ^
           +-------------+
```

ลึกๆ ในใจผมมองว่าวิธีนี้มันช่าง*ฟิน*และสง่างามเหลือเกิน แต่อนิจจา ในทางปฏิบัติตัวมันกลับมีปัญหาตามมาสองสามข้อ:

ปัญหาข้อที่ 1: เกิด indirection และการจองหน่วยความจำ (allocation) เพิ่มขึ้นมาโดยไม่จำเป็น โดยเฉพาะสำหรับลิสต์ว่างเปล่า ซึ่งก็ต้องเสียพื้นที่สร้าง dummy node ตัวนี้ขึ้นมาด้วย ทางออกที่เป็นไปได้ได้แก่:

* ไม่ต้อง allocate เจ้า dummy node จนกว่าจะมีการใส่ข้อมูลตัวแรกเข้ามา: ฟังดูเรียบง่ายและมีประสิทธิภาพดี แต่มันก็ดันดึงเอาเคสขอบบางส่วนที่เราอุตส่าห์หนีมาด้วยการใช้ dummy node วนกลับมาหาเราใหม่อีกรอบ!

* ใช้ dummy node ตัวเดียวแบบ static copy-on-write singleton ร่วมกับกลอุบายอันแยบยลที่ทำให้การเช็ก Copy-On-Write แอบเนียนไปกับการเช็กปกติได้: ฟังนะ... ผมโคตรอยากทำเลย ผมชอบอะไรวิตถารแบบนั้นเป็นบ้า แต่อนิจจา เราไม่สามารถพาทุกคนดำดิ่งสู่เส้นทางสายมืดในหนังสือเล่มนี้ได้ ถ้าคุณอยากเห็นอะไรที่พิสดารพิลึกกึกกือขนาดนั้น ลองไปเปิดดู [ซอร์สโค้ดของ ThinVec](https://docs.rs/thin-vec/0.2.4/src/thin_vec/lib.rs.html#319-325) ดูเอาเองละกัน

* เก็บ dummy node ไว้บน stack &mdash; ซึ่งเป็นไปไม่ได้ในทางปฏิบัติสำหรับภาษาที่ไม่มี move constructor แบบ C++ ผมมั่นใจว่ามันคงมีท่าประหลาดๆ ที่ทำได้ด้วย [Pin](https://doc.rust-lang.org/std/pin/index.html) แหละ แต่เราจะไม่ทำ

ปัญหาข้อที่ 2: แล้วจะเอา*ค่าอะไร*ไปเก็บไว้ในตัว dummy node ล่ะ? จริงอยู่ว่าถ้าเป็นตัวเลขจำนวนเต็มมันก็ไม่มีปัญหาอะไรหรอก แต่ถ้าลิสต์ของเราเก็บ `Box` ล่ะ? เราอาจจะไม่มีทางกำหนดค่าเริ่มต้น (initialize) ให้มันได้เลยด้วยซ้ำ! ทางออกที่เป็นไปได้ได้แก่:

* บังคับให้ทุกโหนดเก็บเป็น `Option<T>`: เรียบง่ายและได้ผลดี แต่มันทั้งบวมเทอะทะและน่ารำคาญ

* บังคับให้ทุกโหนดเก็บเป็น [`MaybeUninit<T>`](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html): ทั้งน่าสยดสยองและชวนปวดหัว

* ใช้ท่า type punning เลียนแบบการสืบทอด (inheritance) อย่างระมัดระวังและแยบยลสุดขีด เพื่อไม่ให้ตัว dummy node มีฟิลด์ข้อมูลติดมาด้วย ท่านี้ก็น่าเย้ายวนใจมากเหมือนกัน แต่มันอันตรายสุดกู่และชวนปวดหัวชะมัด ถ้าอยากเห็นอะไรที่วิตถารพิสดารขนาดนั้น ลองไปส่อง [ซอร์สโค้ดของ BTreeMap](https://doc.rust-lang.org/1.55.0/src/alloc/collections/btree/node.rs.html#49-104) ดูสิครับ

เมื่อชั่งน้ำหนักดูแล้ว ปัญหาพวกนี้มีมากกว่าความสะดวกสบายที่ได้รับสำหรับภาษาอย่าง Rust ดังนั้น เราจึงจะปักหลักอยู่กับ layout แบบดั้งเดิมกันต่อไป โดยเราจะใช้โครงสร้างพื้นฐานแบบเดียวกับที่เราเคยทำใน unsafe queue เมื่อบทที่แล้ว:

```rust
pub struct LinkedList<T> {
    front: Link<T>,
    back: Link<T>,
    len: usize,
}

type Link<T> = *mut Node<T>;

struct Node<T> {
    front: Link<T>,
    back: Link<T>,
    elem: T, 
}
```

(ในที่สุด เมื่อเราเดินทางมาถึง doubly-linked-deque เราก็ได้รับสิทธิ์อันชอบธรรมที่จะเรียกตัวเองว่า LinkedList เสียที เพราะนี่แหละคือ ลิงก์ลิสต์ที่แท้จริง)

แต่นี่อาจจะยังไม่ใช่ layout คุณภาพระดับโปรดักชันที่*แท้จริง*หรอกนะ มันก็*ใช้ได้*แหละ แต่มันยังมีลูกเล่นเวทมนตร์บางอย่างที่เราสามารถทำเพื่อช่วยบอก Rust ให้เข้าใจสิ่งที่เรากำลังทำได้ดียิ่งขึ้นไปอีก และในการจะทำแบบนั้นได้ เราจะต้องดำดิ่ง... ลึกลงไปอีกขั้น
