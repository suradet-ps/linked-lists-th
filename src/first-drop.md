# Drop (การทำลายอ็อบเจกต์และคืนทรัพยากร)

ตอนนี้เราสร้างสแต็กขึ้นมาได้แล้ว, สั่ง push ข้อมูลเข้าได้, สั่ง pop ข้อมูลออกได้ แถมเรายังเขียนเทสต์ยืนยันแล้วด้วยว่าทุกอย่างทำงานถูกต้องเป๊ะ!

แล้วเราจำเป็นต้องมานั่งกังวลเรื่องการเคลียร์หน่วยความจำและเก็บกวาดลิสต์ของเราไหมนะ? ถ้าตอบในทางเทคนิคแล้ว ก็แทบไม่ต้องเลยสักนิด! เช่นเดียวกับภาษา C++ ภาษา Rust มีระบบดีสตรัคเตอร์ (destructor) เพื่อช่วยเก็บกวาดทรัพยากรและคืนหน่วยความจำทิ้งให้โดยอัตโนมัติเมื่อตัวแปรนั้นหมดอายุการใช้งาน โดยชนิดข้อมูลใด ๆ จะมีดีสตรัคเตอร์ได้ก็ต่อเมื่อมันนำ *เทรต (trait)* ที่ชื่อว่า `Drop` ไปปฏิบัติ (implement) ซึ่งคำว่าเทรต ก็คือศัพท์หรู ๆ ที่ Rust ใช้เรียกอินเทอร์เฟซ (interface) นั่นเอง เทรต `Drop` มีหน้าตาอินเทอร์เฟซดังนี้:

```rust ,ignore
pub trait Drop {
    fn drop(&mut self);
}
```

ความหมายสั้น ๆ ง่าย ๆ ก็คือ "ทันทีที่คุณหลุดออกจากสโคป ฉันจะให้เวลาคุณสักแวบหนึ่งเพื่อเคลียร์สะสางธุระและเก็บกวาดตัวเองให้เรียบร้อย"

จริง ๆ แล้วคุณไม่จำเป็นต้อง implement `Drop` ด้วยตัวเองเลย หากชนิดข้อมูลของคุณประกอบขึ้นมาจากชนิดข้อมูลอื่น ๆ ที่มี `Drop` อยู่แล้ว และสิ่งเดียวที่คุณต้องการทำก็แค่เรียกดีสตรัคเตอร์ของพวกมันต่อ ๆ กันไป ในกรณีของ `List` สิ่งเดียวที่มันต้องการทำก็แค่สั่ง drop ส่วนหัว (head) ของมัน ซึ่งต่อจากนั้นส่วนหัวก็จะ *พยายาม* drop ตัว `Box<Node>` ต่อไปเป็นทอด ๆ โดยอัตโนมัติ... ทว่า มันมีปัญหาติดขัดอยู่จุดหนึ่ง

เพราะการเก็บกวาดแบบอัตโนมัตินี้ มันจะพังไม่เป็นท่า!

ลองพิจารณาลิสต์หน้าตาเรียบง่ายอันนี้ดู:

```text
list -> A -> B -> C
```

เมื่อตัวแปร `list` ถูก drop มันจะพยายามสั่ง drop โหนด A, ซึ่งโหนด A ก็จะพยายามสั่ง drop โหนด B ต่อ, และโหนด B ก็จะพยายามสั่ง drop โหนด C ต่อไปเรื่อย ๆ หลายคนเห็นภาพนี้แล้วอาจจะเริ่มรู้สึกเสียวสันหลังวาบขึ้นมาทันที... ใช่แล้ว นี่คือการทำงานแบบเรียกซ้ำ (recursive code) และโค้ดที่เรียกซ้ำไม่รู้จบแบบนี้ ย่อมสามารถทำให้สแต็กแตก (stack overflow) ได้อย่างง่ายดาย!

บางท่านอาจจะกำลังแย้งในใจว่า "เฮ้ย นี่มัน tail recursion (การเรียกซ้ำที่ตำแหน่งท้ายสุด) ชัด ๆ และภาษาโปรแกรมที่ดีภาษาไหน ๆ ก็ควรจะการันตีได้สิว่าโค้ดแบบนี้มันจะไม่ทำสแต็กแตก!" ซึ่งเอาจริง ๆ แล้ว... ความคิดนี้ *ผิดมหันต์* เลยครับ! เพื่อให้เห็นภาพว่าทำไมถึงผิด เราลองมาเขียนจำลองโค้ดสิ่งที่คอมไพเลอร์ต้องทำจริง ๆ โดยการเขียน `Drop` ให้กับ `List` เลียนแบบการทำงานของคอมไพเลอร์ดู:

```rust ,ignore
impl Drop for List {
    fn drop(&mut self) {
        // NOTE: you can't actually explicitly call `drop` in real Rust code;
        // we're pretending to be the compiler!
        self.head.drop(); // tail recursive - good!
    }
}

impl Drop for Link {
    fn drop(&mut self) {
        match *self {
            Link::Empty => {} // Done!
            Link::More(ref mut boxed_node) => {
                boxed_node.drop(); // tail recursive - good!
            }
        }
    }
}

impl Drop for Box<Node> {
    fn drop(&mut self) {
        self.ptr.drop(); // uh oh, not tail recursive!
        deallocate(self.ptr);
    }
}

impl Drop for Node {
    fn drop(&mut self) {
        self.next.drop();
    }
}
```

เห็นไหมล่ะ! เรา *ไม่สามารถ* สั่ง drop ข้อมูลข้างใน `Box` *หลังจาก* ที่เราคืนหน่วยความจำ (deallocate) ไปแล้วได้ ดังนั้นคำสั่งสุดท้ายจึงต้องเป็นการคืนหน่วยความจำเสมอ ส่งผลให้มันไม่มีทางที่จะ drop ในรูปแบบ tail-recursive ได้เลย! ด้วยเหตุนี้ เราจึงจำเป็นต้องลงมือเขียนกระบวนการ drop ของ `List` ด้วยตัวเองโดยใช้วิธีวนลูป (iterative drop) เพื่อยกเอาโหนดออกจากกล่อง box ทีละตัว:

```rust ,ignore
impl Drop for List {
    fn drop(&mut self) {
        let mut cur_link = mem::replace(&mut self.head, Link::Empty);
        // `while let` == "do this thing until this pattern doesn't match"
        while let Link::More(mut boxed_node) = cur_link {
            cur_link = mem::replace(&mut boxed_node.next, Link::Empty);
            // boxed_node goes out of scope and gets dropped here;
            // but its Node's `next` field has been set to Link::Empty
            // so no unbounded recursion occurs.
        }
    }
}
```

## โบนัสพิเศษ: ว่าด้วยเรื่อง Premature Optimization (การด่วนปรับประสิทธิภาพก่อนเวลาอันควร)!

โค้ดการ implement `drop` ของเราจริง ๆ แล้วมีหน้าตา *คล้ายคลึงมาก* กับการเขียนสั้น ๆ ว่า `while let Some(_) = self.pop() { }` ซึ่งดูเรียบง่ายกว่าเห็น ๆ แล้วสองวิธีนี้มันต่างกันยังไงล่ะ? และปัญหาด้านประสิทธิภาพแบบไหนที่อาจจะตามมาหลอกหลอนเราได้เมื่อเราเริ่มปรับให้ลิสต์ของเรารองรับเจเนอริกเพื่อเก็บข้อมูลอย่างอื่นที่ไม่ใช่แค่ตัวเลขอินทิเจอร์?

<details>
  <summary>คลิกตรงนี้เพื่อเปิดดูคำเฉลย</summary>

เมธอด `pop` ส่งค่ากลับออกมาเป็น `Option<i32>` ในขณะที่โค้ด `drop` ของเราจัดการเฉพาะตัว `Link` (`Box<Node>`) เท่านั้น ดังนั้น โค้ดของเราจึงขยับโยกย้ายแค่ตัวชี้ไปยังโหนดเท่านั้น ส่วนวิธีที่เรียกใช้ `pop` จะต้องโยกย้ายค่าของข้อมูลจริงที่เราเก็บไว้ในโหนดขึ้นมาบนสแต็กด้วยเสมอ ซึ่งสิ่งนี้จะมีราคาแพงมหาศาลหากในอนาคตเราปรับลิสต์เป็นแบบเจเนอริก แล้วมีใครสักคนเอาลิสต์นี้ไปเก็บอ็อบเจกต์ขนาดยักษ์อย่าง `VeryBigThingWithADropImpl` (VBTWADI) ในขณะที่ตัว `Box` จะสามารถสั่งรันดีสตรัคเตอร์ของข้อมูลข้างใน ณ ตำแหน่งเดิมในหน่วยความจำ (in-place) ได้ทันที จึงไม่เจอปัญหานี้ และในเมื่อข้อมูลยักษ์อย่าง VBTWADI ดันเป็น *เหตุผลหลักแท้ ๆ* ที่ทำให้ใครสักคนอยากเลือกใช้ลิงก์ลิสต์มากกว่าอาร์เรย์ หากเราทำประสิทธิภาพในเคสนี้ออกมาได้ห่วยแตก ก็คงจะเป็นเรื่องที่น่าผิดหวังไปหน่อย

ถ้าคุณอยากได้ข้อดีของทั้งสองวิธีนี้มารวมกัน คุณก็สามารถเพิ่มเมธอดใหม่เข้าไปได้ เช่น `fn pop_node(&mut self) -> Link` ซึ่งจะทำให้ทั้ง `pop` และ `drop` สามารถต่อยอดนำไปใช้งานได้อย่างสะอาดสะอ้านทั้งคู่

</details>
