# Layout

เราเริ่มจากการศึกษาโครงสร้างของศัตรูกันก่อน ลิงก์ลิสต์แบบสองทางนั้นเข้าใจง่ายในทางทฤษฎี แต่นั่นเองที่ทำให้มันหลอกลวงและควบคุมเราได้ มันเป็นลิงก์ลิสต์แบบเดียวกับที่เราเคยเห็นซ้ำแล้วซ้ำเล่า แต่คราวนี้ลิงก์ไปทั้งสองทิศทาง ลิงก์เป็นสองเท่า ความชั่วร้ายก็เป็นสองเท่า

ดังนั้นแทนที่จะเป็นแบบนี้ (จะละเว้น Some/None เพื่อให้กระชับขึ้น):

```text
... -> (A, ptr) -> (B, ptr) -> ...
```

เราจะมีแบบนี้:

```text
... <-> (ptr, A, ptr) <-> (ptr, B, ptr) <-> ...
```

สิ่งนี้ทำให้เราเดินทางข้ามลิสต์ได้จากทั้งสองทิศทาง หรือเคลื่อนที่ไปมาด้วย [เคอร์เซอร์](https://doc.rust-lang.org/std/collections/struct.LinkedList.html#method.cursor_back_mut)

แลกกับความยืดหยุ่นนี้ ทุกโหนดต้องจัดเก็บตัวชี้ (pointer) เป็นสองเท่า และทุกการดำเนินการต้องแก้ไขตัวชี้จำนวนมากขึ้นอย่างมาก นี่เป็นความซับซ้อนที่มากพอจะทำให้เกิดข้อผิดพลาดได้ง่าย ดังนั้นเราจะต้องทำเทสต์เป็นจำนวนมาก

คุณอาจสังเกตเห็นว่าผมจงใจไม่ได้แสดง *ปลายทั้งสอง* ของลิสต์ นั่นเป็นเพราะนี่เป็นจุดหนึ่งที่มีทางเลือกที่สมเหตุสมผลสำหรับการดำเนินการจริงๆ เรา *จำเป็นต้อง* ให้การดำเนินการของเรามีตัวชี้สองตัว: ตัวหนึ่งชี้ไปที่ต้นลิสต์ และอีกตัวชี้ไปที่ท้ายลิสต์

ในสายตาของผมมีสองวิธีที่โดดเด่นในการทำสิ่งนี้: แบบ "ดั้งเดิม" และแบบ "โหนด Dummy"

วิธีดั้งเดิมคือการขยายแบบง่ายๆ จากวิธีที่เราทำสแต็ก (stack) — เพียงเก็บตัวชี้หัว (head) และหาง (tail) ไว้ในสแต็ก:

```text
[ptr, ptr] <-> (ptr, A, ptr) <-> (ptr, B, ptr)
  ^                                        ^
  +----------------------------------------+
```

วิธีนี้ใช้ได้ แต่มีข้อเสียอยู่อย่างหนึ่ง: กรณีขอบ (corner cases) ตอนนี้ลิสต์ของเรามีปลายสองด้าน ซึ่งหมายความว่ามีกรณีขอบเป็นสองเท่า เป็นเรื่องง่ายที่จะลืมกรณีใดกรณีหนึ่งและเกิดข้อผิดพลาดร้ายแรง

วิธีโหนด Dummy พยายามลดกรณีขอบเหล่านี้โดยเพิ่มโหนดพิเศษเข้าไปในลิสต์ซึ่งไม่มีข้อมูลใดๆ แต่เชื่อมต่อปลายทั้งสองเข้าด้วยกันเป็นวง:

```text
[ptr] -> (ptr, ?DUMMY?, ptr) <-> (ptr, A, ptr) <-> (ptr, B, ptr)
           ^                                                 ^
           +-------------------------------------------------+ 
```

ด้วยวิธีนี้ ทุกโหนด *always* มีตัวชี้จริงไปยังโหนดก่อนหน้าและถัดไปในลิสต์ แม้แต่เมื่อคุณลบองค์ประกอบสุดท้ายออกจากลิสต์ คุณก็เพียงแค่เชื่อมต่อโหนด Dummy ให้ชี้กลับไปที่ตัวเอง:

```text
[ptr] -> (ptr, ?DUMMY?, ptr) 
           ^             ^
           +-------------+
```

มีส่วนหนึ่งในตัวผมที่รู้สึกว่าสิ่งนี้ *มาก* พึงพอใจและงดงาม น่าเสียดายที่มันมีปัญหาเชิงปฏิบัติอยู่สองประการ:

ปัญหาที่ 1: การ indirection และการจัดสรร (allocation) เพิ่มเติม โดยเฉพาะสำหรับลิสต์ว่างเปล่า ซึ่งต้องรวมโหนด Dummy ไว้ด้วย วิธีแก้ปัญหาที่เป็นไปได้ ได้แก่:

* อย่าจัดสรรโหนด Dummy จนกว่าจะมีการแทรกข้อมูล: ง่ายและมีประสิทธิภาพ แต่จะนำกรณีขอบบางส่วนที่เราพยายามหลีกเลี่ยงโดยใช้ตัวชี้ Dummy กลับมา!

* ใช้ singleton Dummy แบบ copy-on-write แบบ static พร้อมกับวิธีที่ชาญฉลาดมากบางอย่างที่ทำให้การตรวจสอบ Copy-On-Write สามารถใช้ประโยชน์จากการตรวจสอบปกติได้: ผมอยากลองมาก แต่เราไม่สามารถเดินบนเส้นทางมืดมิดนั้นในหนังสือเล่มนี้ได้ อ่าน [ซอร์สโค้ดของ ThinVec](https://docs.rs/thin-vec/0.2.4/src/thin_vec/lib.rs.html#319-325) หากคุณต้องการเห็นสิ่งแปลกประหลาดแบบนั้น

* เก็บโหนด Dummy ไว้ในสแต็ก — ไม่เป็นจริงในภาษาที่ไม่มี move-constructors แบบ C++ ผมแน่ใจว่ามีวิธีแปลกๆ ที่เราสามารถทำได้ที่นี่ด้วย [pinning](https://doc.rust-lang.org/std/pin/index.html) แต่เราจะไม่ทำแบบนั้น

ปัญหาที่ 2: *ค่า* ใดที่เก็บไว้ในโหนด Dummy? แน่นอนว่าถ้าเป็นจำนวนเต็มก็ไม่มีปัญหา แต่ถ้าเราเก็บลิสต์ที่เต็มไปด้วย `Box` ล่ะ? เราอาจไม่สามารถเริ่มต้นค่านี้ได้เลย! วิธีแก้ปัญหาที่เป็นไปได้ ได้แก่:

* ให้ทุกโหนดเก็บ `Option<T>`: ง่ายและมีประสิทธิภาพ แต่ก็ใหญ่เทอะทะและน่ารำคาญ

* ให้ทุกโหนดเก็บ [`MaybeUninit<T>`](https://doc.rust-lang.org/std/mem/union.MaybeUninit.html). น่ากลัวและน่ารำคาญ

* การ type punning แบบ inheritance-style ที่ *จริงจัง* ระวังและชาญฉลาดมาก จนโหนด Dummy ไม่รวมฟิลด์ข้อมูล วิธีนี้ก็น่าลองเช่นกัน แต่อันตรายและน่ารำคาญอย่างยิ่ง อ่าน [ซอร์สของ BTreeMap](https://doc.rust-lang.org/1.55.0/src/alloc/collections/btree/node.rs.html#49-104) หากคุณต้องการเห็นสิ่งแปลกประหลาดแบบนั้น

ปัญหาเหล่านี้มีมากกว่าความสะดวกสำหรับภาษาอย่าง Rust ดังนั้นเราจะยึดติดกับเลย์เอาต์แบบดั้งเดิม เราจะใช้การออกแบบพื้นฐานเดียวกับที่เราใช้สำหรับคิว (queue) แบบ unsafe ในบทก่อนหน้า:

```rust
pub struct LinkedList<T> {
    front: Link<T>,
    back: Link<T>,
    len: usize,
}

type Link<T> = *mut Node<T>;

struct Node<T> {
    front: Link<T>,
    back: Link<T>,
    elem: T, 
}
```

(ตอนนี้ที่เราได้มาถึง doubly-linked-deck แล้ว ในที่สุดเราก็ได้รับสิทธิ์ที่จะเรียกตัวเองว่า LinkedList เพราะนี่คือ True Linked List.)

นี่ยังไม่ใช่เลย์เอาต์แบบ *จริง* สำหรับการผลิตจริงๆ มัน *fine* แต่ยังมีเทคนิคเวทมนตร์ที่เราสามารถทำได้เพื่อบอก Rust ว่าเรากำลังทำอะไรอยู่ได้ดีขึ้นอีกหน่อย เพื่อทำสิ่งนั้นเราจะต้องเข้า... ลึกขึ้น
