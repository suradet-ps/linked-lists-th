# เรียน Rust ด้วยลิงก์ลิสต์ที่เยอะเกินเหตุ

> มีปัญหาอะไรมั้ย หรืออยากดูโค้ดสุดท้ายทั้งหมดในครั้งเดียว?
> [ทุกอย่างอยู่บน Github!][github]

> **หมายเหตุ**: หนังสือฉบับปัจจุบันเขียนขึ้นสำหรับ Rust 2018
> ซึ่งปล่อยครั้งแรกพร้อมกับ rustc 1.31 (8 ธ.ค. 2018) ถ้าทูลเชน Rust ของคุณ
> ใหม่พอ ไฟล์ Cargo.toml ที่ `cargo new` สร้างขึ้นควรมีบรรทัด
> `edition = "2018"` (หรือถ้าคุณกำลังอ่านอยู่นี้ในอนาคตอันไกล บางทีอาจเป็นเลข
> ที่ใหญ่กว่านั้น!). การใช้ทูลเชนเก่าก็เป็นไปได้ แต่มันจะปลดล็อก
> **โหมดยากสุด (hardmode)** ลับ ๆ ซึ่งคุณจะเจอข้อผิดพลาดจากคอมไพเลอร์เพิ่มเติม
> ที่ไม่มีกล่าวถึงในหนังสือเล่มนี้เลย โว้ว ฟังดูสนุกดี!

ผมถูกถามบ่อย ๆ ว่าต้องเขียนลิงก์ลิสต์ใน Rust ยังไง คำตอบก็คือมันขึ้นอยู่กับ
ความต้องการของคุณจริง ๆ และแน่นอนว่ามันไม่ใช่คำถามที่ตอบได้ง่าย ๆ ในทันทีทันใด
ผมเลยตัดสินใจเขียนหนังสือเล่มนี้เพื่อตอบคำถามนี้อย่างครอบคลุมที่สุด ทีเดียวจบ

ในชุดบทความนี้ ผมจะสอนคุณทั้งการเขียนโปรแกรม Rust ระดับพื้นฐานและระดับสูง
โดยให้คุณเขียนลิงก์ลิสต์ทั้งหมด 6 ตัว เมื่อทำเสร็จ คุณควรจะได้เรียนรู้:

* ชนิดของตัวชี้ต่อไปนี้: `&`, `&mut`, `Box`, `Rc`, `Arc`, `*const`, `*mut`, `NonNull`(?)
* ความเป็นเจ้าของ, การยืม, มิวเทบิลิตี้ที่สืบทอด, มิวเทบิลิตี้ภายใน, Copy
* คีย์เวิร์ดทั้งหมด: struct, enum, fn, pub, impl, use, ...
* การจับคู่แพตเทิร์น, เจเนอริก, ดีสตรัคเตอร์
* การทดสอบ, การติดตั้งทูลเชนใหม่, การใช้ `miri`
* Rust แบบ unsafe: ตัวชี้ดิบ, การแอลิเอส, stacked borrows, UnsafeCell, วาเรียนซ์

ใช่แล้ว ลิงก์ลิสต์มันแย่ขนาดนั้นแหละ คุณจะได้เจอกับแนวคิดพวกนี้ทั้งหมด
ตอนทำให้มันใช้งานได้จริง

ทุกอย่างอยู่ที่แถบด้านข้าง (บนมือถืออาจถูกยุบไว้) แต่เพื่อความรวดเร็ว

เพื่อให้เราเข้าใจตรงกัน ผมจะเขียนคำสั่งทั้งหมดที่ผมพิมพ์ใส่เทอร์มินัล
ผมจะใช้ตัวจัดการแพ็กเกจมาตรฐานของ Rust อย่าง Cargo ในการพัฒนาโปรเจกต์ด้วย
Cargo ไม่ได้จำเป็นสำหรับการเขียนโปรแกรม Rust แต่มัน*ดีกว่ามาก*เมื่อเทียบกับ
การใช้ rustc โดยตรง ถ้าคุณแค่อยากลองเล่น ๆ คุณก็สามารถรันโปรแกรมง่าย ๆ
บนเบราว์เซอร์ได้ผ่าน [play.rust-lang.org][play]

ในส่วนหลัง ๆ เราจะใช้ "rustup" เพื่อติดตั้งเครื่องมือ Rust เพิ่มเติม
ผมแนะนำอย่างยิ่งให้[ติดตั้งทูลเชน Rust ทั้งหมดของคุณด้วย rustup](https://www.rust-lang.org/tools/install)

มาเริ่มกันเลยและสร้างโปรเจกต์ของเรา:

```text
> cargo new --lib lists
> cd lists
```

เราจะใส่ลิสต์แต่ละตัวไว้ในไฟล์แยกกัน เพื่อที่เราจะได้ไม่เสียงานที่ทำไป

ควรจะบอกไว้ก่อนว่า ประสบการณ์การเรียนรู้ Rust แบบ*แท้จริง*นั้น
คือการเขียนโค้ด ให้คอมไพเลอร์ตะโกนใส่คุณ แล้วพยายามคิดว่ามันหมายความว่าอะไรกันแน่
ผมจะคอยดูแลให้สิ่งนี้เกิดขึ้นบ่อยที่สุดเท่าที่จะเป็นไปได้
การเรียนรู้ที่จะอ่านและเข้าใจข้อผิดพลาดและเอกสารประกอบที่ยอดเยี่ยมโดยทั่วไปของ Rust
นั้น*สำคัญอย่างไม่น่าเชื่อ*ต่อการเป็นโปรแกรมเมอร์ Rust ที่มีประสิทธิภาพ

จริง ๆ แล้วนั่นเป็นเรื่องโกหก ตอนเขียนหนังสือเล่มนี้ ผมเจอข้อผิดพลาดจากคอมไพเลอร์
*เยอะกว่ามาก*ที่ผมแสดงให้เห็น โดยเฉพาะในบทหลัง ๆ ผมจะไม่แสดงข้อผิดพลาดแบบสุ่ม ๆ
ที่คุณพิมพ์ (หรือก๊อปแปะ) ผิดซึ่งคุณคาดว่าจะเจอได้ในทุกภาษา
นี่คือ*ทัวร์พร้อมไกด์*ของการที่คอมไพเลอร์ตะโกนใส่เรา

เราจะไปกันช้า ๆ และพูดจริง ๆ ว่าผมจะไม่ค่อยจริงจังเท่าไหร่ตลอดทั้งเล่ม
ผมคิดว่าการเขียนโปรแกรมควรจะสนุก ให้ตายเถอะ!
ถ้าคุณเป็นคนที่อยากได้เนื้อหาที่แน่นไปด้วยข้อมูล, จริงจัง, และเป็นทางการที่สุด
หนังสือเล่มนี้ไม่ใช่สำหรับคุณ ไม่มีอะไรที่ผมจะทำเพื่อคุณ
คุณผิดแล้ว

# ประกาศสาธารณะที่ต้องมี

เพื่อให้ชัดเจน 100%: ผมเกลียดลิงก์ลิสต์ เกลียดแบบสุดหัวใจ
ลิงก์ลิสต์เป็นโครงสร้างข้อมูลที่แย่มาก แน่นอนว่ามันมีกรณีการใช้งานที่ยอดเยี่ยมอยู่หลายกรณี:

* คุณต้องการ*แยกหรือรวม*ลิสต์ขนาดใหญ่*เป็นจำนวนมาก*
* คุณกำลังทำอะไรแบบ lock-free คอนเคอร์เรนต์เจ๋ง ๆ
* คุณกำลังเขียนอะไรแบบเคอร์เนล/เอ็มเบดเด็ด และอยากใช้ลิสต์แบบอินทรูซีฟ
* คุณใช้ภาษาเชิงฟังก์ชันล้วน ๆ ซึ่งความหมายที่จำกัดและการไม่มีการกลายพันธุ์
  ทำให้ลิงก์ลิสต์ใช้งานได้ง่ายกว่า
* ... และอีกมากมาย!

แต่กรณีทั้งหมดนี้*หายากมาก*สำหรับใครก็ตามที่เขียนโปรแกรม Rust
99% ของเวลาคุณควรใช้ Vec (สแต็กแบบอาร์เรย์) และ 99% ของอีก 1% ที่เหลือ
คุณควรใช้ VecDeque (เดกแบบอาร์เรย์) โครงสร้างข้อมูลพวกนี้เหนือกว่าอย่างเห็นได้ชัด
สำหรับงานส่วนใหญ่ เนื่องจากจัดสรรหน่วยความจำน้อยกว่า ใช้หน่วยความจำน้อยกว่า
เข้าถึงแบบสุ่มได้จริง และ cache locality ดีกว่า

ลิงก์ลิสต์เป็นโครงสร้างข้อมูลที่*เฉพาะทาง (niche)* และ*คลุมเครือ*พอ ๆ กับ trie
คงไม่มีใครเถียงถ้าผมบอกว่า trie เป็นโครงสร้างเฉพาะทางที่โปรแกรมเมอร์ทั่วไป
สามารถใช้ทั้งอาชีพโดยไม่ต้องเรียนรู้มันเลยได้อย่างมีความสุข -- แต่ลิงก์ลิสต์กลับมี
สถานะคนดังที่แปลกประหลาด เราสอนนักศึกษาปริญญาตรีทุกคนให้เขียนลิงก์ลิสต์
มันเป็นคอลเลกชันเฉพาะทางเพียงตัวเดียว
[ที่ผมฆ่าไม่ตายจาก std::collections][rust-std-list] มันเป็น
[*ลิสต์*ใน C++][cpp-std-list]!

เราทุกคนในคอมมูนิตี้ควรพูด *ไม่* กับลิงก์ลิสต์ในฐานะโครงสร้างข้อมูล "มาตรฐาน"
มันเป็นโครงสร้างข้อมูลที่ใช้ได้ดีกับกรณีการใช้งานที่ยอดเยี่ยมหลายกรณี
แต่กรณีเหล่านั้น*เป็นกรณียกเว้น* ไม่ใช่เรื่องปกติ

มีคนหลายคนที่ดูเหมือนจะอ่านแค่ย่อหน้าแรกของประกาศนี้แล้วก็หยุดอ่าน
คือแบบ พวกเขาจะพยายามโต้แย้งโดยการยกหนึ่งในรายการที่ผมเขียนไว้ใน
รายการ*กรณีการใช้งานที่ยอดเยี่ยม* สิ่งที่อยู่ถัดจากย่อหน้าแรกน่ะแหละ!

เพื่อให้ผมสามารถลิงก์ไปยังข้อโต้แย้งโดยละเอียดได้โดยตรง
นี่คือความพยายามโต้แย้งหลายครั้งที่ผมเคยเห็น และคำตอบของผมต่อมัน
ถ้าอยากเรียนรู้ Rust เลยก็ข้ามไปที่[บทแรก](first.md)ได้เลย!

## ประสิทธิภาพไม่ได้สำคัญเสมอไป

ใช่! บางทีแอปพลิเคชันของคุณอาจเป็นแบบ I/O-bound หรือโค้ดส่วนนั้นอยู่ในกรณี
ที่ไม่ค่อยได้ใช้ซึ่งมันไม่สำคัญเท่าไหร่ แต่นี่ไม่ใช่ข้อโต้แย้งสำหรับการใช้ลิงก์ลิสต์
นี่คือข้อโต้แย้งสำหรับการใช้*อะไรก็ได้เลย* จะมัวใช้ลิงก์ลิสต์ทำไม?
ใช้ลิงก์แฮชแมปสิ!

ถ้าประสิทธิภาพไม่สำคัญ มันก็*แน่นอน*ว่าการใช้ค่าเริ่มต้นตามธรรมชาติอย่างอาร์เรย์
นั้นไม่มีปัญหา

## พวกมันมี O(1) สำหรับ split-append-insert-remove ถ้าคุณมีตัวชี้อยู่ตรงนั้น

ใช่แล้ว! แม้ว่าตามที่ [Bjarne Stroustrup กล่าวไว้][bjarne] *มันไม่ได้สำคัญจริง ๆ*
ถ้าเวลาที่ใช้ในการได้ตัวชี้มานั้นมากกว่าเวลาที่ใช้คัดลอกองค์ประกอบทั้งหมดในอาร์เรย์
(ซึ่งจริง ๆ แล้วเร็วมาก) เสียอีก

นอกจากคุณจะมีเวิร์กโหลดที่ถูกครอบงำด้วยต้นทุนการแยกและรวมอย่างหนัก
การลงโทษของ*การทำงานอื่น ๆ ทุกครั้ง*จากผลกระทบของแคชและความซับซ้อนของโค้ด
จะทำลายกำไรทางทฤษฎีทั้งหมด

*แต่ใช่ ถ้าคุณโปรไฟล์แอปพลิเคชันของคุณแล้วพบว่ามันใช้เวลาส่วนใหญ่กับ
การแยกและรวม คุณอาจได้กำไรจากการใช้ลิงก์ลิสต์*

## ผมจ่ายค่าเฉลี่ย (amortization) ไม่ไหว

คุณเข้าไปในพื้นที่เฉพาะทางมากแล้ว -- คนส่วนใหญ่รับมือกับค่าเฉลี่ยได้
ยังไงก็ตาม อาร์เรย์มีค่าเฉลี่ย*ในกรณีแย่ที่สุด* การใช้อาร์เรย์ไม่ได้หมายความว่า
คุณมีต้นทุนแบบเฉลี่ย ถ้าคุณคาดเดาได้ว่าคุณจะเก็บกี่องค์ประกอบ (หรือแม้แต่มี
ขอบเขตบน) คุณก็สามารถจองพื้นที่ทั้งหมดที่ต้องการไว้ล่วงหน้าได้
จากประสบการณ์ของผม มัน*บ่อยมาก*ที่จะคาดเดาได้ว่าคุณต้องใช้องค์ประกอบกี่ตัว
ใน Rust โดยเฉพาะ อิเทอเรเตอร์ทุกตัวมี `size_hint` สำหรับกรณีนี้โดยเฉพาะ

จากนั้น `push` และ `pop` จะเป็นโอเปอเรชัน O(1) อย่างแท้จริง
และมันจะ*เร็วกว่าอย่างเห็นได้ชัด*เมื่อเทียบกับ `push` และ `pop` บนลิงก์ลิสต์
คุณแค่เลื่อนตัวชี้ เขียนไบต์ และเพิ่มจำนวนเต็ม ไม่ต้องไปยุ่งกับตัวจัดสรรหน่วยความจำ
แบบไหนทั้งนั้น

ว่าไงล่ะ สำหรับความหน่วงต่ำ?

*แต่ใช่ ถ้าคุณคาดเดาภาระงานไม่ได้ ก็ยังมีการประหยัดความหน่วงในกรณีแย่ที่สุดอยู่!*

## ลิงก์ลิสต์ใช้พื้นที่น้อยกว่า

อืม เรื่องนี้มันซับซ้อน กลยุทธ์การปรับขนาดอาร์เรย์แบบ "มาตรฐาน" คือการขยายหรือ
หดขนาดให้อย่างน้อยครึ่งหนึ่งของอาร์เรย์ว่างเปล่า นี่คือพื้นที่ที่สูญเปล่าเยอะมากจริง ๆ
โดยเฉพาะใน Rust เราไม่หดขนาดคอลเลกชันอัตโนมัติ (มันเสียเปล่าถ้าคุณแค่จะเติม
มันกลับเข้าไปใหม่) ดังนั้นการสูญเปล่าอาจเข้าใกล้ไม่มีที่สิ้นสุด!

แต่นี่เป็นกรณีแย่ที่สุด ในกรณีดีที่สุด สแต็กแบบอาร์เรย์มีตัวชี้โอเวอร์เฮดเพียงสามตัว
สำหรับทั้งอาร์เรย์ โดยพื้นฐานคือไม่มีโอเวอร์เฮดเลย

ในทางกลับกัน ลิงก์ลิสต์เสียพื้นที่ต่อองค์ประกอบอย่างไม่มีเงื่อนไข
ลิงก์ลิสต์แบบซิงกลีเสียตัวชี้หนึ่งตัว ในขณะที่ลิงก์ลิสต์แบบดับเบิลเสียสองตัว
ไม่เหมือนอาร์เรย์ ความสูญเปล่าสัมพัทธ์เป็นสัดส่วนกับขนาดขององค์ประกอบ
ถ้าคุณมีองค์ประกอบ*ขนาดใหญ่* ความสูญเปล่านี้จะเข้าใกล้ 0 ถ้าคุณมีองค์ประกอบเล็ก ๆ
(เช่น ไบต์) ความสูญเปล่าอาจสูงถึง 16 เท่าของหน่วยความจำ (8 เท่าในระบบ 32 บิต)!

จริง ๆ แล้วมันประมาณ 23 เท่า (11 เท่าในระบบ 32 บิต) เพราะจะมีการเพิ่ม padding
ให้กับไบต์เพื่อให้ขนาดของโหนดทั้งตัวเรียงกับขนาดของตัวชี้

นี่ยังสมมติกรณีดีที่สุดสำหรับตัวจัดสรรหน่วยความจำของคุณ: การจัดสรรและ
ปลดปล่อยโหนดเกิดขึ้นอย่างหนาแน่น และคุณไม่สูญเสียหน่วยความจำให้กับการแตกกระจาย (fragmentation)

*แต่ใช่ ถ้าคุณมีองค์ประกอบขนาดใหญ่ คาดเดาภาระงานไม่ได้ และมีตัวจัดสรรที่เหมาะสม
ก็ยังมีการประหยัดหน่วยความจำอยู่!*

## ฉันใช้ลิงก์ลิสต์ตลอดเวลาในภาษาเชิงฟังก์ชัน

เยี่ยม! ลิงก์ลิสต์ใช้งานได้อย่างสวยงามในภาษาเชิงฟังก์ชัน เพราะคุณสามารถจัดการมันได้
โดยไม่ต้องกลายพันธุ์อะไร บรรยายมันแบบรีเคอร์ซีฟได้ และยังใช้งานกับลิสต์อนันต์ได้
ด้วยเวทมนตร์แห่งความเกียจคร้าน (laziness)

โดยเฉพาะอย่างยิ่ง ลิงก์ลิสต์เป็นสิ่งที่ดีเพราะมันแทนการวนซ้ำโดยไม่ต้องมีสถานะที่
กลายพันธุ์ได้ ขั้นตอนถัดไปก็แค่เยี่ยมชมซับลิสต์ถัดไป

Rust ทำสิ่งแบบนี้เป็นส่วนใหญ่ด้วย [อิเทอเรเตอร์][iterators] พวกมันสามารถเป็นอนันต์ได้
และคุณสามารถ map, filter, reverse, และต่อพวกมันเข้าด้วยกันได้เหมือนลิสต์เชิงฟังก์ชัน
และทั้งหมดจะเกิดขึ้นแบบเกียจคร้านเหมือนกัน!

Rust ยังให้คุณพูดถึงซับอาร์เรย์ได้ง่าย ๆ ด้วย *[สไลซ์][slices]*
การแยก head/tail แบบปกติของคุณในภาษาเชิงฟังก์ชันคือ
[แค่ `slice.split_at_mut(1)`][split] เป็นเวลานาน Rust มีระบบทดลองสำหรับ
การจับคู่แพตเทิร์นบนสไลซ์ซึ่งเจ๋งมาก แต่ฟีเจอร์นั้นถูกทำให้ง่ายขึ้นตอนที่มัน
ถูกทำให้เสถียร ยังไงก็ตาม [แพตเทิร์นสไลซ์พื้นฐาน][slice-pats] ก็ยังเจ๋งอยู่!
และแน่นอน สไลซ์สามารถกลายเป็นอิเทอเรเตอร์ได้!

*แต่ใช่ ถ้าคุณถูกจำกัดให้ใช้ความหมายแบบอิมมิวเทเบิล ลิงก์ลิสต์ก็ใช้งานได้ดีมาก*

โปรดสังเกตว่าผมไม่ได้บอกว่าการเขียนโปรแกรมเชิงฟังก์ชันอ่อนแอหรือไม่ดีโดยเนื้อแท้
แต่มัน*ถูกจำกัดทางความหมายโดยพื้นฐาน*: คุณส่วนใหญ่ได้รับอนุญาตให้พูดถึงว่าสิ่งต่าง ๆ
*เป็น*อย่างไร ไม่ใช่ว่าควรจะ*ทำ*อย่างไร นี่เป็น*ฟีเจอร์*จริง ๆ เพราะมันทำให้
คอมไพเลอร์ทำ[การแปลงสุดแปลก][ghc]มากมาย และอาจหาวิธี*ที่ดีที่สุด*ในการทำสิ่งต่าง ๆ
โดยที่คุณไม่ต้องกังวลกับมัน แต่นี่แลกมาด้วยการ*ไม่สามารถ*กังวลกับมันได้
โดยปกติจะมีช่องหนีภัยอยู่บ้าง แต่ถึงจุดหนึ่งคุณก็กลับไปเขียนโค้ดแบบโพรซีดเดอรัลอีกครั้ง

แม้แต่ในภาษาเชิงฟังก์ชัน คุณควรพยายามใช้โครงสร้างข้อมูลที่เหมาะสมกับงาน
เมื่อคุณต้องการโครงสร้างข้อมูลจริง ๆ ใช่ ลิงก์ลิสต์แบบซิงกลีเป็นเครื่องมือหลัก
ของคุณสำหรับการควบคุมโฟลว์ แต่มันเป็นวิธีที่แย่มากสำหรับการเก็บข้อมูลจำนวนมาก
และค้นหาข้อมูลในนั้น

## ลิงก์ลิสต์ดีมากสำหรับการสร้างโครงสร้างข้อมูลแบบคอนเคอร์เรนต์!

ใช่! แม้ว่าการเขียนโครงสร้างข้อมูลแบบคอนเคอร์เรนต์จะเป็นอะไรที่คนละเรื่องเลย
และไม่ใช่สิ่งที่ควรทำอย่างเบามือ แน่นอนว่าไม่ใช่สิ่งที่หลายคนจะ*คิด*จะทำด้วยซ้ำ
เมื่อเขียนเสร็จแล้ว คุณก็ไม่ได้เลือกใช้ลิงก์ลิสต์อีกต่อไป
คุณเลือกใช้คิว MPSC หรืออะไรก็ตาม กลยุทธ์การนำไปปฏิบัติในกรณีนี้
ห่างไกลกันมาก!

*แต่ใช่ ลิงก์ลิสต์เป็นฮีโร่โดยพฤตินัยของโลกมืดแห่งคอนเคอร์เรนซีแบบ lock-free*

## พึมพำ ๆ เคอร์เนล เอ็มเบดเด็ด อะไรสักอย่าง อินทรูซีฟ.

มันเฉพาะทางมาก คุณกำลังพูดถึงสถานการณ์ที่คุณไม่ได้ใช้*รันไทม์*ของภาษาด้วยซ้ำ
นั่นไม่ใช่ธงแดงหรือว่าคุณกำลังทำอะไรที่แปลก ๆ อยู่?

มันยังอันตรายสุดขีดอีกด้วย

*แต่เอาเถอะ สร้างลิสต์แบบ zero-allocation สุดเจ๋งของคุณบนสแต็กไปเลย*

## อิเทอเรเตอร์ไม่ถูกทำให้ใช้งานไม่ได้จากการเพิ่ม/ลบที่ไม่เกี่ยวข้อง

นั่นเป็นการเต้นที่ละเอียดอ่อนที่คุณกำลังทำอยู่ โดยเฉพาะถ้าคุณไม่มี garbage collector
ผมอาจเถียงได้ว่าโฟลว์การควบคุมและแพตเทิร์นความเป็นเจ้าของของคุณ
อาจจะพันกันเกินไปเล็กน้อย ขึ้นอยู่กับรายละเอียด

*แต่ใช่ คุณสามารถทำอะไรเจ๋ง ๆ แบบบ้าคลั่งกับเคอร์เซอร์ได้*

## พวกมันง่ายและดีมากสำหรับการสอน!

ก็ใช่สิ คุณกำลังอ่านหนังสือที่อุทิศให้กับสมมติฐานนั้นอยู่
เอาล่ะ ลิงก์ลิสต์แบบซิงกลีค่อนข้างง่าย ลิงก์ลิสต์แบบดับเบิล
อาจจะยุ่งยากไปบ้าง อย่างที่เราจะได้เห็นกัน
