# Arc (การแชร์แบบอะตอมิก)

เหตุผลหนึ่งในการใช้ลิงก์ลิสต์ที่ไม่เปลี่ยนแปลงได้คือเพื่อแบ่งปันข้อมูล
ระหว่างเธรด ท้ายที่สุด สถานะที่กลายพันธุ์ร่วมคือรากของความชั่วร้ายทั้งปวง
และวิธีแก้ปัญหาหนึ่งคือกำจัดส่วนที่*กลายพันธุ์*ตลอดกาล

ยกเว้นลิสต์ของเราไม่ปลอดภัยต่อเธรดเลย เพื่อให้ปลอดภัยต่อเธรด เราต้อง
จัดการจำนวนอ้างอิง*แบบอะตอมิก* ไม่อย่างนั้นสองเธรดอาจพยายามเพิ่ม
จำนวนอ้างอิง *และมีแค่ตัวเดียวที่เกิดขึ้น* จากนั้นลิสต์อาจถูกปลดปล่อย
เร็วเกินไป!

เพื่อให้ปลอดภัยต่อเธรด เราต้องใช้ *Arc* Arc เหมือน Rc ทุกประการ
เว้นแต่จำนวนอ้างอิงถูกแก้ไขแบบอะตอมิก สิ่งนี้มีโอเวอร์เฮดเล็กน้อยถ้าคุณ
ไม่ต้องการ ดังนั้น Rust จึงมีทั้งสองแบบ สิ่งเดียวที่เราต้องทำเพื่อให้
ลิสต์ของเราปลอดภัยต่อเธรดคือแทนที่ทุกการอ้างถึง Rc ด้วย `std::sync::Arc`
แค่นั้น เราปลอดภัยต่อเธรดแล้ว เสร็จ!

แต่นี่ raises คำถามที่น่าสนใจ: เรา*รู้*ได้ยังไงว่าชนิดหนึ่งปลอดภัยต่อเธรด
หรือไม่? เราทำให้พังโดยบังเอิญได้มั้ย?

ไม่! คุณไม่สามารถทำให้ความปลอดภัยต่อเธรดพังใน Rust ได้!

เหตุผลที่เป็นแบบนี้คือ Rust สร้างแบบจำลองความปลอดภัยต่อเธรด
ในรูปแบบเฟิร์สคลาสด้วยสองเทรต: `Send` และ `Sync`

ชนิดหนึ่งเป็น *Send* ถ้ามันปลอดภัยที่จะ*ย้าย*ไปยังเธรดอื่น ชนิดหนึ่งเป็น
*Sync* ถ้ามันปลอดภัยที่จะ*แบ่งปัน*ระหว่างหลายเธรด นั่นคือถ้า `T` เป็น Sync
`&T` จะเป็น Send ปลอดภัยในที่นี้หมายความว่ามันเป็นไปไม่ได้ที่จะก่อให้เกิด
*data races* (ไม่ต้องสับสนกับปัญหาที่กว้างกว่าของ*race conditions*)

เหล่านี้คือเทรตมาร์กเกอร์ ซึ่งเป็นคำหรู ๆ ที่บอกว่ามันเป็นเทรตที่ไม่มี
อินเทอร์เฟซเลย คุณ*เป็น* Send หรือไม่เป็น มันเป็นแค่คุณสมบัติที่
API *อื่น*สามารถเรียกได้ ถ้าคุณไม่ Send อย่างเหมาะสม
มันเป็นไปไม่ได้ที่จะถูกส่งไปยังเธรดอื่นแบบ static! ยอดเยี่ยม!

Send และ Sync ยังเป็นเทรตที่ถูกสืบทอดโดยอัตโนมัติตามว่าคุณ
ประกอบด้วยชนิด Send และ Sync ทั้งหมดหรือไม่ มันคล้ายกับวิธีที่คุณ
สามารถ implement Copy ได้เฉพาะเมื่อคุณประกอบด้วยชนิด Copy เท่านั้น
แต่แล้วเราก็ implement มันโดยอัตโนมัติถ้าคุณเป็น

แทบทุกชนิดเป็น Send และ Sync ชนิดส่วนใหญ่เป็น Send เพราะพวกมัน
เป็นเจ้าของข้อมูลของมันทั้งหมด ชนิดส่วนใหญ่เป็น Sync เพราะวิธีเดียว
ในการแบ่งปันข้อมูลระหว่างเธรดคือการใส่ไว้หลังเรเฟอเรนซ์ร่วม
ซึ่งทำให้มันไม่เปลี่ยนแปลงได้!

อย่างไรก็ตามมีชนิดพิเศษที่ละเมิดคุณสมบัติเหล่านี้: พวกที่มี
*มิวเทบิลิตี้ภายใน (interior mutability)* จนถึงตอนนี้เราได้โต้ตอบแค่กับ
*มิวเทบิลิตี้ที่สืบทอดมา (inherited mutability)* (หรือมิวเทบิลิตี้ภายนอก):
มิวเทบิลิตี้ของค่าถูกสืบทอดจากมิวเทบิลิตี้ของตัวมันเอง นั่นคือคุณไม่สามารถ
กลายพันธุ์ฟิลด์บางอย่างของค่าที่ไม่เปลี่ยนแปลงได้เพราะคุณรู้สึกอยากทำ

ชนิดมิวเทบิลิตี้ภายในละเมิดสิ่งนี้: มันให้คุณกลายพันธุ์ผ่านเรเฟอเรนซ์ร่วม
มีสองคลาสหลักของมิวเทบิลิตี้ภายใน: เซลล์ ซึ่งทำงานเฉพาะในบริบทเธรดเดียว;
และล็อก ซึ่งทำงานในบริบทหลายเธรด ด้วยเหตุผลที่ชัดเจน เซลล์ถูกกว่าเมื่อ
คุณใช้มันได้ ยังมี atomic ซึ่งเป็นพรีมิทีฟที่ทำตัวเหมือนล็อก

แล้วทั้งหมดนี้เกี่ยวอะไรกับ Rc และ Arc? ทั้งคู่ใช้มิวเทบิลิตี้ภายใน
สำหรับ*จำนวนอ้างอิง*ของมัน แย่กว่านั้น จำนวนอ้างอิงนี้เป็นร่วมกัน
ระหว่างทุกอินสแตนซ์! Rc ใช้แค่เซลล์ ซึ่งหมายความว่ามันไม่ปลอดภัยต่อเธรด
Arc ใช้ atomic ซึ่งหมายความว่ามัน*ปลอดภัยต่อเธรด* แน่นอนว่าคุณไม่สามารถ
ทำให้ชนิดปลอดภัยต่อเธรดได้อย่างมหัศจรรย์โดยใส่ไว้ใน Arc Arc สามารถ
สืบทอดความปลอดภัยต่อเธรดได้เหมือนชนิดอื่น ๆ

ผมไม่อยากลงลึกในรายละเอียดของโมเดลหน่วยความจำแบบอะตอมิก
หรือการ implement Send ที่ไม่ได้สืบทอด ไม่ต้องพูดถึงว่าเมื่อคุณลึกเข้าไป
ในเรื่องราวความปลอดภัยต่อเธรดของ Rust ของจะซับซ้อนขึ้นในฐานะ
ผู้บริโภคระดับสูง มันทั้งหมด*ใช้ได้เลย*และคุณไม่ต้องคิดมากเกี่ยวกับมัน
