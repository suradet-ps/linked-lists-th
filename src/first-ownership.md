# ความเป็นเจ้าของ 101

ตอนนี้เราสร้างลิสต์ได้แล้ว มันคงจะดีถ้าเราสามารถ*ทำอะไรสักอย่าง*กับมันได้
เราทำแบบนั้นด้วยเมธอด "ปกติ" (แบบไม่ใช่สแตติก) เมธอดคือกรณีพิเศษของฟังก์ชัน
ใน Rust เพราะอาร์กิวเมนต์ `self` ที่ไม่มีชนิดประกาศไว้:

```rust ,ignore
fn foo(self, arg2: Type2) -> ReturnType {
    // body
}
```

มีรูปแบบหลัก 3 แบบที่ self รับได้: `self`, `&mut self`, และ `&self`
สามรูปแบบนี้แทนรูปแบบหลักสามแบบของความเป็นเจ้าของใน Rust:

* `self` - ค่า (value)
* `&mut self` - เรเฟอเรนซ์ที่เปลี่ยนแปลงได้ (mutable reference)
* `&self` - เรเฟอเรนซ์ร่วม (shared reference)

ค่าหมายถึงความเป็นเจ้าของ*ที่แท้จริง* คุณสามารถทำอะไรก็ได้กับค่า: ย้ายมัน
ทำลายมัน กลายพันธุ์มัน หรือให้ยืมมันผ่านเรเฟอเรนซ์ เมื่อคุณส่งอะไรด้วยค่า
มันจะถูก*ย้าย*ไปยังตำแหน่งใหม่ ตำแหน่งใหม่เป็นเจ้าของค่านั้นแล้ว และตำแหน่งเก่า
ไม่สามารถเข้าถึงมันได้อีกต่อไป ด้วยเหตุนี้เมธอดส่วนใหญ่จึงไม่ต้องการ `self` --
มันคงแย่มากถ้าการลองใช้งานลิสต์ทำให้มันหายไป!

เรเฟอเรนซ์ที่เปลี่ยนแปลงได้แทนการ*เข้าถึงแบบเอกสิทธิ์ (exclusive access)*
ชั่วคราวต่อค่าที่คุณไม่ได้เป็นเจ้าของ คุณได้รับอนุญาตให้ทำอะไรก็ตามที่ต้องการ
กับค่าที่คุณมีเรเฟอเรนซ์ที่เปลี่ยนแปลงได้ ตราบใดที่คุณปล่อยให้มันอยู่ในสถานะที่ถูกต้อง
เมื่อทำเสร็จ (ไม่อย่างนั้นมันจะหยาบคายต่อเจ้าของเดิม!). นี่หมายความว่าคุณสามารถ
เขียนทับค่าทั้งหมดได้เลยจริง ๆ กรณีพิเศษที่มีประโยชน์มากคือการ*สวอป*ค่าออก
เป็นอีกค่าหนึ่ง ซึ่งเราจะใช้บ่อยมาก สิ่งเดียวที่คุณทำไม่ได้กับ `&mut` คือการย้ายค่า
ออกไปโดยไม่แทนที่ด้วยอะไร `&mut self` เหมาะมากสำหรับเมธอดที่ต้องการกลายพันธุ์ `self`

เรเฟอเรนซ์ร่วมแทนการ*เข้าถึงร่วม (shared access)* ชั่วคราวต่อค่าที่คุณไม่ได้เป็นเจ้าของ
เพราะคุณมีการเข้าถึงร่วม คุณโดยทั่วไปจึงไม่ได้รับอนุญาตให้กลายพันธุ์อะไร
คิดว่า `&` เป็นการนำค่าออกจัดแสดงในพิพิธภัณฑ์ `&` เหมาะมากสำหรับเมธอดที่
แค่อยากสังเกต `self`

ต่อมาเราจะเห็นว่ากฎเกี่ยวกับการกลายพันธุ์สามารถเลี่ยงได้ในบางกรณี
นี่คือเหตุผลที่เรเฟอเรนซ์ร่วมไม่ได้ถูกเรียกว่าเรเฟอเรนซ์*แบบอิมมิวเทเบิล*
จริง ๆ แล้วเรเฟอเรนซ์ที่เปลี่ยนแปลงได้อาจเรียกว่าเรเฟอเรนซ์*แบบยูนีก (unique)*
แต่เราพบว่าการเชื่อมโยงความเป็นเจ้ากับการกลายพันธุ์ให้สัญชาตญาณที่ถูกต้อง 99% ของเวลา
