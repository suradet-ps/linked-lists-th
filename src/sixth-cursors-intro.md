# บทนำสู่เคอร์เซอร์

โอเคครับบบบ!!! ตอนนี้เรามี `LinkedList` ที่มีฟีเจอร์เทียบเท่ากับ standard library เวอร์ชัน 1.0 แล้ว! ซึ่งแน่นอนว่ามันแปลว่า `LinkedList` ของเรายังคง *ไร้ประโยชน์สิ้นดีอยู่เหมือนเดิม* เรายอมแบกรับความเสียหายด้านประสิทธิภาพมหาศาลจากการอิมพลีเมนต์ Deque ด้วย linked list **แต่เรากลับยังไม่มี API ที่ดึงเอาพลังที่แท้จริงของมันออกมาใช้ได้เลย**

นี่คือสถานะของเราเมื่อเทียบกับฟีเจอร์เด็ด ("killer app") ของบรรดา linked list ทั้งหลาย:

* 🚫 ทำ [ลูกเล่นพิลึกพิลั่น](https://docs.rs/linked-hash-map/latest/linked_hash_map/) ได้
* 🚫 ทำ [ของแผลง ๆ แบบ lock-free](https://doc.rust-lang.org/std/sync/mpsc/) ได้
* 🚫 จัดเก็บ [Dynamically Sized Types (DST)](https://doc.rust-lang.org/nomicon/exotic-sizes.html#dynamically-sized-types-dsts) ได้
* 🌟 push/pop ได้ใน O(1) โดยไม่ต้องพึ่ง [amortization (การเฉลี่ยต้นทุน)](https://en.wikipedia.org/wiki/Amortized_analysis) (ถ้าคุณยอมหลับหูหลับตาเชื่อว่า `malloc` เป็น O(1) นะ)
* 🚫 สปลิต (split) แยกกิ่งลิสต์ได้ใน O(1)
* 🚫 สไปลซ์ (splice) เชื่อมต่อลิสต์ได้ใน O(1)

ก็นะ... ได้ 1 จากทั้งหมด 6 ข้อ... ก็ยังดีกว่าไม่ได้เลยสักข้อแหละมั้ง! พอจะมองออกหรือยังล่ะครับว่าทำไมผมถึงอยากถีบส่งไอ้ลิสต์ตัวนี้ออกจาก standard library ให้พ้น ๆ นัก?

เราคงไม่มานั่งทำให้ลิสต์ของเรารองรับ "ลูกเล่นพิลึกพิลั่น" พวกนั้นหรอกครับ เพราะของพรรค์นั้นมันเฉพาะทางและขึ้นกับโดเมนเกินไป แต่เรื่อง splitting กับ splicing เนี่ยสิ คือสิ่งที่เราพอจะทำได้!

ทว่าปัญหาก็คือ จริง ๆ แล้วการ *เข้าถึง* สมาชิกตัวที่ $k$ ใน `LinkedList` มันกินเวลา $O(k)$ แล้วเราจะ *มีปัญญา* ทำการ split และ merge ตรงจุดไหนก็ได้ใน $O(1)$ ได้ยังไงกันล่ะ? เคล็ดลับก็คือ คุณอย่าไปทำ API แบบ `split_at(index)` สิครับ — คุณต้องสร้างระบบที่ยอมให้ผู้ใช้สามารถวนลูป (iterate) แบบจำสถานะ (statefully) เข้าไปยังตำแหน่งใดตำแหน่งหนึ่งในลิสต์ แล้วสั่งแก้ไขเปลี่ยนแปลงด้วยความเร็ว $O(1)$ ณ จุดนั้นได้เลยต่างหาก!

เฮ้ย เรามี iterator อยู่แล้วนี่หว่า! เอามาใช้ไม่ได้เหรอ? ก็นะ... ได้แค่บางส่วนครับ เพราะพลังวิเศษ ("super-power") อย่างหนึ่งของมันดันมาขวางทางเราอยู่ คุณอาจจะจำได้ว่าการผูก lifetime สำหรับ iterator แบบ by-ref หมายความว่า reference ที่มันส่งกลับคืนมานั้น *ไม่ได้* ถูกยึดโยงอยู่กับตัว iterator เอง ทำให้เราสามารถเรียก `next` รัว ๆ แล้วเก็บค่า element หลายตัวเอาไว้พร้อมกันได้:

```rust ,ignore
let mut list = ...;
let iter = list.iter_mut();
let elem1 = list.next();
let elem2 = list.next();

if elem1 == elem2 { ... }
```

หาก reference ที่คืนมานั้นไปยืม (borrow) ตัว iterator ไว้ โค้ดชุดนี้จะไม่มีทางทำงานได้เลย คอมไพเลอร์จะก่นด่าตอนที่เราเรียก `next` ครั้งที่สองแน่นอน! ความยืดหยุ่นตรงนี้มันยอดเยี่ยมมากก็จริง แต่มันก็แอบสร้างข้อจำกัดโดยนัยให้กับเรา:

* Iterator แบบ By-Mutable-Ref จะไม่มีวันถอยหลังกลับไป yield สมาชิกตัวเดิมซ้ำได้เด็ดขาด เพราะไม่งั้นผู้ใช้จะถือ `&mut` สองตัวชี้ไปยังสมาชิกตัวเดียวกันพร้อมกัน ซึ่งผิดกฎพื้นฐานระดับจักรวาลของ Rust ทันที

* Iterator แบบ By-Ref ไม่สามารถมีเมธอดเสริมที่อาจเข้าไปดัดแปลงคอลเลกชันที่อยู่เบื้องล่าง ในลักษณะที่อาจทำให้ reference ที่เคย yield ออกไปแล้วกลายเป็นโมฆะ (invalidate) ได้

น่าเสียดายที่ทั้งสองข้อนี้ดันเป็น *สิ่งที่ตรงข้าม* กับสิ่งที่เราอยากให้ API ของ LinkedList ทำได้พอดิบพอดี! ดังนั้นเราจึงไม่สามารถใช้แค่ iterator ธรรมดาได้ เราต้องการของเล่นชิ้นใหม่: นั่นคือ *Cursor (เคอร์เซอร์)* ครับ

เคอร์เซอร์ก็ทำงานเหมือนกับขีดกระพริบ `|` เล็ก ๆ เวลาคุณพิมพ์งานบนคอมพิวเตอร์นั่นแหละครับ มันคือตำแหน่งในลำดับข้อมูล (ข้อความ) ที่คุณสามารถเลื่อนไปมาได้ (ด้วยปุ่มลูกศร) และเมื่อใดก็ตามที่คุณพิมพ์ การแก้ไขก็จะเกิดขึ้นตรงจุดนั้นทันที

ขอโทษที คุณกำลังยืนอยู่ข้างหลังผมแล้วแอบดูผมพิมพ์อยู่ใช่ไหมล่ะ? ถ้าใช่ มันก็ฟังดูสมเหตุสมผลสุด ๆ เลยใช่ไหมล่ะครับ? ถูกต้องแล้ว

คราวนี้ ถ้าคุณเคยซวยใช้คีย์บอร์ดที่มีปุ่ม "insert" แล้วเผลอไปกดมันเข้า คุณคงจะรู้ว่าในทางเทคนิคแล้ว เคอร์เซอร์มีการตีความได้สองแบบ: มันอาจจะวางตัวอยู่ *ระหว่าง* สมาชิก (ตัวอักษร) หรือไม่ก็วางตัวทับอยู่ *บน* สมาชิกตัวนั้นไปเลย ผมค่อนข้างมั่นใจว่าในชีวิตนี้ไม่เคยมีมนุษย์คนไหนตั้งใจกดปุ่ม "insert" แน่ ๆ และมันมีอยู่เพื่อเป็น "ปุ่มแห่งความทุกข์ทรมาน" ล้วน ๆ ดังนั้นมันจึงชัดเจนแจ่มแจ้งว่าแบบไหนที่ดีกว่าและถูกต้อง: เคอร์เซอร์ต้องอยู่ระหว่างสมาชิกสิครับ!

เป็นตรรกะที่แน่นปึ้กไร้รอยต่อจริง ๆ ผมคิดว่าคงไม่มีใครหน้าไหนกล้าเถียงผมได้หรอก

เอ๊ะ อะไรนะ? เคยมี [RFC ในปี 2018 เพื่อขอเพิ่ม Cursor ให้กับ LinkedList ของ Rust](https://github.com/rust-lang/rfcs/blob/master/text/2570-linked-list-cursors.md) งั้นเหรอ?

> With a Cursor one can seek back and forth through a list and get the current element. With a CursorMut One can seek back and forth and get mutable references to elements, and it can insert and delete elements before and behind the current element (along with performing several list operations such as splitting and splicing).

*Current element* (สมาชิกปัจจุบัน) เรอะ? เคอร์เซอร์ตัวนี้ดันไปอยู่ *บน* สมาชิก ไม่ได้อยู่ระหว่างสมาชิกเนี่ยนะ! ไม่อยากจะเชื่อเลยว่าพวกเขาไม่ยอมรับข้อโต้แย้งอันแน่นปึ้กของผม! แต่ช่างเถอะ คุณจะแวบไปใช้ Cursor ใน std ก็ได้นะ... เดี๋ยวนะ นี่มัน [ปี 2022 แล้ว แต่ Rust 1.60 ก็ยังมาร์ก Cursor เป็น unstable ไว้อยู่เลยเรอะ](https://doc.rust-lang.org/1.60.0/std/collections/linked_list/struct.CursorMut.html)?

เฮ้ย ช้าก่อน:

> Cursors always rest between two elements in the list, and index in a logically circular way. To accommodate this, there is a "ghost" non-element that yields None between the head and tail of the list.

เฮ้ยยยยย เดี๋ยวสิเว้ย นี่มันตรงกันข้ามกับที่เขียนไว้ใน RFC เลยไม่ใช่เหรอ??? แต่ช้าก่อน ทำไม doc ของแต่ละเมธอดถึงยังคงอ้างถึงสมาชิก "current" อยู่ล่ะ... เดี๋ยวนะ ไอ้เรื่องโหนดผี (ghost) นี่ผมเคยเห็นที่ไหนมาก่อนนะ อ้าวเฮ้ย นั่นมันสิ่งที่ผมเขียนไว้ใน [โปรเจกต์ fork linked-list เก่าของผม](https://docs.rs/linked-list/0.0.3/linked_list/struct.Cursor.html) ที่ผมทำต้นแบบ (prototype) ไว้เองไม่ใช่เรอะ?

> Cursors always rest between two elements in the list, and index in a logically circular way. To accomadate this, there is a "ghost" non-element that yields None between the head and tail of the List.

เดี๋ยว ๆๆๆ นี่มันเชี่ยอะไรกันวะเนี่ย นี่ไม่ได้เล่นมุกนะเว้ย ผมกำลังนั่ง Read The Docs ของจริงอยู่เนี่ย std อุตส่าห์ทำ RFC ด้วยดีไซน์ที่ต่างจากที่ผมเคยเสนอไว้ในปี 2015 แต่ดันไปก็อปปี้แปะข้อความ doc จากตัว prototype ของผมมาเนี่ยนะ??? นี่พวกใน std กำลังเล่นมุก meta-shitpost ปั่นประสาทผม โทษฐานที่ผมเขียนหนังสือด่าความห่วยของ LinkedList งั้นเรอะ????? คือใช่ ผมเขียน prototype ตัวนั้นขึ้นมาเพื่อสาธิตแนวคิด เพื่อหวังให้คนยอมให้ผมเพิ่มมันเข้าไปใน std จะได้ทำให้ LinkedList เลิกไร้ประโยชน์สักที แต่... qu'est-ce que le fuck?????????????? (อิหยังวะภาษาฝรั่งเศส)

โอเค ช่างแม่ง ชัดเจนแล้วว่า std กำลังอวยพรให้ดีไซน์ของผมเหนือชั้นกว่าอย่างเป็นรูปธรรม ดังนั้นเราจะทำตามดีไซน์ของผมครับ! แถมมันยังดีตรงที่ ทั้งบทนี้คือการที่ผมมานั่งเขียนไลบรารีตัวนั้นใหม่อีกรอบจริง ๆ จากศูนย์ ดังนั้นการที่ไม่ต้องเปลี่ยน API ก็ถือว่าเข้าทางผมเลย!

นี่คือ top-level docs ที่ผมเขียนทั้งหมด:

> A Cursor is like an iterator, except that it can freely seek back-and-forth, and can safely mutate the list during iteration. This is because the lifetime of its yielded references are tied to its own lifetime, instead of just the underlying list. This means cursors cannot yield multiple elements at once.
>
> Cursors always rest between two elements in the list, and index in a logically circular way. To accomadate this, there is a "ghost" non-element that yields None between the head and tail of the List.
>
> When created, cursors start between the ghost and the front of the list. That is, next will yield the front of the list, and prev will yield None. Calling prev again will yield the tail.

น่ารักดีนะ ถึงแม้ก่อนหน้านี้เราจะได้ข้อสรุปว่าไอ้เรื่อง "sentinel node" มันสร้างความปวดกบาลมากกว่าประโยชน์ แต่สุดท้ายเราก็ยังต้องมาลงเอยด้วยความหมายทางพฤติกรรม (semantics) ที่ "แกล้งทำเป็น" มี sentinel node อยู่ดี เพื่อให้ตัวเคอร์เซอร์สามารถวนรอบ (wrap around) ข้ามไปยังอีกฝั่งหนึ่งของลิสต์ได้

*นั่งกวาดตาดู API เก่าของตัวเองต่ออีกนิด*

```rust ,ignore
fn splice(&mut self, other: &mut LinkedList<T>)
```

> Inserts the entire list's contents right after the cursor.

อ้อ ใช่ ความทรงจำเริ่มย้อนกลับมาละ ผมเขียนเมธอดนี้ขึ้นมาตอนที่กำลังหัวร้อนกับปัญหาเรื่อง combinatoric explosion สุด ๆ และพยายามเค้นหาวิธีที่จะให้มีสำเนาของแต่ละการดำเนินการเพียงชุดเดียว น่าเสียดายที่วิธีนี้... มีปัญหาทางความหมายอย่างจัง ลองนึกภาพดูสิครับ เมื่อผู้ใช้ต้องการสไปลซ์ลิสต์หนึ่งเข้าไปในอีกลิสต์หนึ่ง พวกเขาอาจจะต้องการให้เคอร์เซอร์ไปหยุดอยู่ *ข้างหน้า* ส่วนที่แทรกเข้าไป หรือ *ข้างหลัง* มันก็ได้ แล้วลิสต์ที่แทรกเข้ามาก็อาจยาวเป็นล้านตัว ดังนั้นการที่เราบังคับให้เลือกได้แค่ทางเดียว แล้วหวังให้ผู้ใช้เดินลุยข้ามลิสต์ทั้งหมดที่เพิ่งแทรกเข้ามาจึงเป็นปัญหาใหญ่แน่นอน!

ดูท่าเราคงต้องรื้อดีไซน์นี้ใหม่ตั้งแต่รากฐานจริง ๆ เสียแล้ว สิ่งที่ type `Cursor` ของเราต้องการมีอะไรบ้างล่ะ? มันจำเป็นต้อง:

* ชี้ "ระหว่าง" สมาชิกสองตัว
* มีฟีเจอร์เล็ก ๆ น่ารักคอยติดตามว่า "index" ถัดไปคืออะไร
* อัปเดตตัวลิสต์เองเพื่อปรับเปลี่ยน `front`, `back`, และ `len`

แล้วคุณจะชี้ไปที่ช่องว่างระหว่างสมาชิกสองตัวได้ยังไง? คำตอบคือ ทำไม่ได้หรอกครับ คุณก็แค่ชี้ไปที่สมาชิกตัว "ถัดไป" (next) นั่นแหละ ดังนั้น ใช่ครับ แม้ภายนอกเราจะเปิดเผยพฤติกรรมว่า "เคอร์เซอร์แทรกตัวอยู่ตรงกลาง" แต่จริง ๆ ภายในเราอิมพลีเมนต์แบบ "เคอร์เซอร์เกาะอยู่บนโหนด" แล้วแกล้งทำเนียนว่าทุกอย่างเกิดขึ้นก่อนหน้าหรือหลังจากจุดนั้นต่างหาก

แต่มันมีเหตุผลอยู่นะ! การใช้งานแบบ splice อยากให้ผู้ใช้เลือกได้ว่าจะให้เคอร์เซอร์ไปหยุดอยู่ข้างหน้าหรือข้างหลังลิสต์ แต่นี่มัน... อธิบายด้วย API ของ `std` ได้ซับซ้อน *บรรลัย* มาก! พวกเขามี `splice_after` กับ `splice_before` แต่ไม่มีตัวไหนยอมเปลี่ยนตำแหน่งของเคอร์เซอร์เลย ดังนั้นจริง ๆ คุณต้องมี `splice_after_before` กับ `splice_after_after` งั้นเรอะ...

เดี๋ยวนะ ไม่สิ ผมกำลังคิดฟุ้งซ่านไปเอง ใน API ของ `std` คุณแค่เลือกโหนดที่คุณอยากให้เคอร์เซอร์ไปหยุดอยู่ แล้วค่อยเรียกใช้ `splice_after` หรือ `splice_before` ตามความเหมาะสมก็สิ้นเรื่องแล้วนี่หว่า

*หรี่ตามอง*

เดี๋ยวนะ หรือว่าจริง ๆ แล้ว API ของ std มันออกแบบมาดีวะ

*กวาดตาไล่ดูโค้ด*

โอเค API ของ std มันออกแบบมาดีจริง ๆ ด้วยว่ะ

เอาวะ ช่างหัวมัน! เราจะ [อิมพลีเมนต์ตาม RFC](https://github.com/rust-lang/rfcs/blob/master/text/2570-linked-list-cursors.md) ไปเลย หรืออย่างน้อยก็เก็บส่วนที่น่าสนใจของมันมาทำ

ถึงผมจะมีข้อกังขาเรื่องคำศัพท์บางคำที่ `std` เลือกใช้ก็เถอะ แต่เรื่องเคอร์เซอร์เนี่ยมันชวนให้สมองละลายได้ตลอดเวลาจริง ๆ นะ: การเรียก `iter().next_back()` จะพาคุณไปหา `back()` ซึ่งก็ฟังดูดี แต่พอเรียก `next_back()` ครั้งถัด ๆ ไป มันกลับพาคุณ *ขยับเข้าใกล้ฝั่งด้านหน้า (front) มากขึ้นเรื่อย ๆ* และจริง ๆ แล้ว พอยน์เตอร์ทุกตัวที่เราวิ่งตามไปก็คือพอยน์เตอร์ฝั่ง "front" เสียด้วยซ้ำ! ถ้าผมคิดถึงความย้อนแย้งที่ดูขัดหูขัดตานี้มากไป สมองผมคงระเบิดแน่ ๆ ดังนั้นผมจึงยอมรับได้ที่พวกเขาเลือกใช้คำศัพท์ที่ต่างออกไปเพื่อเลี่ยงความสับสนนี้

โดย API ของ `std` จะพูดถึงการดำเนินการที่ทำ "before" (มุ่งหน้าไปทาง front) และ "after" (มุ่งหน้าไปทาง back) และแทนที่จะใช้คำว่า `next` กับ `next_back` มันกลับ... ตั้งชื่อว่า `move_next` กับ `move_prev` ซะงั้น อืมมม โอเค พวกเขาแอบเอาคำศัพท์ฝั่ง iterator มาปนบ้าง แต่อย่างน้อยคำว่า `next` ก็ไม่ได้ชวนให้นึกถึง front/back ตรง ๆ และช่วยให้คุณพอนึกภาพออกว่ามันมีพฤติกรรมเทียบเคียงกับ iterator ยังไง
