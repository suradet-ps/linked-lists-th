# IterMut

พูดตามตรงเลยนะ `IterMut` นี่มันโคตรจะหลุดโลก! ซึ่งฟังดูอาจจะแปลกพิลึกที่จะพูดแบบนั้น เพราะใคร ๆ ก็คงคิดว่ามันก็น่าจะเหมือนกับ `Iter` เด๊ะ ๆ ไม่ใช่เหรอ!

ในแง่ของความหมาย (semantics) แล้ว ก็ใช่ครับ... แต่ด้วยธรรมชาติอันแตกต่างระหว่างเรเฟอเรนซ์แบบแชร์ (shared reference) กับเรเฟอเรนซ์ที่แก้ไขได้ (mutable reference) มันทำให้ `Iter` กลายเป็นเรื่อง "เด็ก ๆ เบเบ" ไปเลย ในขณะที่ `IterMut` คือ "ศาสตร์เวทมนตร์ขั้นสูงของพ่อมดตัวจริงเสียงจริง" ต่างหากล่ะ

กุญแจสำคัญของเรื่องนี้มาจากโค้ดที่เรา implement `Iterator` ให้กับ `Iter` ในบทก่อน:

```rust ,ignore
impl<'a, T> Iterator for Iter<'a, T> {
    type Item = &'a T;

    fn next(&mut self) -> Option<Self::Item> { /* stuff */ }
}
```

ซึ่งเมื่อถอดรูปย่อไวยากรณ์ (desugar) ออกมาแล้ว จะเทียบเท่ากับโค้ดนี้:

```rust ,ignore
impl<'a, T> Iterator for Iter<'a, T> {
    type Item = &'a T;

    fn next<'b>(&'b mut self) -> Option<&'a T> { /* stuff */ }
}
```

สังเกตไหมครับว่า ลายเซ็นของ `next` *ไม่ได้มีข้อผูกมัดหรือเงื่อนไขใด ๆ เลย* ระหว่างไลฟ์ไทม์ของอินพุต (`'b`) กับไลฟ์ไทม์ของเอาต์พุต (`'a`)! แล้วทำไมเราถึงต้องสนใจเรื่องนี้ด้วยล่ะ? ก็เพราะมันหมายความว่า เราสามารถเรียกเมธอด `next` รัว ๆ ซ้ำแล้วซ้ำเล่าได้อย่างอิสระเสรียังไงล่ะ!:

```rust ,ignore
let mut list = List::new();
list.push(1); list.push(2); list.push(3);

let mut iter = list.iter();
let x = iter.next().unwrap();
let y = iter.next().unwrap();
let z = iter.next().unwrap();
```

เจ๋งเป้ง!

พฤติกรรมแบบนี้ *ไม่มีปัญหาอะไรแน่นอน* สำหรับเรเฟอเรนซ์แบบแชร์ (`&`) เพราะหัวใจสำคัญของมันคือคุณจะมีเรเฟอเรนซ์แบบนี้กี่ร้อยกี่พันตัวพร้อมกันในเวลาเดียวกันก็ได้ ทว่า เรเฟอเรนซ์ที่แก้ไขได้ (`&mut`) *ไม่สามารถอยู่ร่วมกันได้* เพราะหัวใจของมันคือต้องเป็นสิทธิ์ขาดแต่เพียงผู้เดียว (exclusive) เท่านั้น

ผลลัพธ์ก็คือ มันจะยากขึ้นกว่าเดิมอย่างเห็นได้ชัดเวลาที่เราต้องเขียน `IterMut` ด้วยโค้ดแบบปลอดภัย (safe Rust) (ซึ่งเรายังไม่ได้พูดถึงเลยด้วยซ้ำว่าคำนี้จริง ๆ หมายความว่าอะไร...) แต่น่าประหลาดใจมากที่ในหลาย ๆ โครงสร้างข้อมูล `IterMut` สามารถเขียนขึ้นมาได้อย่างปลอดภัย 100% โดยไม่ต้องพึ่ง unsafe เลย!

งั้นเรามาเริ่มต้นด้วยการเอาโค้ดของ `Iter` มาแปลงทุกจุดให้กลายเป็นแบบ mutable กันก่อนเลย:

```rust ,ignore
pub struct IterMut<'a, T> {
    next: Option<&'a mut Node<T>>,
}

impl<T> List<T> {
    pub fn iter_mut(&self) -> IterMut<'_, T> {
        IterMut { next: self.head.as_deref_mut() }
    }
}

impl<'a, T> Iterator for IterMut<'a, T> {
    type Item = &'a mut T;

    fn next(&mut self) -> Option<Self::Item> {
        self.next.map(|node| {
            self.next = node.next.as_deref_mut();
            &mut node.elem
        })
    }
}
```

โอเค ดูเหมือนเราจะเจอ error สองจุดที่แตกต่างกัน ข้อผิดพลาดแรกดูชัดเจนแจ่มแจ้งมาก แถมคอมไพเลอร์ยังบอกวิธีแก้มาให้เสร็จสรรพ: คุณไม่สามารถอัปเกรดเรเฟอเรนซ์แบบแชร์ให้อยู่ดี ๆ กลายเป็นเรเฟอเรนซ์ที่แก้ไขได้เฉย ๆ ได้ ดังนั้น `iter_mut` จึงจำเป็นต้องรับพารามิเตอร์เป็น `&mut self` นั่นเอง เรื่องนี้แค่ความผิดพลาดจากการก็อปแปะเฉย ๆ:

```rust ,ignore
pub fn iter_mut(&mut self) -> IterMut<'_, T> {
    IterMut { next: self.head.as_deref_mut() }
}
```

แล้วอีก error หนึ่งล่ะ เกิดจากอะไร?

อุ๊ปส์! เอาจริง ๆ ตอนที่ผมเขียนโค้ด `iter` ในบทที่แล้ว ผมแอบทำผิดพลาดไปจุดหนึ่งโดยไม่ได้ตั้งใจ และที่เราผ่านมันมาได้ก็เพราะโชคช่วยล้วน ๆ เลยครับ!

เพราะเราเพิ่งจะได้เจอกับเวทมนตร์ของเทรต `Copy` เข้าให้แล้ว ในตอนที่เราเริ่มพูดถึงเรื่อง [ความเป็นเจ้าของ (ownership)][ownership] เราบอกว่าเมื่อคุณย้าย (move) ข้อมูลออกไป คุณจะไม่สามารถใช้งานข้อมูลนั้นได้อีกต่อไป สำหรับชนิดข้อมูลบางประเภท กฎนี้สมเหตุสมผลสุด ๆ เพื่อนยากอย่าง `Box` คอยจัดการหน่วยความจำบนฮีปให้เรา และเราคงไม่อยากให้โค้ดสองจุดแย่งกันสั่งคืนหน่วยความจำ (deallocate) ก้อนเดียวกันแน่นอน

ทว่า สำหรับชนิดข้อมูลบางชนิด กฎนี้กลับดู *งี่เง่าไร้สาระ* มาก ตัวเลขอินทิเจอร์ไม่ได้มีกรรมสิทธิ์ความเป็นเจ้าของอะไรในหน่วยความจำเลย มันก็แค่ตัวเลขตัวหนึ่ง! ด้วยเหตุนี้ ตัวเลขอินทิเจอร์จึงถูกประทับตราไว้ว่าเป็น `Copy` โดยชนิดข้อมูลที่เป็น `Copy` จะสามารถคัดลอกตัวเองได้อย่างสมบูรณ์แบบด้วยการก็อปปี้ระดับบิต (bitwise copy) ส่งผลให้มันมีพลังวิเศษ: คือเมื่อถูกย้ายไปแล้ว ค่าเดิม *ก็ยังคง* สามารถนำมาใช้งานต่อได้ตามปกติ! และทำให้คุณสามารถย้ายชนิดข้อมูลที่เป็น `Copy` ออกมาจากเรเฟอเรนซ์ได้ทันทีโดยไม่ต้องหาอะไรมาใส่แทนที่ด้วยซ้ำ!

ชนิดข้อมูลพื้นฐานตัวเลขทุกชนิดใน Rust (`i32`, `u64`, `bool`, `f32`, `char` ฯลฯ) ล้วนเป็น `Copy` ทั้งสิ้น และคุณยังสามารถประกาศให้ชนิดข้อมูลที่คุณสร้างขึ้นเองเป็น `Copy` ได้ด้วยเช่นกัน ตราบใดที่ฟิลด์ประกอบทั้งหมดของมันเป็น `Copy`

และจุดสำคัญที่สุดที่ทำให้โค้ดบทก่อนของเราทำงานได้โดยไม่พังก็คือ: เรเฟอเรนซ์แบบแชร์ (`&`) ก็เป็น `Copy` ด้วยครับ! และเมื่อ `&` เป็น Copy ตัว `Option<&>` ก็พลอยได้เป็น `Copy` ตามไปด้วย! ดังนั้น ตอนที่เราสั่ง `self.next.map(...)` มันจึงทำงานได้สบาย ๆ เพราะตัว Option ถูกก็อปปี้สำเนาส่งเข้าไป แต่ตอนนี้เราทำแบบนั้นไม่ได้แล้ว เพราะ `&mut` *ไม่ได้เป็น Copy* (ถ้าคุณก็อปปี้ `&mut` ได้ คุณก็จะมี `&mut` สองตัวชี้ไปยังหน่วยความจำที่เดียวกันพร้อมกัน ซึ่งเป็นเรื่องต้องห้ามเด็ดขาด) ดังนั้น เราจึงต้องสั่ง `take()` ขโมยตัว `Option` ออกมาอย่างถูกต้องก่อน:

```rust ,ignore
fn next(&mut self) -> Option<Self::Item> {
    self.next.take().map(|node| {
        self.next = node.next.as_deref_mut();
        &mut node.elem
    })
}
```

คุณพระช่วย

มันเป็นไปได้ยังไงเนี่ย

โอเค คือจริง ๆ มันก็ *ควรจะ* ทำงานได้นั่นแหละ แต่มันมักจะมีเรื่องงี่เง่าคอยขัดแข้งขัดขาเราตลอดเวลาไง! ขอพูดให้เห็นภาพชัด ๆ ตรงนี้เลยนะ:

เราเพิ่งจะ implement โค้ดชิ้นหนึ่งที่รับซิงกลีลิงก์ลิสต์เข้ามา แล้วสามารถส่งคืนเรเฟอเรนซ์ที่แก้ไขได้ (`&mut`) ไปยังทุก ๆ องค์ประกอบในลิสต์ โดยการันตีว่าแต่ละตัวจะถูกส่งออกมาได้ **ไม่เกินหนึ่งครั้ง (at most once)** เสมอ แถมโค้ดนี้ยังได้รับการตรวจสอบยืนยันความถูกต้องในระดับคอมไพล์ (statically verified) ปลอดภัย 100% โดยที่เราไม่ต้องพึ่งท่าพิสดารหรือเขียนโค้ด unsafe เลยแม้แต่นิดเดียว!

นี่คือความสำเร็จที่ยิ่งใหญ่มากเลยนะครับถ้าคุณถามผม และเหตุผลที่กลไกนี้ทำงานได้มีอยู่ 2 ประการหลัก ๆ:

* เราใช้ `take()` กับ `Option<&mut>` ทำให้เราได้สิทธิ์การเข้าถึงเรเฟอเรนซ์ที่แก้ไขได้นั้นแต่เพียงผู้เดียว โดยไม่ต้องกลัวว่าจะมีใครแอบมองมันซ้อนอีก
* Rust ฉลาดพอที่จะเข้าใจว่า การแบ่งซอยเรเฟอเรนซ์ที่แก้ไขได้ (`&mut Node`) ออกเป็นชิ้นย่อย ๆ ตามฟิลด์ของ struct (`node.elem` และ `node.next`) นั้นปลอดภัย เพราะฟิลด์ทั้งสองแยกขาดจากกันโดยสิ้นเชิง (disjoint) และไม่มีทางที่จะมีใครวิ่งย้อนกลับขึ้นไปหาตัวแม่ได้

และที่ยอดเยี่ยมไปกว่านั้นก็คือ คุณสามารถนำลอจิกพื้นฐานตรงนี้ไปประยุกต์ใช้เพื่อสร้าง `IterMut` ที่ปลอดภัย 100% ให้กับโครงสร้างข้อมูลแบบอาร์เรย์หรือโครงสร้างทรี (Tree) ได้เช่นกัน! ยิ่งไปกว่านั้น คุณยังปรับแต่งให้อิเทอเรเตอร์นี้รองรับ `DoubleEndedIterator` เพื่อให้สามารถดึงข้อมูลออกมาจากทั้งด้านหน้า *และ* ด้านหลังพร้อม ๆ กันได้อีกด้วย! เจ๋งสุดยอดไปเลยใช่ไหมล่ะ!
