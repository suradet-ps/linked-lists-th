# พยายามทำความเข้าใจสแต็กด์บอร์โรวส์

ในส่วนก่อนหน้าเราได้ลองรันคิวแบบลิงก์ลิสต์เดี่ยวที่ไม่ปลอดภัยของเราภายใต้ miri และมันบอกว่าเราละเมิดกฎของ *สแต็กด์บอร์โรวส์* และลิงก์เราไปยังเอกสารประกอบ

ตามปกติฉันจะนำชมเอกสาร แต่เราไม่ใช่กลุ่มเป้าหมายจริงๆ ของเอกสารนั้น มันถูกออกแบบมาให้กับนักพัฒนาคอมไพเลอร์และนักวิชาการที่ทำงานเกี่ยวกับอรรถศาสตร์ของ Rust มากกว่า

ดังนั้นฉันจะให้ภาพรวมระดับสูงของ "สแต็กด์บอร์โรวส์" เท่านั้น แล้วจะให้กลยุทธ์ง่ายๆ ในการปฏิบัติตามกฎ

> **ผู้บรรยาย:** สแต็กด์บอร์โรวส์ยังคงเป็น "รุ่นทดลอง" ในฐานะโมเดลอรรถศาสตร์สำหรับ Rust ดังนั้นการละเมิดกฎเหล่านี้อาจไม่ได้หมายความว่าโปรแกรมของคุณ "ผิด" จริงๆ แต่เว้นแต่คุณจะทำงานกับคอมไพเลอร์จริงๆ คุณควรแก้ไขโปรแกรมของคุณเมื่อ miri ร้องเรียน ปลอดภัยดีกว่าเสียใจเมื่อพูดถึงพฤติกรรมที่ไม่กำหนด (Undefined Behaviour)



# เหตุผล: การแอลิเอสของตัวชี้

ก่อนที่เราจะเข้าสู่ *อะไร* ที่เราละเมิด จะช่วยให้เข้าใจ *ทำไม* กฎเหล่านี้ถึงมีอยู่ตั้งแต่แรก มีปัญหาที่กระตุ้นให้เกิดกฎหลายประการ แต่ฉันคิดว่าสิ่งที่สำคัญที่สุดคือ *การแอลิเอสของตัวชี้*

เราบอกว่าตัวชี้สองตัว *แอลิเอส* กันเมื่อชิ้นส่วนของหน่วยความจำที่มันชี้ไปทับซ้อนกัน เหมือนกับคนที่ "ใช้ชื่อเล่น" สามารถถูกเรียกโดยสองชื่อที่ต่างกัน ชิ้นส่วนหน่วยความจำที่ทับซ้อนกันนั้นสามารถถูกอ้างถึงโดยตัวชี้สองตัวที่ต่างกัน ซึ่งอาจนำไปสู่ปัญหาได้

คอมไพเลอร์ใช้ข้อมูลเกี่ยวกับการแอลิเอสของตัวชี้เพื่อเพิ่มประสิทธิภาพการเข้าถึงหน่วยความจำ ดังนั้นหากข้อมูลที่มี *ผิด* โปรแกรมจะถูกคอมไพล์ผิดและทำงานแบบสุ่ม

> **ผู้บรรยาย:** ในทางปฏิบัติ การแอลิเอสให้ความสำคัญกับการเข้าถึงหน่วยความจำมากกว่าตัวชี้เอง และมีความสำคัญเฉพาะเมื่อการเข้าถึงอย่างใดอย่างหนึ่งกำลังเปลี่ยนแปลงข้อมูล ตัวชี้ถูกเน้นเพราะเป็นสิ่งที่สะดวกในการเชื่อมกฎเข้าด้วยกัน

เพื่อทำความเข้าใจว่าทำไมข้อมูลการแอลิเอสของตัวชี้ถึงมีความสำคัญ ให้เราพิจารณา *อุปมาของชายตัวเล็กขี้โมโห*

----

Michiel กำลังดูหนังสือในชั้นหนังสือของพวกเขาในวันหนึ่ง เมื่อพวกเขาเห็นหนังสือเล่มหนึ่งที่พวกเขาจำไม่ได้ พวกเขาหยิบมันออกจากชั้นหนังสือและดูหน้าปก

"โอ้ใช่ สำเนาเก่าของ *War and Peace* ของฉัน หนังสือที่ฉันอ่านแน่นอน ฉันชอบตอนที่มี Peace ทั้งหมด"

จู่ๆ ก็มีเสียงเคาะที่ประตู Michiel คืนหนังสือไปที่ชั้นแล้วเปิดประตู -- มันคือศัตรูสาบานของพวกเขา **Hamslaw** ขณะที่ Hamslaw เตรียมคำพูดที่ทำลายล้างเกี่ยวกับทักษะ codegolfing ที่ด้อยกว่าอย่างเห็นได้ชัดของ Michiel พวกเขารู้สึกว่ามีโอกาส:

"เฮ้ Hamslaw เคยอ่าน War and Peace ไหม?"

"เชอะ ไม่มีใคร *จริงๆ* อ่าน War and Peace หรอก"

"ก็ฉันอ่านนะ ดูนี่สิมันอยู่ในชั้นหนังสือของฉัน ซึ่ง *แน่นอน* ว่าฉันอ่านแล้ว"

Hamslaw ไม่เชื่อ ใบหน้าของเธอเปลี่ยนจากท่าทางโอ้อวดตามปกติเป็นหน้ากากเหล็กแห่งความโกรธและความมุ่งมั่น Hamslaw ผลัก Michiel ออกไปแล้วเดินเร็วไปที่ชั้นหนังสือ ดึงหนังสือออกจากที่พักด้วยความโกรธของ Valkyrie นับพัน เธอพลิกหนังสือเก่าแก่ในมือ และทันทีที่เห็นหน้าปกเธอก็เริ่มสั่น

Michiel เตรียมจะอวดความฉลาดที่เหนือชั้นอย่างเห็นได้ชัดของพวกเขา แต่ถูกขัดจังหวะด้วยเสียงหัวเราะทันทีของ Hamslaw

"นี่ไม่ใช่ War and Peace นี่คือ War and *Feet*!"

น้ำตาไหลลงมาบนใบหน้าของ Hamslaw นี่เป็นช่วงเวลาที่ยิ่งใหญ่ที่สุดในชีวิตของเธออย่างชัดเจน

"น-ไม่! ฉันเพิ่งดูมัน!"

พวกเขาหยิบหนังสือจาก Hamslaw มาดูหน้าปก แน่นอนว่าคำว่า "Peace" ถูกขูดออกและเปลี่ยนเป็น "Feet" Michiel รู้สึกอาย นี่เป็นช่วงเวลาที่เลวร้ายที่สุดในชีวิตของพวกเขาอย่างชัดเจน

พวกเขาคุกเข่าลงและจ้องมองชั้นหนังสืออย่างว่างเปล่า เรื่องนี้เกิดขึ้นได้อย่างไร? พวกเขาเพิ่งตรวจสอบหน้าปกเมื่อสักครู่!

แล้วพวกเขาก็เห็นการเคลื่อนไหวเล็กน้อยในชั้นหนังสือ มันเป็นชายตัวเล็ก ชายตัวเล็กที่มีหน้าตาโกรธที่สุดเท่าที่ Michiel เคยเห็น ชายตัวเล็กยักนิ้วให้ Michiel และพูดว่า "ไม่มีใครจะเชื่อเธอ" แล้วหายกลับไประหว่างหนังสือ

แผนของ Michiel *เคย* สมบูรณ์แบบ แต่พวกเขาลืมคำนึงถึงความเป็นไปได้ของชายตัวเล็กขี้โมโหที่มีปากกาเมจิกและต้องการทำลายล้าง พวกเขาคิดว่าพวกเขารู้ว่าหน้าปกหนังสือเขียนว่าอะไร และพวกเขาคิดว่าไม่มีใครสามารถเปลี่ยนมันได้ แต่โชคร้ายที่พวกเขาคิดผิด

Hamslaw กำลังทำนิตยสารเพื่อรำลึกถึงชัยชนะที่น่าทึ่งของเธอ &mdash; ชื่อเสียงของ Michiel ที่ร้านอินเทอร์เน็ตคาเฟ่ในท้องถิ่นจะไม่มีวันฟื้นตัว

----

ไม่มีใครอยากเป็นเหมือน Michiel แต่ก็ไม่มีใครอยากใช้ชีวิตด้วยความกลัวชายตัวเล็กขี้โมهوตลอดเวลาเช่นกัน เราต้องการรู้ว่าเมื่อไหร่ที่ชายตัวเล็กขี้โมโหจะเล่นตลกกับเรา เมื่อเขาทำ เขาจะระมัดระวังและหวาดระแวงเกี่ยวกับการตรวจสอบทุกอย่างก่อนใช้งาน แต่เมื่อชายตัวเล็กขี้โมโหหายไป เราต้องการที่จะจดจำสิ่งต่างๆ ได้

นั่นคือ (แบบง่ายมาก) แก่นของการแอลิเอสของตัวชี้: เมื่อไหร่ที่คอมไพเลอร์สามารถสมมติว่าปลอดภัยที่จะ "จดจำ" (แคช) ค่าแทนที่จะโหลดซ้ำแล้วซ้ำอีก? เพื่อที่จะรู้เรื่องนี้ คอมไพเลอร์จำเป็นต้องรู้ว่าเมื่อใดที่ *อาจ* มีชายตัวเล็กขี้โมโหกำลังเปลี่ยนแปลงหน่วยความจำข้างหลังคุณ

> **ผู้บรรยาย:** คอมไพเลอร์ยังใช้ข้อมูลนี้เพื่อแคชการจัดเก็บ ซึ่งหมายความว่ามันสามารถหลีกเลี่ยงการบันทึกสิ่งต่างๆ ลงในหน่วยความจำได้หากคิดว่าไม่มีใครสังเกตเห็น ในกรณีนี้ปัญหายังคงเป็นชายตัวเล็กขี้โมโห แต่พวกเขาเพียงแค่ต้องอ่านหน่วยความจำเพื่อให้เป็นปัญหาได้






# สแต็กด์บอร์โรวส์ที่ปลอดภัย

ตกลง ดังนั้นเราต้องการให้คอมไพเลอร์มีข้อมูลการแอลิเอสของตัวชี้ที่ดี ทำได้ไหม? ดูเหมือน Rust ถูก *ออกแบบ* มาเพื่อสิ่งนี้ เรเฟอเรนซ์ที่เปลี่ยนแปลงได้ไม่แอลิเอสกันตามนิยาม และถึงแม้เรเฟอเรนซ์ร่วม *จะ* แอลิเอสกันได้ แต่ไม่สามารถเปลี่ยนแปลงได้ สมบูรณ์แบบ! ส่งเลย!

นอกจากนั้นซับซ้อนกว่านั้น เราสามารถ "reborrow" ตัวชี้ที่เปลี่ยนแปลงได้แบบนี้:

```rust
let mut data = 10;
let ref1 = &mut data;
let ref2 = &mut *ref1;

*ref2 += 2;
*ref1 += 1;

println!("{}", data);
```

มันคอมไพล์และรันได้ดี เรื่องคืออะไร?

เราจะเห็นว่าเกิดอะไรขึ้นโดยการสลับการใช้งานทั้งสอง:

```rust ,ignore
let mut data = 10;
let ref1 = &mut data;
let ref2 = &mut *ref1;

// ORDER SWAPPED!
*ref1 += 1;
*ref2 += 2;

println!("{}", data);
```

```text
error[E0503]: cannot use `*ref1` because it was mutably borrowed
 --> src/main.rs:6:5
  |
4 |     let ref2 = &mut *ref1;
  |                ---------- borrow of `*ref1` occurs here
5 |     
6 |     *ref1 += 1;
  |     ^^^^^^^^^^ use of borrowed `*ref1`
7 |     *ref2 += 2;
  |     ---------- borrow later used here

For more information about this error, try `rustc --explain E0503`.
error: could not compile `playground` due to previous error
```

มันกลายเป็นข้อผิดพลาดของคอมไพเลอร์ทันที!

เมื่อเรา reborrow ตัวชี้ที่เปลี่ยนแปลงได้ ตัวชี้เดิมจะไม่สามารถใช้งานได้อีกจนกว่าผู้ยืมจะเสร็จสิ้นการใช้งาน (ไม่มีการใช้งานอีกต่อไป)

ในโค้ดที่ทำงานได้ มีการซ้อนทับอย่างดีของการใช้งาน เรา reborrow ตัวชี้ ใช้ตัวชี้ใหม่สักพัก แล้วหยุดใช้ก่อนที่จะใช้ตัวชี้เก่าอีกครั้ง ในโค้ดที่ *ไม่* ทำงาน สิ่งนี้ไม่เกิดขึ้น เราแค่สลับการใช้งานแบบสุ่ม

นี่คือวิธีที่เราสามารถมี reborrow ได้และยังมีข้อมูลการแอลิเอส: reborrow ทั้งหมดของเราซ้อนกันชัดเจน ดังนั้นเราสามารถพิจารณาว่ามีเพียงตัวเดียวเท่านั้นที่ "ยังใช้งานอยู่" ณ เวลาใดก็ตาม

เฮ้ รู้ไหมว่าวิธีที่ดีในการแสดงสิ่งที่ซ้อนกันอย่างเรียบร้อยคืออะไร? สแต็ก สแต็กของการยืม

โอ้ นี่มัน *สแต็กด์บอร์โรวส์*!

สิ่งที่อยู่ด้านบนของสแต็กยืมจะ "ยังใช้งานอยู่" และรู้ว่ามันไม่แอลิเอสโดยจริง เมื่อคุณ reborrow ตัวชี้ ตัวชี้ใหม่จะถูกผลักลงบนสแต็ก กลายเป็น *ตัว* ชี้ที่ยังใช้งานอยู่ เมื่อคุณใช้ตัวชี้ที่เก่ากว่ามันจะถูกนำกลับมาใช้งานอีกครั้งโดยการดึงทุกอย่างบนสแต็กยืมที่อยู่เหนือมันออก ณ จุดนี้ตัวชี้ "รู้" ว่ามันถูก reborrow และหน่วยความจำอาจถูกเปลี่ยนแปลง แต่มันมีสิทธิ์เข้าถึงแบบเอกสิทธิ์อีกครั้ง -- ไม่ต้องกังวลเกี่ยวกับชายตัวเล็กขี้โมโห

ดังนั้นจึง *ปลอดภัย* เสมอที่จะเข้าถึงตัวชี้ที่ถูก reborrow เพราะเราสามารถดึงทุกอย่างที่อยู่เหนือมันออกได้เสมอ ปัญหาจริงคือการเข้าถึงตัวชี้ที่ถูกดึงออกจากสแต็กยืมแล้ว -- นั่นหมายความว่าคุณทำพลาดแล้ว

โชคดีที่การออกแบบของบอร์โรว์เช็กเกอร์ทำให้โปรแกรม Rust ที่ปลอดภัยปฏิบัติตามกฎเหล่านี้ อย่างที่เราเห็นในตัวอย่างข้างต้น แต่คอมไพเลอร์มักจะมองปัญหานี้ "ย้อนกลับ" จากมุมมองของสแต็กด์บอร์โรวส์ แทนที่จะพูดว่าการใช้ `ref1` ทำให้ `ref2` ไม่ถูกต้อง มันยืนยันว่า `ref2` *ต้อง* ถูกต้องสำหรับการใช้งานทั้งหมดของมัน และ `ref1` เป็นตัวที่ทำให้เกิดปัญหาโดยการใช้งานก่อนเวลา

ดังนั้น "cannot use `*ref1` because it was mutably borrowed" มันเป็นผลลัพธ์เดียวกัน (โดยเฉพาะอย่างยิ่งกับไลฟ์ไทม์ที่ไม่ใช่นิพจน์) แต่ถูกนำเสนอในลักษณะที่อาจเป็นธรรมชาติมากกว่า

แต่บอร์โรว์เช็กเกอร์ไม่สามารถช่วยเราได้เมื่อเราเริ่มใช้ตัวชี้ unsafe!




# สแต็กด์บอร์โรวส์ที่ไม่ปลอดภัย

ดังนั้นเราต้องการมีวิธีให้ตัวชี้ unsafe เข้าร่วมในระบบสแต็กด์บอร์โรวส์นี้ แม้คอมไพเลอร์จะติดตามมันไม่ได้อย่างถูกต้อง และเราต้องการให้ระบบค่อนข้างอนุญาตให้มากเพื่อที่จะไม่ *ง่าย* เกินไปที่จะทำให้มันเสียหายและก่อให้เกิด UB

นั่นเป็นปัญหาที่ยาก และฉันไม่รู้ว่าจะแก้ไขอย่างไร แต่ผู้ที่ทำงานเกี่ยวกับสแต็กด์บอร์โรวส์ได้คิดหาสิ่งที่น่าเชื่อถือ และ miri พยายามที่จะใช้มัน

แนวคิดระดับสูงมากคือเมื่อคุณแปลงเรเฟอเรนซ์ (หรือตัวชี้ที่ปลอดภัยอื่นๆ) เป็นตัวชี้ดิบ (raw pointer) มันเหมือนกับการรับ reborrow ตอนนี้ตัวชี้ดิบ (raw pointer) ได้รับอนุญาตให้ทำอะไรก็ได้กับหน่วยความจำนั้น และเมื่อ reborrow หมดอายุก็เหมือนกับที่เกิดขึ้นกับ reborrow ปกติ

แต่คำถามคือ เมื่อไหร่ reborrow นั้นจะหมดอายุ? น่าจะเป็นเวลาที่ดีที่จะหมดอายุเมื่อคุณเริ่มใช้เรเฟอเรนซ์เดิมอีกครั้ง ไม่เช่นนั้นสิ่งต่างๆ จะไม่เป็นสแต็กที่ซ้อนกันอย่างดี

แต่เดี๋ยวก่อน คุณสามารถแปลงตัวชี้ดิบ (raw pointer) *เป็น* เรเฟอเรนซ์ได้! และคุณสามารถคัดลอกตัวชี้ดิบ (raw pointer) ได้! ถ้าคุณไป `&mut -> *mut -> &mut -> *mut` แล้วเข้าถึง `*mut` ตัวแรกล่ะ? สแต็กด์บอร์โรวส์ทำงานอย่างไรตอนนั้น?

ฉันไม่รู้จริงๆ! นั่นคือเหตุผลที่สิ่งต่างๆ ซับซ้อน ในความเป็นจริงมัน *ซับซ้อนเป็นพิเศษ* เพราะสแต็กด์บอร์โรวส์ *พยายาม* ที่จะอนุญาตให้มากขึ้นและปล่อยให้โค้ด unsafe จำนวนมากทำงานในแบบที่คุณคาดหวัง นี่คือเหตุผลที่ฉันรันสิ่งต่างๆ ภายใต้ miri เพื่อพยายามช่วยฉันจับข้อผิดพลาด

ในความเป็นจริง ความยุ่งเหยิงนี้เป็นเหตุผลที่มีโหมดของ miri ที่เป็นรุ่นทดลองพิเศษและเคร่งครัดพิเศษ: `-Zmiri-tag-raw-pointers`

เพื่อเปิดใช้งาน เราต้องส่งมันผ่านตัวแปรสภาพแวดล้อม MIRIFLAGS แบบนี้:

```text
MIRIFLAGS="-Zmiri-tag-raw-pointers" cargo +nightly-2022-01-21 miri test
```

หรือแบบนี้บน Windows ที่คุณต้องตั้งค่าตัวแปรแบบทั่วโลก:

```text
$env:MIRIFLAGS="-Zmiri-tag-raw-pointers"
cargo +nightly-2022-01-21 miri test
```

เราจะพยายามปฏิบัติตามโหมดเคร่งครัดพิเศษนี้โดยทั่วไปเพื่อให้ *มั่นใจ* เป็นพิเศษในงานของเรา มันยัง "ง่ายกว่า" ในบางแง่ ดังนั้นมันจึงดีกว่าสำหรับการเล่นและการได้สัมผัสกับสแต็กด์บอร์โรวส์






# การจัดการสแต็กด์บอร์โรวส์

ดังนั้นเมื่อใช้ตัวชี้ดิบ (raw pointer) เราจะพยายามยึดตามฮิวริสติกที่เรียบง่ายและตรงไปตรงมาและหวังว่าจะมีช่วงผิดพลาดที่กว้าง:

**เมื่อคุณเริ่มใช้ตัวชี้ดิบ (raw pointer) พยายามใช้เฉพาะตัวชี้ดิบ (raw pointer) เท่านั้น**

สิ่งนี้ทำให้มันเป็นไปได้ยากที่สุดที่จะสูญเสีย "สิทธิ์" ของตัวชี้ดิบ (raw pointer) ในการเข้าถึงหน่วยความจำโดยบังเอิญ

> **ผู้บรรยาย:** นี้เกินจริงในสองแง่:
>
> 1. ตัวชี้ที่ปลอดภัยมักจะยืนยันคุณสมบัติมากกว่าการแอลิเอส: หน่วยความจำถูกจัดสรร จัดตำแหน่ง ใหญ่พอที่จะเก็บชนิดของสิ่งที่ชี้ไป สิ่งที่ชี้ไปถูกเริ่มต้นอย่างถูกต้อง ฯลฯ ดังนั้นมันจึงอันตรายมากขึ้นที่จะโยนมันไปมาเมื่อสิ่งต่างๆ อยู่ในสถานะที่น่าสงสัย
>
> 2. แม้ว่าคุณจะอยู่ในโลกของตัวชี้ดิบ (raw pointer) คุณก็ไม่สามารถแอลิเอสหน่วยความจำใดๆ ได้อย่างอิสระ ตัวชี้เชื่อมโยงกับ "การจัดสรร" เฉพาะ (ซึ่งอาจละเอียดเท่ากับตัวแปรบนสแต็ก) และคุณไม่ควรนำตัวชี้จากการจัดสรรหนึ่ง จัดตำแหน่งมัน แล้วเข้าถึงหน่วยความจำในการจัดสรรอื่น หากอนุญาตให้ทำสิ่งนี้ จะ *มี* ภัยคุกคามของชายตัวเล็กขี้โมโห *ทุก* ที่ *ตลอดเวลา* นี่เป็นส่วนหนึ่งของเหตุผลที่ "ตัวชี้เป็นแค่จำนวนเต็ม" เป็นมุมมองที่ *มีปัญหา*

ตอนนี้เรายังต้องการเรเฟอเรนซ์ที่ปลอดภัยใน *อินเทอร์เฟซ* ของเรา เพราะเราต้องการสร้าง *abstract ที่ปลอดภัย* ที่ดีเพื่อให้ผู้ใช้ลิงก์ลิสต์ของเราไม่ต้องรู้หรือกังวล

ดังนั้นสิ่งที่เราจะทำคือ:

1. ที่จุดเริ่มต้นของเมธอด ใช้เรเฟอเรนซ์ที่รับเข้ามาเพื่อรับตัวชี้ดิบ (raw pointer) ของเรา
2. พยายามที่ดีที่สุดที่จะใช้เฉพาะตัวชี้ unsafe จากจุดนี้เป็นต้นไป
3. แปลงตัวชี้ดิบ (raw pointer) ของเรากลับเป็นตัวชี้ที่ปลอดภัยเมื่อสิ้นสุดหากจำเป็น

แต่ฟิลด์ของชนิดของเราเป็นส่วนตัว ดังนั้นเราจะเก็บมันไว้ *ทั้งหมด* เป็นตัวชี้ดิบ (raw pointer)

ในความเป็นจริง ส่วนหนึ่งของความผิดพลาดครั้งใหญ่ที่เราทำคือการยังคงใช้ Box! Box มี annotation พิเศษที่บอกคอมไพเลอร์ว่า "เฮ้ นี่เหมือน `&mut` มาก เพราะมันเป็นเจ้าของตัวชี้นั้นแต่เพียงผู้เดียว" ซึ่งเป็นเรื่องจริง!

แต่ตัวชี้ดิบ (raw pointer) ที่เราเก็บไว้จนถึงปลายลิสต์กำลังชี้เข้าไปใน Box ดังนั้นเมื่อใดก็ตามที่เราเข้าถึง Box ตามปกติ เราน่าจะทำให้ "reborrow" ของตัวชี้ดิบ (raw pointer) นั้นไม่ถูกต้อง! ☠

ในส่วนถัดไปเราจะกลับไปเป็นรูปแบบจริงของเราและชนหัวของเราเข้ากับตัวอย่างหลายตัวอย่าง
