# Variance และ PhantomData

คงจะน่ารำคาญพิลึกถ้าเราผลัดเรื่องนี้ออกไปแล้วต้องย้อนกลับมาแก้มือทีหลัง ดังนั้นเรามาจัดการกับเนื้อหา Layout ขั้นฮาร์ดคอร์ให้จบตั้งแต่ตอนนี้เลยดีกว่า

จตุรอาชา (แถมอีกหนึ่ง) แห่งความวิปโยคในการสร้าง unsafe collection บน Rust มีอยู่ 5 ประการด้วยกัน:

1. [Variance](https://doc.rust-lang.org/nightly/nomicon/subtyping.html)
2. [Drop Check](https://doc.rust-lang.org/nightly/nomicon/dropck.html)
3. [NonNull Optimizations](https://doc.rust-lang.org/nightly/std/ptr/struct.NonNull.html)
4. [The isize::MAX Allocation Rule](https://doc.rust-lang.org/nightly/nomicon/vec/vec-alloc.html)
5. [Zero-Sized Types](https://doc.rust-lang.org/nightly/nomicon/vec/vec-zsts.html)

ยังโชคดีที่ 2 ข้อสุดท้ายจะไม่เป็นปัญหาสำหรับเราในบทนี้

ส่วนข้อสาม เรา*จะ*เก็บมาเป็นปัญหาให้ปวดหัวก็ได้ แต่มันได้ไม่คุ้มเสีย &mdash; เพราะถ้าคุณริอาจเลือกใช้ `LinkedList` ตั้งแต่แรก นั่นแปลว่าคุณได้ยอมแพ้ต่อสงครามความคุ้มค่าด้านหน่วยความจำ (memory-efficiency) ไปเรียบร้อยแล้วกว่า 100 เท่า

ส่วนข้อสองคือสิ่งที่ผมเคยดึงดันว่ามันสำคัญนักหนาและใน std ก็มีแอบเล่นท่ายากกับมันอยู่ แต่ค่าเริ่มต้นของมันนั้นปลอดภัยดีอยู่แล้ว แถมวิธีเข้าไปยุ่มย่ามกับมันก็ยังเป็นฟีเจอร์ unstable และคุณจะต้องพยายาม*อย่างเลือดตาแทบกระเด็น*ถึงจะสังเกตเห็นข้อจำกัดของค่าเริ่มต้นนั้นได้ ดังนั้น อย่าไปคิดมากเลยครับ

นั่นทำให้เหลือแค่เรื่อง Variance เพียงอย่างเดียว พูดตามตรง คุณจะแกล้งทำเป็นมองไม่เห็นมันไปก่อนก็ได้เหมือนกัน แต่ในฐานะที่ผมยังคงมีศักดิ์ศรีของ "คนทำ Collection" ค้ำคออยู่ เราจึงจะมาลุยเรื่อง Variance กันให้รู้ดำรู้แดงไปเลย!

เซอร์ไพรส์ครับ: Rust มีระบบ subtyping ซ่อนอยู่ด้วย โดยเฉพาะอย่างยิ่ง `&'big T` นั้นถือเป็น *subtype* ของ `&'small T` ทำไมถึงเป็นงั้นล่ะ? ก็เพราะว่าถ้าโค้ดท่อนหนึ่งต้องการ reference ที่มีอายุการใช้งานครอบคลุมช่วงหนึ่งของโปรแกรม การที่เราส่ง reference ที่มีอายุยืนยาว*นานกว่านั้น*ไปให้ มันย่อมปลอดภัยหายห่วงอยู่แล้วใช่ไหมล่ะ? ในเชิงสัญชาตญาณ มันก็เมคเซนส์ชัดเจนอยู่แล้ว ถูกไหมครับ?

ทำไมเรื่องนี้ถึงสำคัญ? ลองจินตนาการถึงโค้ดธรรมดาๆ ที่รับค่า 2 ค่าที่มี type เดียวกัน:

```rust ,ignore
fn take_two<T>(_val1: T, _val2: T) { }
```

นี่คือโค้ดที่แสนจะน่าเบื่อ และเราก็ย่อมคาดหวังว่ามันจะทำงานกับ `T = &u32` ได้อย่างราบรื่น จริงไหม?

```rust
fn two_refs<'big: 'small, 'small>(
    big: &'big u32, 
    small: &'small u32,
) {
    take_two(big, small);
}

fn take_two<T>(_val1: T, _val2: T) { }
```

ใช่แล้ว คอมไพล์ผ่านฉลุย!

คราวนี้ มาลองเล่นพิเรนทร์ด้วยการห่อมันไว้ใน... เอ่อ... ไม่รู้สิ `std::cell::Cell` ดูหน่อยเป็นไง:

```rust ,compilefail
use std::cell::Cell;

fn two_refs<'big: 'small, 'small>(
    // NOTE: these two lines changed
    big: Cell<&'big u32>, 
    small: Cell<&'small u32>,
) {
    take_two(big, small);
}

fn take_two<T>(_val1: T, _val2: T) { }
```

หือ??? เราไม่ได้ไปแตะต้อง lifetime เลยสักกะติ๊ด ทำไมคราวนี้คอมไพเลอร์ถึงของขึ้นล่ะเนี่ย!?

อ๋อ... กลไก subtyping ของ lifetime มันคงจะทำมาแบบทื่อๆ ง่ายๆ แน่เลย พอเอา reference ไปห่อไว้ในอะไรสักอย่างมันก็เลยเอ๋อทันที ดูสิ เอาไปห่อใน `Vec` ก็ต้องพังเหมือนกันแน่ๆ:

```rust
fn two_refs<'big: 'small, 'small>(
    big: Vec<&'big u32>, 
    small: Vec<&'small u32>,
) {
    take_two(big, small);
}

fn take_two<T>(_val1: T, _val2: T) { }
```

เห็นไหมล่ะ มันคอมไพล์ไม่ผ่า-- เดี๋ยวๆๆ อะไรวะเนี่ย??? `Vec` มีเวทมนตร์เรอะ??????

ก็... ใช่ แต่ก็ไม่เชิง เวทมนตร์นั้นแท้จริงแล้วสถิตอยู่ในใจเรามาโดยตลอด และเวทมนตร์นั้นมีชื่อว่า ✨*Variance*✨

ลองไปอ่าน [บทเรื่อง subtyping ใน Rustonomicon](https://doc.rust-lang.org/nightly/nomicon/subtyping.html) ดูได้ถ้าอยากรู้รายละเอียดไส้ในแบบเลือดสาด แต่โดยสรุปสั้นๆ คือ subtyping *ไม่ได้*ปลอดภัยเสมอไป โดยเฉพาะอย่างยิ่ง มันจะไม่ปลอดภัยทันทีที่มี mutable reference เข้ามาเอี่ยว เพราะคุณสามารถหยิบฟังก์ชันอย่าง `mem::swap` มาสลับค่า แล้วอยู่ดีๆ ก็เกิด dangling pointer ขึ้นมาเฉยเลย!

อะไรก็ตามที่ "ทำตัวคล้ายกับ mutable reference" จะถูกจัดให้เป็น *invariant* ซึ่งแปลว่ามันจะปิดกั้นไม่ให้เกิด subtyping บน generic parameter ของมัน ดังนั้น เพื่อความปลอดภัยสูงสุด `&mut T` จึงเป็น invariant เมื่อเทียบกับ `T` และ `Cell<T>` ก็เป็น invariant เมื่อเทียบกับ `T` เช่นกัน เพราะ `&Cell<T>` โดยเนื้อแท้แล้วก็แทบไม่ต่างอะไรกับ `&mut T` (สืบเนื่องมาจาก interior mutability)

ส่วนสิ่งอื่นๆ เกือบทั้งหมดที่ไม่ใช่ invariant จะมีสถานะเป็น *covariant* ซึ่งหมายความว่ากฎ subtyping สามารถ "ทะลุผ่าน" มันไปได้ และยังคงทำงานได้ตามปกติ (นอกจากนี้ยังมีประเภท contravariant ที่ทำให้ subtyping ไหลย้อนกลับทิศทางด้วย แต่มันหายากมากและไม่มีใครชอบมัน ดังนั้นผมจะไม่เอ่ยถึงมันอีก)

โดยทั่วไป Collection มักจะเก็บ mutable pointer ชี้ไปยังข้อมูลของตัวเอง คุณจึงอาจคิดว่าพวกมันก็น่าจะเป็น invariant ด้วยเหมือนกัน แต่ในความเป็นจริง มันไม่จำเป็นต้องเป็นแบบนั้นครับ! ด้วยระบบ ownership ของ Rust ทำให้ในเชิงความหมาย `Vec<T>` มีค่าเทียบเท่ากับตัว `T` เอง และนั่นทำให้มันปลอดภัยอย่างยิ่งที่จะทำตัวเป็น covariant!

แต่อนิจจา นิยาม struct ของเราข้างล่างนี้ ดันมีสถานะเป็น invariant:

```rust
pub struct LinkedList<T> {
    front: Link<T>,
    back: Link<T>,
    len: usize,
}

type Link<T> = *mut Node<T>;

struct Node<T> {
    front: Link<T>,
    back: Link<T>,
    elem: T, 
}
```

แล้วจริงๆ แล้ว Rust ตัดสินใจเรื่อง variance ของประเภทข้อมูลต่างๆ อย่างไรกันล่ะ? ย้อนกลับไปในยุคโบราณกาลก่อน Rust 1.0 เราเคยลองเปิดให้โปรแกรมเมอร์กำหนด variance ที่ตัวเองต้องการได้เองตามใจชอบ... และผลลัพธ์คือ หายนะวินาศสันตะโรขั้นสุด! เรื่อง subtyping กับ variance มันเป็นอะไรที่เข้าใจได้ยากสุดกู่ แม้แต่นักพัฒนาระดับแกนนำของ Rust ยังเถียงกันคอเป็นเอ็นเรื่องนิยามคำศัพท์พื้นฐานเลยด้วยซ้ำ! เราก็เลยเปลี่ยนมาใช้วิธี "variance by example" แทน: โดยคอมไพเลอร์จะก้มดูฟิลด์ต่างๆ ภายใน struct ของคุณ แล้วก็ก็อปปี้คุณสมบัติ variance ของฟิลด์เหล่านั้นมาใช้ หากเกิดข้อขัดแย้งไม่ลงรอยกัน invariance จะเป็นฝ่ายชนะเสมอ เพราะนั่นคือทางเลือกที่ปลอดภัยที่สุด

ถ้าอย่างนั้น ฟิลด์ตัวไหนใน struct ของเรากันล่ะที่ทำให้ Rust อารมณ์เสีย? คำตอบคือ `*mut` ไงล่ะ!

Raw pointer ใน Rust โดยพื้นฐานแล้วมันพยายามจะปล่อยให้คุณทำอะไรก็ได้ตามใจชอบ แต่มันมีฟีเจอร์ความปลอดภัยอยู่เพียงข้อเดียวเท่านั้น: เนื่องจากคนส่วนใหญ่ไม่รู้เรื่องว่าใน Rust มีเรื่อง variance กับ subtyping อยู่ด้วย และการปล่อยให้มันเป็น covariant *แบบผิดๆ* จะอันตรายถึงชีวิต ดังนั้น `*mut T` จึงถูกบังคับให้เป็น invariant ไว้ก่อน เพราะมีความเป็นไปได้สูงมากที่มันจะถูกนำไปใช้งาน "ในฐานะ" `&mut T`

เรื่องนี้น่าหงุดหงิดเป็นบ้าสำหรับคนอย่างผมโดยเฉพาะ ในฐานะคนที่อุทิศชีวิตให้กับการเขียน collection ในภาษา Rust มานับไม่ถ้วน นี่จึงเป็นเหตุผลว่าทำไมตอนที่ผมสร้าง [std::ptr::NonNull](https://doc.rust-lang.org/std/ptr/struct.NonNull.html) ขึ้นมา ผมถึงได้แอบยัดเวทมนตร์ชิ้นเล็กๆ นี้เข้าไปด้วย:

> แตกต่างจาก `*mut T` ตรงที่ `NonNull<T>` ถูกเลือกให้มีสถานะเป็น covariant เมื่อเทียบกับ `T` สิ่งนี้ทำให้เราสามารถนำ `NonNull<T>` ไปใช้ในการสร้าง covariant type ได้ แต่ก็แฝงมาด้วยความเสี่ยงเรื่องความไม่ปลอดภัย (unsoundness) หากนำไปใช้ใน type ที่ไม่ควรจะเป็น covariant จริงๆ

แต่อ้าว... interface ของมันก็ยังวนเวียนอยู่กับ `*mut T` นี่นา แล้วมันทำได้ยังไงกันล่ะ!? มันเป็นเวทมนตร์หรือเปล่า!? มาดูกันครับ:

```rust
pub struct NonNull<T> {
    pointer: *const T,
}


impl<T> NonNull<T> {
    pub unsafe fn new_unchecked(ptr: *mut T) -> Self {
        // SAFETY: the caller must guarantee that `ptr` is non-null.
        unsafe { NonNull { pointer: ptr as *const T } }
    }
}
```

ไม่อะ! ไม่มีเวทมนตร์อะไรทั้งนั้นแหละ! `NonNull` มันแค่หน้าด้านฉวยโอกาสจากความจริงที่ว่า `*const T` มีสถานะเป็น covariant แล้วแอบเก็บค่านั้นไว้ข้างในแทน จากนั้นก็อาศัยการแคสต์สลับไปมาระหว่าง `*mut T` ตรงขอบเขตของ API เพื่อตบตาให้ "ดูเหมือนกับว่า" มันกำลังเก็บ `*mut T` อยู่เท่านั้นเอง! ลูกเล่นมีแค่นั้นจริงๆ! และนี่แหละคือวิธีที่ทำให้ collection ใน Rust กลายสภาพเป็น covariant ได้! ซึ่งมันทุเรศทุรังมาก! ผมก็เลยสร้าง Good Pointer Type ตัวนี้ขึ้นมาทำเรื่องบัดซบนี้แทนคุณยังไงล่ะ! ไม่ต้องขอบคุณหรอก! ขอให้สนุกกับปืนยิงเท้าฉบับ subtyping นะพวก!

ทางออกสำหรับปัญหาทั้งหมดของคุณก็คือการหันมาใช้ `NonNull` และถ้าคุณอยากได้พอยน์เตอร์ที่ยอมให้เป็น null ได้อีกครั้ง ก็แค่ห่อมันด้วย `Option<NonNull<T>>` แล้วเราจะต้องลำบากลำบนทำขนาดนั้นจริงๆ เหรอ..?

ช่ายยย! มันห่วยแตกสิ้นดี แต่นี่เรากำลังจะสร้าง *production grade linked list* กันนะเฟ้ย ดังนั้นเราจึงต้องยอมกลืนเลือดกินผักขมๆ แล้วเลือกเดินทางสายโหด (จริงๆ เราจะใช้ `*const T` เพียวๆ แล้วเที่ยวไปแคสต์มั่วซั่วทุกที่ก็ได้แหละ แต่ผมอยากรู้จริงๆ ว่ามันจะทรมานสักแค่ไหน... เพื่อการทดลองวิทยาศาสตร์ด้าน Ergonomics)


ดังนั้น นี่คือนิยาม type ฉบับสุดท้ายของเรา:

```rust
use std::ptr::NonNull;

// !!!This changed!!!
pub struct LinkedList<T> {
    front: Link<T>,
    back: Link<T>,
    len: usize,
}

type Link<T> = Option<NonNull<Node<T>>>;

struct Node<T> {
    front: Link<T>,
    back: Link<T>,
    elem: T, 
}
```

...เดี๋ยวนะ ยังไม่หมด มีอีกเรื่องหนึ่ง ทุกครั้งที่คุณยุ่งเกี่ยวกับ raw pointer คุณควรจะอัญเชิญ "ภูตผี (Ghost)" มาคอยคุ้มครองพอยน์เตอร์ของคุณไว้ด้วยเสมอ:

```rust ,ignore
use std::marker::PhantomData;

pub struct LinkedList<T> {
    front: Link<T>,
    back: Link<T>,
    len: usize,
    /// We semantically store values of T by-value.
    _boo: PhantomData<T>,
}
```

ในกรณีนี้ ผมไม่คิดว่าเรา*จำเป็นต้องใช้* [PhantomData](https://doc.rust-lang.org/std/marker/struct.PhantomData.html) จริงๆ หรอก แต่ทุกครั้งที่คุณ*เริ่มใช้* `NonNull` (หรือ raw pointer ทั่วๆ ไป) คุณควรจะใส่มันไว้เสมอเพื่อความปลอดภัย และเพื่อเป็นการประกาศบอกคอมไพเลอร์รวมถึงคนอื่นๆ ให้เข้าใจตรงกันว่าคุณ*คิดว่า*ตัวเองกำลังทำอะไรอยู่

PhantomData เป็นวิธีที่เรามอบฟิลด์ "ตัวอย่าง" จำลองให้คอมไพเลอร์ดู ซึ่งเป็นฟิลด์ที่*ในเชิงแนวคิด*ควรจะมีตัวตนอยู่ใน struct ของคุณ แต่ด้วยเหตุผลหลายประการ (เช่น indirection หรือ type erasure) มันเลยไม่มีอยู่จริง ในเคสนี้เราเลือกใช้ `NonNull` เพราะเรากำลังกล่าวอ้างว่า struct ของเราทำตัว "เสมือนกับว่า" มันเก็บค่า `T` ไว้ข้างใน ดังนั้นเราจึงแปะ PhantomData เอาไว้เพื่อยืนยันเจตนารมณ์นั้นให้ชัดเจน

อันที่จริง stdlib มีเหตุผลอื่นอีกในการทำแบบนี้ เพราะมันมีอภิสิทธิ์เข้าถึงฟีเจอร์คำสาปอย่าง [Drop Check overrides](https://doc.rust-lang.org/nightly/nomicon/dropck.html) แต่ฟีเจอร์นั้นถูกรื้อแก้ไปหลายตลบจนผมเองก็ไม่แน่ใจแล้วว่า PhantomData ยัง*จำเป็น*สำหรับมันอยู่อีกหรือไม่ แต่ถึงอย่างนั้น ผมก็ยังจะขอกราบไหว้ยึดถือทำตามๆ กันมา (cargo-cult) ต่อไปชั่วกัลปวสานอยู่ดี เพราะมนต์ดำของ Drop Check มันถูกฝังลึกลงในรอยหยักสมองของผมไปเรียบร้อยแล้ว!

(ส่วน `Node` นั้น มันเก็บ `T` ไว้ในตัวจริงๆ อยู่แล้ว จึงไม่จำเป็นต้องทำอะไรแบบนี้... เย้!)
